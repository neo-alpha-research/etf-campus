# Antigravity 작업 지시: 인프라 방향 결정 통보와 순차 실행 지시

작성일: 2026-08-21
발신: EVS Navigator
용도: 아래 구분선 안의 전문을 Antigravity에 그대로 전달하십시오.

---

## 결정 통보

인프라 현황 조사 회신을 검토했습니다. 큰 방향은 채택합니다. **Cloudflare 이전은 하지 않고, 저장소는 private을 유지하며, 데이터 단일 진실은 계속 Git에 둡니다.** 자체 서버는 코어 서비스 대체가 아니라 모니터링과 백오피스 용도로만 씁니다.

다만 회신 내용 중 세 가지를 정정합니다.

**정정 1. 측정값이 실제 청구 분을 대표하지 못합니다.** 보고된 소모 합계는 약 384분인데 한도는 2,000분입니다. 19퍼센트만 설명됩니다. `gh run list --limit 100`은 최근 100건이지 이번 달 전체가 아니고, GitHub는 job 단위로 분 단위 올림 청구를 하므로 "1분 미만"으로 기록된 실행도 각각 1분씩 청구됩니다. 나머지 1,600분의 출처를 모르는 상태이므로 재측정이 필요합니다.

**정정 2. 권고 우선순위가 뒤바뀌어 있습니다.** 회신은 배포 워크플로를 주범(63회, 322분)으로 지목해 놓고 권고 1순위로 `daily-market.yml`의 빌드 제거를 제시했습니다. 그 빌드는 데이터가 갱신된 rung에서만 도는 조건부 실행이라 월 약 85분, 한도의 4퍼센트입니다. 배포 워크플로가 실제 지렛대입니다. 빌드 제거는 함께 실행하되 1순위는 아닙니다.

**정정 3. public 반대의 근거를 교체합니다.** "포함되었을지 모르는 설정값"은 추정입니다. 결론은 유지하되 근거는 다음 둘로 대체합니다. 첫째, 공개 시 커밋 작성자 이메일이 노출되어 Neo의 익명성이 깨집니다. 둘째, 운용사별 연금 편입 목록 대조 데이터는 복제가 어려운 자산이며 공개는 이를 무상 제공하는 것과 같습니다.

**추가 지적.** 회신은 자체 서버를 "언제든 꺼져도 되는 작업"에만 쓰라고 하면서 동시에 일일 수집을 n8n으로 넘기라고 권고했습니다. 일일 수집은 꺼지면 안 되는 작업이고 서버는 1개월 뒤 회수됩니다. 이 모순은 아래 6단계의 이중 스케줄러 안전망으로 해소합니다.

## 작업 방식

아래 1단계부터 6단계까지 **한 번에 하나씩** 진행하고 각 단계 완료 후 보고한 뒤 다음으로 넘어가십시오. 여러 단계를 묶어 진행하지 마십시오.

모든 단계에 다음 규칙이 적용됩니다.

기존 파일을 통째로 다시 쓰지 말고 증분 편집만 하십시오. 파일 전체를 생성하는 스크립트 방식을 금지합니다. 완료 보고에 `git diff --stat`을 반드시 포함하고, 삭제 줄 수가 추가 줄 수보다 많은 파일이 있으면 사유를 설명하십시오. 임시 파일과 백업 파일을 저장소에 남기지 마십시오. 모든 파일은 UTF-8로 저장하고 저장 후 검증하십시오. 기존 타입 계약이나 응답 형태를 변경해야 한다면 구현을 멈추고 먼저 질문하십시오. 문서에 없는 결정이 필요하면 임의로 정하지 말고 질문하십시오.

## 1단계. 실제 청구 분 재측정 (읽기 전용, 코드 변경 없음)

아래 API로 계정 수준의 실제 청구 분을 조회하십시오. 이것이 유일하게 권위 있는 숫자입니다.

```
GET /orgs/neo-alpha-research/settings/billing/actions
```

`total_minutes_used`, `included_minutes`, `total_paid_minutes_used`, `minutes_used_breakdown`을 그대로 보고하십시오. API가 동작하지 않으면 GitHub 결제 대시보드에서 확인해 스크린샷 또는 수치를 보고하십시오.

**함께 확인할 것.** 2,000분 한도는 저장소가 아니라 조직 단위로 공유됩니다. `neo-alpha-research` 조직의 전체 저장소 목록과 각 저장소의 Actions 사용 여부를 확인해, `etf-campus` 외에 같은 풀을 소모하는 저장소가 있는지 보고하십시오.

**완료 판정.** 실제 청구 분과 조직 내 다른 소비처가 확인되어 384분과 2,000분 사이의 격차가 설명되면 완료입니다. 설명되지 않으면 그 사실 자체를 보고하십시오.

## 2단계. 배포 워크플로 트리거 축소 (최대 절감)

`market-briefing-production.yml`이 확인된 최대 소비처입니다.

**먼저 조사하십시오.** 이 워크플로가 실제로 배포하는 대상 디렉터리를 특정하고, 최근 63회 실행 중 몇 건이 그 대상과 무관한 변경(문서, `data/` 커밋, 프런트엔드 등)으로 촉발되었는지 집계해 보고하십시오. **이 집계 결과를 먼저 보고한 뒤 수정에 착수하십시오.**

**그다음 아래를 적용하십시오.**

경로 필터를 적용해 배포 대상 코드가 변경될 때만 실행되게 하십시오. `data/` 일일 커밋이나 `docs/` 변경으로 배포가 도는 일이 없어야 합니다.

`concurrency` 그룹에 `cancel-in-progress`를 적용하되 **브랜치에 따라 다르게 두십시오.** PR 및 프리뷰 실행에는 `true`를 적용해 연속 푸시 시 이전 실행을 취소합니다. main 브랜치의 프로덕션 배포에는 `false`를 유지하십시오. 배포 도중 취소는 위험합니다.

draft PR에서는 실행하지 않도록 조건을 추가하십시오.

**완료 판정.** 경로 필터 적용 후 `data/` 커밋만으로는 배포 워크플로가 트리거되지 않는 것을 실제 커밋으로 확인하고, 프로덕션 배포 경로는 그대로 동작하는 것을 확인하면 완료입니다.

## 3단계. daily-market 빌드 제거와 워크플로 시작 시각 재분산

### 3-1. 빌드 스텝 제거

`daily-market.yml`의 `Validate refreshed data` 스텝에서 `npm run build`만 제거하십시오. `python -m unittest discover -s scripts/tests`와 `npm test`는 유지합니다. Cloudflare Pages가 커밋마다 자체 인프라에서 다시 빌드하므로 중복이며, 회신에서 이 스텝이 오류를 걸러낸 이력이 없다고 보고된 바 있습니다.

**착수 전 확인.** 같은 워크플로의 후속 스텝이 빌드 산출물(`.next` 등)에 의존하는지 검사하고, 의존이 있으면 제거하지 말고 보고하십시오.

`npm ci`는 `npm test` 실행에 필요하므로 유지합니다. 다만 `steps.changes.outputs.changed == 'true'` 조건이 그대로 걸려 있는지 확인하십시오.

### 3-2. 동시 실행으로 인한 무음 취소 위험 점검 (중요)

`daily-market.yml`, `daily-distribution.yml`, `daily-fees.yml`이 현재 모두 `cron: "37 21,22 * * 1-5"`로 **같은 분에 시작**하며, 셋 다 `concurrency: group: daily-etf-data`, `cancel-in-progress: false`를 공유합니다.

GitHub의 동시성 규칙상 한 그룹에 실행 중인 run과 대기 중인 run이 있는 상태에서 새 run이 들어오면 **대기 중이던 run이 취소됩니다.** 세 워크플로가 동시에 트리거되면 하나는 실행, 하나는 대기, 세 번째가 도착하며 대기 중이던 것을 취소시킵니다. 즉 매일 세 작업 중 하나가 조용히 취소되고 있을 가능성이 있습니다.

**이것이 보고된 "작업 소실" 현상의 원인 중 하나일 수 있습니다.**

먼저 최근 실행 이력에서 `conclusion == "cancelled"`인 건수를 워크플로별로 집계해 이 가설을 검증하고 보고하십시오.

가설이 확인되면 세 워크플로의 시작 시각을 최소 15분 간격으로 분산하십시오. 예를 들어 `daily-market`은 `:07`, `daily-distribution`은 `:22`, `daily-fees`는 `:37`입니다. 공유 `concurrency` 그룹은 git push 충돌 방지를 위해 유지하십시오.

**완료 판정.** 취소 건수 집계 결과를 보고하고, 시각 분산 적용 후 세 워크플로가 모두 정상 완료되는 것을 최소 1영업일 확인하면 완료입니다.

## 4단계. D1 잠금 문제 해결 (P0, Actions 절감과 동급)

회신에서 보고한 다음 현상이 이번 조사에서 가장 중요한 발견입니다.

> 수집은 되었으나 이벤트 발행 단계에서 멈추면 `market_data_readiness`나 `market_source_consumer_runs`에 `processing` 또는 `skipped_duplicate` 상태로 잠금이 남고, 시스템이 복구되어도 이 잠금 때문에 다음 파이프라인이 영구적으로 무시됩니다.

자원 부족은 실행이 안 된 사실이 드러나지만, 잠금이 남으면 파이프라인이 정상 종료된 것처럼 보이면서 데이터가 조용히 누락됩니다. 24일자 누락이 실제 사례로 보고되었습니다.

**아래 세 가지를 D1 마이그레이션 `0009`로 구현하십시오.**

### 4-1. 임대 시간 부여

상태 레코드에 `locked_at` 컬럼을 추가하고, `processing` 상태로 진입할 때 현재 시각을 기록합니다. 상태를 조회하는 쪽에서 현재 시각과 `locked_at`의 차이가 **30분**을 넘으면 잠금이 만료된 것으로 간주해 자동 회수하고 재처리 가능 상태로 되돌립니다. 프로세스가 죽어도 잠금이 영구화되지 않습니다.

임계치 30분은 기본값이며, 환경변수로 조정 가능하게 두십시오.

### 4-2. 멱등 재처리

`skipped_duplicate`가 남은 상태에서 같은 기준일을 다시 처리할 때, 안전하게 통과하거나 명시적으로 실패해야 합니다. 지금처럼 조용히 무시되어서는 안 됩니다. 재처리 시도와 그 결과를 로그로 남기십시오.

### 4-3. 노후 잠금 알림

`monitor-market-daily-pipeline.yml`이 이미 매일 10:15 KST에 실행되고 있으므로, 여기에 "임계치를 넘긴 `processing` 레코드가 존재하는가" 검사를 추가하십시오. 존재하면 워크플로를 실패 처리하고 이슈를 생성합니다. 추가 실행 비용이 들지 않습니다.

### 4-4. 마이그레이션 작성 시 주의

`0008` 마이그레이션에 인덱스가 하나도 없었던 문제를 반복하지 마십시오. 상태와 시각으로 조회하므로 `(status, locked_at)` 복합 인덱스가 필요합니다.

**완료 판정.** 인위적으로 `processing` 상태를 30분 이상 남긴 뒤 다음 파이프라인이 정상적으로 잠금을 회수하고 진행하는 것을 테스트로 확인하고, 노후 잠금이 있을 때 모니터 워크플로가 실패하는 것을 확인하면 완료입니다. 경계 조건 테스트(29분, 31분)를 포함하십시오.

## 5단계. 커밋 이력 시크릿 스캔 (읽기 전용)

저장소 공개 여부와 무관하게 1회 수행합니다. private 저장소도 협업자 추가나 실수로 노출될 수 있습니다.

gitleaks 또는 trufflehog로 **전체 커밋 이력**을 스캔하십시오. 현재 워킹 트리만이 아니라 과거 이력 전체가 대상입니다.

**보고 시 실제 시크릿 값을 붙여넣지 마십시오.** 탐지된 항목의 파일 경로, 커밋 해시, 시크릿 유형, 탐지 규칙명만 보고하십시오.

함께 확인할 것으로, 커밋 작성자 이메일 목록을 중복 제거해 집계하십시오. 개인 실명 계정 이메일이 이력에 남아 있는지 확인하기 위함이며, 이는 Neo 익명성 관련 판단에 필요합니다. 이메일 전체를 보고하지 말고 도메인과 로컬파트 앞 두 글자만 마스킹해 보고하십시오.

**완료 판정.** 스캔 완료 보고서와 작성자 이메일 집계가 제출되면 완료입니다. 탐지 항목이 있으면 그 자체를 별도 P0 과제로 보고하고 임의로 이력을 재작성하지 마십시오.

## 6단계. 조기 종료 가드 (이중 스케줄러 안전망의 전제)

`daily-market.yml`의 수집 스텝 앞에 가드 스텝을 추가해, 이미 목표 거래일 데이터를 보유하고 있으면 이후 스텝 전체를 건너뛰게 하십시오.

```yaml
- name: Short-circuit when the target close is already committed
  id: guard
  run: |
    if python scripts/check_data_freshness.py; then
      echo "done=true" >> "$GITHUB_OUTPUT"
    else
      echo "done=false" >> "$GITHUB_OUTPUT"
    fi

- name: Refresh official ETF data
  if: steps.guard.outputs.done != 'true'
  ...
```

수동 실행(`workflow_dispatch`)에 `target` 입력이 있는 경우에는 가드를 건너뛰어야 합니다. 특정 날짜를 강제로 다시 수집하려는 의도이기 때문입니다.

이 가드는 두 가지 효과가 있습니다. 재시도 사다리의 두 번째 rung이 첫 rung 성공 시 몇 초 만에 종료되어 외부 API 호출과 Actions 분을 절약합니다. 그리고 이후 자체 서버의 n8n이 수집을 맡게 되더라도 GitHub Actions cron을 그대로 켜 둘 수 있어, 서버가 회수되거나 장애가 나면 Actions가 자동으로 이어받는 안전망이 됩니다.

**완료 판정.** 데이터가 이미 최신인 상태에서 워크플로를 수동 실행했을 때 수집 없이 조기 종료되고, `workflow_dispatch`에 `target`을 지정하면 가드를 건너뛰고 정상 수집되는 것을 확인하면 완료입니다.

## 이번 지시에 포함하지 않는 것

Cloudflare 이전, 저장소 public 전환, 데이터 저장소 변경은 하지 않습니다.

자체 서버의 Grafana와 appsmith 설치는 저장소 코드 변경이 아니라 서버 작업이므로 별도 지시로 진행합니다. n8n을 이용한 수집 이전은 서버 이용 기간 연장 가능 여부가 확인된 뒤에 결정합니다. 이번 지시에서 착수하지 마십시오.

Superset, Airbyte, ELK, RAGFlow, SIM은 현 규모에 과설계라는 판단에 동의하므로 추가 승인을 신청하지 마십시오.

1단계 재측정을 먼저 보고하십시오. 그 결과가 이후 우선순위를 바꿀 수 있습니다. 다만 2단계와 3단계는 재측정 결과와 무관하게 실행할 가치가 있으므로, 1단계 보고 직후 바로 착수해도 됩니다.

4단계는 데이터 정합성 문제이므로 Actions 절감과 병행해 진행하십시오. 5단계와 6단계는 그 이후입니다.

각 단계 완료 시 `git diff --stat`과 완료 판정 결과를 함께 보고하고 다음 지시를 기다리십시오.
