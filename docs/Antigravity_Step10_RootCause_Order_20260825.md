# Antigravity 지시: 근본 원인 확정과 스케줄 재설계

작성일: 2026-08-25
발신: EVS Navigator
용도: 아래 구분선 안의 전문을 Antigravity에 그대로 전달하십시오.

## 1. 이번 조사로 근본 원인이 확정되었습니다

가져오신 타임스탬프를 현재 크론 설정과 대조한 결과입니다.

| 항목 | 시각 (KST) |
|---|---|
| `daily-market` 예약 실행 | 06:07, 07:07 |
| 실제 데이터 도달 (8/19) | 08:08 |
| 실제 데이터 도달 (8/20) | 09:25 |
| 실제 데이터 도달 (8/21) | 10:52 |
| 실제 데이터 도달 (8/24) | 10:08 |

**4일 모두 마지막 예약 실행보다 늦게 도착했습니다. 현재 스케줄로는 단 하루도 자동으로 포착할 수 없습니다.**

원본 소스가 공개되기 전에 파이프라인이 돌고 끝나는 구조입니다. 그래서 매일 수동 개입이 필요했고, 그 수동 실행이 한도를 소진했으며, 한도가 소진되자 감시 장치까지 함께 죽었습니다.

### 1-1. 이것이 설명하는 것들

`daily-market`이 예약 42회 대비 124회 실행된 것, `Backfill`이 34회 실행된 것, 배포 워크플로가 215회 수동 실행된 것, 그리고 4일치 데이터가 전부 수동으로 채워진 것이 하나의 원인에서 나옵니다.

### 1-2. 절약이 원인을 만들었습니다

`daily-market.yml`의 주석에는 원래 06:17, 07:17, 08:17, 09:17 네 단계가 있었습니다. 이후 두 단계로 축소되었고 현재는 06:07, 07:07입니다.

**잘라낸 08시대와 09시대가 실제로 데이터를 잡던 구간입니다.** 분을 아끼려던 변경이 파이프라인의 자동 완료 능력을 없앴고, 그 결과 발생한 수동 실행이 아낀 것보다 훨씬 많은 분을 소모했습니다.

### 1-3. 모니터 시각도 어긋나 있습니다

모니터는 KST 10:15에 실행되는데, 8/21 데이터는 10:52에, 8/24는 10:08에 도달했습니다. **수집 창이 닫히기 전에 검사하므로 정상 지연을 실패로 오탐할 수 있습니다.** 감지 장치가 신뢰를 잃는 전형적인 원인입니다.

---

## 2. 수정 지시

### 2-1. 스케줄을 실제 공개 시각에 맞추십시오

조기 종료 가드(`steps.guard.outputs.already_run`)가 이미 구현되어 있으므로, 성공한 날의 후속 실행은 몇 초 만에 끝납니다. **단계를 늘리는 비용이 매우 낮습니다.**

`daily-market.yml`의 크론을 다음으로 변경하십시오.

```yaml
# UTC 23:07, 00:07, 01:07, 02:07, 03:07 = KST 08:07, 09:07, 10:07, 11:07, 12:07
- cron: "07 23 * * 1-5"
- cron: "07 0-3 * * 2-6"
```

06:07과 07:07은 제거하십시오. 관측된 4일 중 어느 날도 그 시각에 데이터가 없었으므로 실행할 이유가 없습니다.

**착수 전 확인.** 위 UTC 표기가 의도한 KST 시각과 일치하는지 직접 계산해 보고에 포함하십시오. 요일 지정(`1-5`와 `2-6`)이 자정을 넘는 구간에서 올바른지도 함께 검증하십시오.

### 2-2. 후속 워크플로 시각도 함께 조정하십시오

`daily-distribution`은 KST 06:22, 07:22, `daily-fees`는 06:37, 07:37입니다. 시장 데이터가 도착하기 전에 실행되므로 순서 전제가 깨져 있습니다.

두 워크플로가 시장 데이터 갱신에 실제로 의존하는지 먼저 확인하고, 의존한다면 `daily-market` 이후로 옮기십시오. 의존하지 않는다면(운용사 사이트와 네이버를 각각 수집하므로 독립일 수 있습니다) 현행 유지하되 그 근거를 보고에 적으십시오.

세 워크플로가 공유하는 `concurrency: daily-etf-data` 그룹 때문에 시각이 겹치면 대기 중 실행이 취소됩니다. 최소 15분 간격을 유지하십시오.

### 2-3. 모니터 시각을 뒤로 옮기십시오

`monitor-market-daily-pipeline.yml`을 KST 10:15에서 **13:15 이후**로 변경하십시오. 마지막 수집 단계(12:07)가 끝난 뒤에 검사해야 오탐이 사라집니다.

### 2-4. 공개 시각 데이터를 계속 축적하십시오

지금 근거는 4개 표본뿐입니다. 스케줄을 확정하려면 더 많은 관측이 필요합니다.

`market_source_snapshot_manifest`의 `created_at`을 주기적으로 집계해 실제 도달 시각의 분포를 파악할 수 있도록, 이 조회를 정기 점검 항목으로 문서에 기록해 두십시오. 2주 뒤 재검토해 단계 수를 조정합니다.

## 3. 감시 장치의 단일 장애점 해결

지적하신 내용이 정확합니다. 관측 대상과 관측 수단이 같은 인프라에 있으면 함께 죽습니다.

**해결책은 Cloudflare Worker cron입니다.** 이미 `market-event-dispatcher`가 5분마다 도는 Worker cron을 운영 중이고, Cloudflare 자원은 한도의 10퍼센트 내외로 여유가 큽니다.

기존 모니터 워크플로의 판정 로직을 그대로 Worker로 옮기고, KST 13:15에 하루 한 번 실행하십시오. 조회 대상과 실패 조건은 현행과 동일하게 유지합니다.

통지 방식은 GitHub Issue 생성이 불가능하므로 대체 수단이 필요합니다. 브리핑 발송에 쓰는 기존 경로를 재사용할 수 있는지 먼저 확인해 보고하십시오. 불가능하면 통지 방식을 별도로 협의합니다.

**GitHub Actions 모니터는 삭제하지 말고 그대로 두십시오.** 두 경로가 병존하면 한쪽이 죽어도 다른 쪽이 살아남습니다. 이번 사태의 교훈이 정확히 그것입니다.

---

## 4. 이 발견이 바꾸는 것

**서버 이전의 필요성이 크게 낮아집니다.** 파이프라인이 자동으로 완료되면 수동 실행이 사라지고, 그것만으로 Actions 소모가 대폭 줄어듭니다. 정부 지원 서버는 이제 대체재가 아니라 감시 장치 이중화나 백오피스 용도로 검토하면 됩니다.

**배포 워크플로 경량화의 우선순위도 재검토됩니다.** 215회 수동 실행의 상당수가 파이프라인이 자동으로 돌지 않아 확인차 돌린 것이라면, 근본 수정만으로 상당 부분이 줄어듭니다. 경량 CI와 함께 효과를 관찰한 뒤 판단합니다.
