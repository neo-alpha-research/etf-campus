# Antigravity 지시: 체이닝 방식 결정과 Worker 감시 장치 구축

작성일: 2026-08-25
발신: EVS Navigator
용도: 아래 구분선 안의 전문을 Antigravity에 그대로 전달하십시오.

---

## 1. 동시성 그룹 분리를 확인했습니다

세 워크플로가 각각 `daily-market`, `daily-distribution`, `daily-fees` 고유 그룹으로 분리되었고 `cancel-in-progress: false`와 기존 주석도 유지되었습니다. 무음 취소 문제는 해결되었습니다.

---

## 2. `repository_dispatch` 제안은 그대로 쓰면 동작하지 않습니다

방식 B를 권장하셨는데 **작성하신 형태로는 후속 워크플로가 트리거되지 않습니다.**

GitHub에는 재귀 실행을 막기 위한 규칙이 있습니다. **기본 `GITHUB_TOKEN`으로 발생시킨 이벤트는 새 워크플로 실행을 트리거하지 않습니다.** `gh api -X POST /repos/.../dispatches` 호출 자체는 성공 응답을 반환하지만 대상 워크플로는 깨어나지 않습니다.

이 규칙을 우회하려면 별도의 PAT나 GitHub App 토큰이 필요하며, 제안에는 그 내용이 없습니다.

**하필 "호출은 성공하는데 아무 일도 일어나지 않는" 유형의 실패입니다.** 우리가 이 프로젝트에서 계속 제거하려는 실패 방식입니다. 구현했다면 후속 워크플로가 영영 돌지 않으면서도 로그상으로는 정상이었을 것입니다.

같은 규칙이 `git push`에도 적용됩니다. 참고로 데이터 봇이 푸시하는 커밋은 `push` 트리거 워크플로를 발동시키지 않습니다. Cloudflare Pages는 GitHub Actions 이벤트가 아니라 저장소를 직접 감시하므로 영향받지 않습니다.

---

## 3. 결정: 체이닝을 도입하지 않습니다

방식 A(`workflow_run`)는 토큰 문제가 없어 동작하지만, 지적하신 대로 조기 종료 실행에서도 발동해 불필요한 실행이 늘어납니다.

**더 단순한 해법이 있습니다. 후속 워크플로의 실행 횟수를 하루 한 번으로 줄이고 시각을 뒤로 옮기는 것입니다.**

`daily-distribution`과 `daily-fees`는 분배금 공시와 총보수를 다루므로 몇 시간 지연이 문제되지 않습니다. 시장 데이터 수집 창이 완전히 닫힌 뒤 한 번만 돌면 충분합니다.

크론을 다음으로 변경하십시오.

```yaml
# daily-distribution.yml  UTC 04:07 = KST 13:07
- cron: "07 4 * * 2-6"

# daily-fees.yml  UTC 04:22 = KST 13:22
- cron: "22 4 * * 2-6"
```

`daily-market`의 마지막 단계가 KST 12:07에 시작해 최대 30분(타임아웃 값)까지 돌더라도 12:37에 끝나므로, 13:07은 안전한 간격입니다.

이 방식의 이점은 세 가지입니다. 후속 워크플로 실행이 하루 10회에서 2회로 줄어듭니다. 새 토큰이나 새 트리거 메커니즘이 필요 없습니다. 그리고 체이닝 특유의 실패 모드(트리거가 조용히 안 걸리는 경우)가 애초에 존재하지 않습니다.

`daily-market`의 5단계 크론(KST 08:07~12:07)은 그대로 유지합니다.

### 3-1. 모니터 시각도 함께 조정하십시오

`monitor-market-daily-pipeline.yml`이 현재 KST 13:15인데, 위 변경 후에는 후속 워크플로(13:07, 13:22)와 겹칩니다.

**KST 14:15(UTC 05:15)로 옮기십시오.** 세 워크플로가 모두 끝난 뒤 판정해야 합니다.

## 4. Worker 감시 장치를 구축하십시오

3번 조사 결과를 채택합니다. Fine-grained PAT에 `Issues: Read and Write` 권한만 부여하고 단일 저장소로 제한하는 설계, HTML 주석 마커로 중복을 방지하는 방식 모두 타당합니다.

아래 세 가지만 조정해 구현하십시오.

### 4-1. 중복 방지는 라벨로 하십시오

본문을 파싱해 마커를 찾는 대신 고정 라벨을 쓰는 편이 단순하고 안전합니다.

`market-daily-monitor` 라벨을 만들고, 조회 시 `GET /repos/{owner}/{repo}/issues?state=open&labels=market-daily-monitor`로 필터링한 뒤 제목의 날짜를 비교하십시오. 본문 파싱보다 실패 지점이 적습니다.

### 4-2. 판정 로직은 기존 워크플로에서 그대로 가져오십시오

`monitor-market-daily-pipeline.yml`의 조회 대상, 실패 조건, Issue 제목 형식을 변경하지 마십시오. 두 경로가 같은 기준으로 판정해야 결과를 비교할 수 있습니다.

**재작성하지 말고 로직을 옮기십시오.** 이전 라운드에서 옮겨 적는 과정에 오류가 두 번 났으므로, 옮긴 뒤 원본과 판정 조건을 항목별로 대조한 표를 보고에 포함하십시오.

### 4-3. 토큰 만료를 문서화하십시오

Fine-grained PAT는 만료됩니다. 만료되면 Worker가 401을 받고 알림이 조용히 멈춥니다. **감시 장치가 스스로 죽는 것을 아무도 모르게 되는 상황**이며, 이 작업의 목적과 정면으로 어긋납니다.

완화책은 두 가지입니다. 첫째, 만료 기간을 허용 최대치로 설정하고 **만료 예정일을 저장소 문서에 명시**하십시오. 둘째, GitHub Actions 모니터를 삭제하지 말고 그대로 두십시오. 두 경로의 실패 원인이 서로 다르므로 한쪽이 죽어도 다른 쪽이 남습니다.

Worker가 GitHub API에서 401 또는 403을 받으면 로그에 명확히 남기고, 가능하면 Worker의 다른 알림 경로로 그 사실 자체를 알리도록 하십시오.

### 4-4. 배치 위치와 스케줄

기존 Worker 중 하나에 붙일지 새 Worker를 만들지는 판단해 보고하십시오. `market-event-dispatcher`가 이미 cron으로 도므로 거기 붙이는 방법과, 감시 장치를 독립시켜 대상과 분리하는 방법 사이의 절충입니다.

**독립 Worker를 권장합니다.** 감시 대상과 감시자가 같은 배포 단위에 있으면 배포 실수로 둘 다 멈춥니다. 다만 운영 부담이 늘어나므로 최종 판단은 조사 결과를 보고 하겠습니다.

실행 시각은 KST 14:15로 Actions 모니터와 동일하게 두십시오. 같은 시점에 같은 판정을 하는 두 경로가 되어야 결과 불일치를 발견할 수 있습니다.

## 5. 작업 규칙

기존 파일을 통째로 다시 쓰지 말고 증분 편집만 하십시오.

이 저장소는 `node_modules`가 여러 곳에 있어 루트에서의 재귀 탐색이 사실상 멈춥니다. 탐색은 대상 디렉터리를 특정하거나 `node_modules`를 제외하고 수행하십시오.

완료 보고에 `git log --oneline -n 5`와 `git status --porcelain`을 함께 넣으십시오.

날짜와 시각을 추정하지 말고 실제로 조회해 확인하십시오.

확인한 사실과 추론을 구분하십시오. **특히 "가능하다", "권장한다"고 제안할 때는 그 방식이 실제로 동작하는지 제약 조건까지 확인한 뒤 제시하십시오.** 이번 `repository_dispatch` 건이 그 사례입니다.

첫째, 3번의 크론 변경(distribution KST 13:07, fees 13:22, monitor 14:15)을 적용하고 UTC 환산을 검증해 보고하십시오.

둘째, 4-4의 배치 위치를 조사해 보고하십시오. 독립 Worker와 기존 Worker 부착의 장단점, 그리고 필요한 설정 작업량입니다.

셋째, 위 두 가지 보고 후 Worker 코드 작성 착수를 지시하겠습니다. **PAT 발급은 운영자가 직접 수행할 사안이므로 필요한 권한과 설정 절차를 정리해 함께 제시하십시오.**

Actions 한도 복구 여부가 확인되면 알려 드리겠습니다. 복구 후 대기 중인 과제는 배포 워크플로 경량화, CI 실행 시간과 취소 동작 검증입니다. 서버 이전은 근본 원인이 스케줄 문제로 확인되었으므로 우선순위를 낮춥니다.
