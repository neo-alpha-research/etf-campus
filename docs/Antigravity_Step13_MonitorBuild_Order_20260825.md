## 2. 독립 Worker 신설을 승인합니다

`market-daily-monitor`라는 이름의 독립 Worker로 진행하십시오. 감시 대상과 감시자를 배포 단위까지 분리한다는 판단이 옳습니다.

---

## 3. 다만 배포 방식은 바꾸십시오

**`market-briefing-production.yml`에 배포 job을 추가하지 마십시오.** 계획에서 제외하십시오.

이유는 두 가지입니다.

첫째, 그 워크플로는 이번 달 Actions 분의 73퍼센트(1,545분)를 소모한 대상이며 우리가 경량화하려는 워크플로입니다. 여섯 번째 job을 추가하는 것은 방향이 반대입니다.

둘째, 더 중요한 이유입니다. **감시 장치의 배포가 Actions에 묶이면 Actions가 죽었을 때 감시 장치를 수정하거나 재배포할 수 없습니다.** 이번에 제거한 결합을 배포 계층에서 되살리는 것입니다.

**배포는 수동으로 하십시오.** 약 60줄짜리 Worker이고 판정 로직이 바뀔 때만 손대므로 `npx wrangler deploy`를 직접 실행하는 것으로 충분합니다. 배포 절차를 Worker 폴더의 README에 기록해 두십시오.

---

## 4. 구현 사양

### 4-1. 환경변수 이름

`GITHUB_TOKEN`이 아니라 **`MONITOR_GITHUB_TOKEN`**을 사용하십시오.

`GITHUB_TOKEN`은 GitHub Actions에서 자동 주입되는 예약된 이름입니다. Worker에서 같은 이름을 쓰면 나중에 어느 토큰인지 혼동할 여지가 생깁니다.

### 4-2. 판정 로직

`monitor-market-daily-pipeline.yml`의 조회 대상, 실패 조건, Issue 제목 형식을 **변경 없이 옮기십시오.**

두 경로가 동일한 기준으로 판정해야 결과 불일치를 발견할 수 있습니다. 한쪽만 실패하면 그 자체가 신호가 됩니다.

**옮긴 뒤 원본과 항목별로 대조한 표를 보고에 포함하십시오.** 조회 URL, 기대 기준일 계산 방식, 각 실패 조건, Issue 제목 형식을 각각 원본과 신규 코드에서 인용해 나란히 제시하십시오. 이전에 옮겨 적는 과정에서 두 번 오류가 났으므로 이 대조는 생략할 수 없습니다.

### 4-3. 중복 방지

`market-daily-monitor` 라벨을 사용하십시오. 라벨이 없으면 Worker가 생성하거나, 운영자가 사전에 만들어야 하는지 확인해 절차에 포함하십시오.

조회는 `GET /repos/{owner}/{repo}/issues?state=open&labels=market-daily-monitor`로 하고, 열린 Issue의 제목에서 날짜를 비교해 같은 날짜가 있으면 새로 만들지 마십시오.

### 4-4. 토큰 실패 처리

GitHub API가 401 또는 403을 반환하면 Worker 로그에 명확히 기록하십시오. 무엇이 실패했는지, 어떤 상태 코드인지가 로그만 봐도 드러나야 합니다.

**어떤 경우에도 예외를 삼키지 마십시오.** `try/catch`로 감싸고 조용히 넘어가는 코드를 넣지 마십시오. 이 프로젝트에서 반복적으로 문제가 된 패턴입니다.

### 4-5. 실행 스케줄

`wrangler.toml`의 cron을 UTC 05:15(KST 14:15)로 설정하고, 화~토에만 실행되도록 하십시오.

Cloudflare Worker cron은 UTC 기준입니다. 요일 지정이 GitHub Actions와 같은 문법인지 확인하고, 환산 결과를 보고에 포함하십시오.

## 5. 운영자 수행 사항

정리해 주신 PAT 발급 절차는 적절합니다. 아래 두 가지만 반영해 최종본으로 다시 제시하십시오.

환경변수 이름을 `MONITOR_GITHUB_TOKEN`으로 수정하십시오.

**만료 예정일을 기록할 위치를 특정하십시오.** "리드미나 위키"가 아니라 구체적인 파일 경로여야 합니다. 새로 만들 Worker 폴더의 README를 권합니다. 만료일이 지나면 감시 장치가 조용히 멈추므로, 기록 위치가 모호하면 아무도 찾지 못합니다.

## 6. 완료 판정

Worker 코드가 작성되고 `wrangler deploy`로 배포 가능한 상태여야 합니다.

4-2의 원본 대조표가 제출되어야 합니다.

로컬에서 `wrangler dev`로 실행해 정상 경로와 실패 경로를 각각 확인하고 로그를 첨부하십시오. 실제 GitHub Issue 생성 테스트는 토큰 발급 이후이므로, 토큰이 없는 상태에서는 401 처리 경로가 의도대로 동작하는 것까지 확인하십시오.

Worker 폴더 README에 배포 절차, 필요한 시크릿, 토큰 만료 예정일 기록란이 포함되어야 합니다.

## 7. 작업 규칙

기존 파일을 통째로 다시 쓰지 말고 증분 편집만 하십시오. 신규 Worker는 새 파일이므로 해당하지 않으나, `monitor-market-daily-pipeline.yml`은 **삭제하거나 수정하지 마십시오.** 두 경로를 병존시킵니다.

이 저장소는 `node_modules`가 여러 곳에 있어 루트에서의 재귀 탐색이 사실상 멈춥니다. 탐색은 대상 디렉터리를 특정하거나 `node_modules`를 제외하고 수행하십시오.

완료 보고에 `git log --oneline -n 5`와 `git status --porcelain`을 함께 넣으십시오.

날짜와 시각을 추정하지 말고 실제로 조회해 확인하십시오.

확인한 사실과 추론을 구분하십시오. 제안할 때는 그 방식의 제약 조건까지 확인한 뒤 제시하십시오.

Worker 코드 작성과 6번의 완료 판정 항목을 수행해 보고하십시오.
