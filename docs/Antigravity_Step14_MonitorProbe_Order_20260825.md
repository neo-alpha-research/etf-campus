## 0. 이번 작업의 배경

운영자가 스케줄에 대해 두 가지를 지적했고, 검토 결과 두 지적 모두 타당하며 그 근거가 예상보다 강했습니다.

**첫째, 우리는 원본 데이터가 언제 공개되는지 모릅니다.** 확보한 네 개 시각(08:08, 09:25, 10:08, 10:52)은 데이터가 도착한 시각이 아니라 운영자가 수동 실행해서 성공한 시각입니다. 상한선일 뿐 실제 공개 시각이 아닙니다. 훨씬 이른 시각에 이미 준비되어 있었을 수 있습니다.

**둘째, 이른 시각의 실행이 싸게 끝나지 않습니다.** `scripts/check_data_freshness.py`는 이미 수집이 완료된 `data/etf_master_draft.csv`의 `bas_dt`를 최신 거래일과 비교합니다. 즉 원본에 데이터가 없어도 1,147종목 수집을 전부 수행한 뒤에야 실패를 인지합니다. 조건에 따라 1.5초 스로틀이 걸린 참조가격 갱신까지 돌 수 있습니다. 헛도는 단계 하나가 몇 초가 아니라 몇 분입니다.

따라서 이번 작업은 세 가지를 함께 처리합니다. 수집 전 사전 확인 도입, 실제 공개 시각 측정, 그리고 앞서 지시한 감시 장치 구축입니다.

## 1. 작업 A: 사전 확인 스크립트 (최우선)

### 1-1. 목적

수집을 시작하기 전에 원본에 전일 데이터가 존재하는지 가벼운 호출 한 번으로 확인하고, 없으면 즉시 종료합니다. 헛도는 단계의 비용을 몇 분에서 몇 초로 줄입니다.

### 1-2. 구현

`scripts/check_source_ready.py`를 신설하십시오.

**호출 대상은 `scripts/update_daily_data.py`가 실제로 사용하는 엔드포인트와 파라미터에서 도출하십시오.** 새로 만들거나 추측하지 마십시오. 어느 API를 어떤 파라미터로 호출하는지 먼저 코드에서 확인하고, 그 결과를 보고에 포함하십시오.

동작은 다음과 같습니다. 대상 거래일을 판정하고, 해당 기준일로 최소 건수(예: `numOfRows=1`)만 요청해 결과가 존재하는지 확인합니다. 존재하면 종료 코드 0, 없으면 2를 반환합니다. 오류가 발생하면 1을 반환해 "데이터 없음"과 "호출 실패"를 구분하십시오.

**거래일 판정 로직을 새로 구현하지 마십시오.** `check_data_freshness.py`가 `data/market_holidays.txt`를 읽어 거래일을 판정하는 로직을 이미 갖고 있습니다. 그 함수를 재사용하거나 공용 모듈로 분리해 양쪽이 같은 코드를 쓰게 하십시오. 두 곳에서 거래일을 다르게 판정하면 진단이 불가능해집니다.

### 1-3. 워크플로 적용

`daily-market.yml`의 기존 `guard` 스텝 직후, **의존성 설치와 수집 스텝보다 앞에** 사전 확인 스텝을 추가하십시오.

사전 확인이 "데이터 없음"을 반환하면 이후 모든 스텝을 건너뛰고 실행을 종료합니다. 이때 워크플로를 실패로 표시할지 성공으로 표시할지는 아래 기준을 따르십시오.

마지막 단계(KST 12:07)가 아니면 성공으로 종료합니다. 아직 공개되지 않은 것은 정상 상황입니다.

마지막 단계에서도 데이터가 없으면 실패로 표시합니다. 그날 수집이 끝내 이루어지지 않았다는 뜻이므로 드러나야 합니다.

`workflow_dispatch`로 `TARGET_DATE`를 지정한 수동 실행에서는 사전 확인을 건너뛰십시오. 특정 날짜를 강제로 다시 수집하려는 의도이기 때문입니다.

### 1-4. 완료 판정

사전 확인 스크립트를 단독 실행해 데이터가 있는 날짜와 없는 날짜에 대해 각각 올바른 종료 코드를 반환하는지 확인하고 로그를 첨부하십시오.

거래일 판정 로직이 `check_data_freshness.py`와 공유되고 있음을 코드로 보이십시오.

## 2. 작업 B: 공개 시각 측정 프로브

### 2-1. 목적

원본 데이터가 실제로 언제 공개되는지를 측정합니다. 이 데이터로 최종 스케줄을 확정합니다.

### 2-2. 배치

**작업 C의 감시 Worker와 같은 Worker에 넣으십시오.** 두 기능 모두 관측 목적이고 데이터 경로에 있지 않으며, 1인 운영 환경에서 배포 단위를 늘리지 않는 편이 낫습니다. Cloudflare cron 핸들러에서 `event.cron` 값으로 분기하면 됩니다.

다만 프로브는 원본 API 키가 필요합니다. 감시 기능은 GitHub 토큰만 필요합니다. 두 시크릿이 한 Worker에 모이는 점을 인지하고, 각각 최소 권한으로 발급하십시오.

### 2-3. 동작

KST 05:00부터 13:00까지 15분 간격으로 실행합니다. UTC 환산과 요일 지정을 직접 계산해 보고에 포함하십시오.

각 실행에서 다음을 수행합니다. KV에서 오늘 날짜의 기록을 조회하고, 이미 기록이 있으면 즉시 종료합니다. 없으면 작업 A와 동일한 방식으로 원본에 전일 데이터가 있는지 확인합니다. 있으면 현재 시각을 KV에 기록합니다. 없으면 아무것도 하지 않고 종료합니다.

**첫 프로브 시각에 이미 데이터가 있었는지를 반드시 구분해 기록하십시오.** 05:00 첫 시도에서 바로 발견되었다면 실제 공개 시각은 05:00 이전이라는 뜻이고, 관측 시작 시각을 더 당겨야 합니다. 기록에 "첫 시도에서 발견"인지 여부를 함께 남기십시오.

### 2-4. 저장

기존 KV 네임스페이스를 접두사를 구분해 재사용할지, 새 네임스페이스를 만들지 판단해 보고하십시오. 키 형식은 `source-availability:YYYY-MM-DD` 같은 형태를 권합니다.

### 2-5. 운영 기간

이 프로브는 상시 기능이 아닙니다. **2주간 측정한 뒤 결과를 보고하고 프로브를 중단하거나 빈도를 낮춥니다.** 이 사실을 Worker README에 명시해 나중에 잊고 방치되지 않게 하십시오.

## 3. 작업 C: 감시 Worker

앞서 지시한 내용을 그대로 수행하십시오. 요약하면 다음과 같습니다.

`market-daily-monitor`라는 독립 Worker를 신설합니다. **배포는 수동(`npx wrangler deploy`)으로 하며 `market-briefing-production.yml`에 배포 job을 추가하지 마십시오.**

환경변수 이름은 `MONITOR_GITHUB_TOKEN`을 사용하십시오.

판정 로직은 `monitor-market-daily-pipeline.yml`에서 변경 없이 옮기고, **원본과 항목별로 대조한 표를 보고에 포함하십시오.** 조회 URL, 기대 기준일 계산 방식, 각 실패 조건, Issue 제목 형식을 원본과 신규 코드에서 나란히 인용하십시오.

중복 방지는 `market-daily-monitor` 라벨로 합니다. 라벨 생성 주체(Worker 자동 생성 또는 운영자 사전 생성)를 확인해 절차에 포함하십시오.

GitHub API가 401 또는 403을 반환하면 로그에 명확히 기록하십시오. **어떤 경우에도 예외를 삼키지 마십시오.**

실행 시각은 KST 14:15입니다.

`monitor-market-daily-pipeline.yml`은 삭제하거나 수정하지 마십시오. 두 경로를 병존시킵니다.

## 4. 스케줄은 지금 바꾸지 마십시오

`daily-market.yml`의 현행 5단계(KST 08:07~12:07)를 유지하십시오.

측정이 끝나기 전에 스케줄을 바꾸면 근거 없이 한 번 바꾸고 또 바꾸게 됩니다. 작업 A의 사전 확인이 적용되면 헛도는 단계의 비용이 이미 크게 줄어들므로 급하지 않습니다.

2주 측정 결과가 나오면 단계 수와 시작 시각을 한 번에 확정합니다.

## 5. 운영자 수행 사항

아래를 정리해 최종본으로 제시하십시오.

Fine-grained PAT 발급 절차(`Issues: Read and write`, 단일 저장소 지정, 최대 만료 기간). 환경변수 이름은 `MONITOR_GITHUB_TOKEN`입니다.

원본 API 키를 Worker 시크릿으로 등록하는 절차.

**만료 예정일을 기록할 파일 경로를 특정하십시오.** 새 Worker 폴더의 README를 권합니다.

## 6. 완료 판정

작업 A의 사전 확인 스크립트가 단독 실행으로 검증되고 워크플로에 적용되어야 합니다.

작업 B와 C의 Worker 코드가 작성되고 `wrangler deploy` 가능한 상태여야 합니다. `wrangler dev`로 로컬 실행해 정상 경로와 실패 경로 로그를 첨부하십시오. 토큰이 없는 상태에서 401 처리 경로가 의도대로 동작하는 것까지 확인하십시오.

작업 C의 원본 대조표가 제출되어야 합니다.

Worker README에 배포 절차, 필요한 시크릿, 토큰 만료 예정일 기록란, 프로브 중단 예정 시점이 포함되어야 합니다.

UTC와 KST 환산 계산 결과가 보고에 포함되어야 합니다.

## 7. 작업 규칙

기존 파일을 통째로 다시 쓰지 말고 증분 편집만 하십시오.

**다른 파일의 내용을 옮길 때는 눈으로 읽고 다시 타이핑하지 말고 원문을 그대로 복사하십시오.** 옮긴 뒤 호출하는 파일과 값이 실제로 존재하는지 기계적으로 검증한 결과를 보고에 포함하십시오. 이 항목에서 이미 두 번 사고가 났습니다.

이 저장소는 `node_modules`가 여러 곳에 있어 루트에서의 재귀 탐색이 사실상 멈춥니다. 탐색은 대상 디렉터리를 특정하거나 `node_modules`를 제외하고 수행하십시오.

완료 보고에 `git log --oneline -n 5`와 `git status --porcelain`을 함께 넣으십시오.

날짜와 시각을 추정하지 말고 실제로 조회해 확인하십시오.

확인한 사실과 추론을 구분하십시오. 제안할 때는 그 방식의 제약 조건까지 확인한 뒤 제시하십시오.

Actions 한도 복구가 확인되면 알려 드리겠습니다. 복구 후 대기 중인 과제는 배포 워크플로 경량화와 CI 실행 시간·취소 동작 검증입니다.
