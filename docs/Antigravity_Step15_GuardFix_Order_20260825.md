### 1-1. 발신 측 오류를 정정합니다

앞선 지시에서 "조기 종료 가드가 이미 구현되어 있으므로 단계를 늘리는 비용이 낮습니다"라고 판단했는데 **틀렸습니다.**

`steps.guard.outputs.already_run`을 참조하는 `if:` 조건들은 있었으나 `id: guard` 스텝 정의가 없었습니다. 존재하지 않는 스텝의 출력은 빈 문자열이므로 `!= 'true'`가 항상 참이 되어 모든 스텝이 매번 실행되었습니다.

**가드는 장식이었고, 헛도는 단계의 비용은 낮지 않았습니다.** 이를 찾아 실제 가드를 구현한 것은 정확한 작업입니다.

## 2. 수정이 필요한 네 가지

### 2-1. 마지막 단계 판정이 크론에 암묵적으로 묶여 있습니다

가드 스텝 73행이 다음과 같습니다.

```bash
if [ "$UTC_HOUR" = "03" ]; then
```

UTC 03시는 현재 스케줄의 마지막 단계(KST 12:07)에 해당하므로 지금은 맞습니다. **문제는 2주 뒤 측정 결과로 스케줄을 바꾸기로 이미 정해져 있다는 것입니다.**

크론을 바꾸면 이 값은 어느 단계와도 일치하지 않게 되고, 그러면 **데이터가 끝내 오지 않은 날에도 실패로 보고되지 않습니다.** 조용히 넘어가는 실패가 다시 생깁니다.

수정 방향은 두 가지 중 하나입니다.

`github.event.schedule`에 트리거된 크론 문자열이 담기므로, 마지막 크론 표현식과 직접 비교하는 방법이 있습니다. 이 방식이 가능한지 먼저 확인하고, 가능하면 이쪽을 택하십시오.

불가능하면 시각 비교를 유지하되, **크론 정의 바로 옆에 이 값을 함께 두고 둘이 연동되어야 함을 주석으로 명시하십시오.** 두 곳이 떨어져 있으면 한쪽만 바뀝니다.

어느 쪽이든 워크플로 상단 크론 블록에 "이 값을 바꾸면 가드 스텝의 최종 단계 판정도 함께 바꿀 것"이라는 주석을 넣으십시오.

### 2-2. `already_run`이 서로 다른 두 상태를 뭉뚱그립니다

현재 가드는 두 경우 모두 `already_run=true`를 출력합니다.

오늘 이미 성공한 경우와, 원본에 아직 데이터가 없는 경우입니다. **의미가 전혀 다른데 같은 신호를 냅니다.** 나중에 로그만 보고 어느 쪽이었는지 구분할 수 없습니다.

출력을 분리하십시오. `skip=true`와 함께 `skip_reason=already_succeeded` 또는 `skip_reason=source_not_ready`를 내보내고, 후속 스텝의 `if:` 조건은 `skip`을 참조하게 하십시오. 실행 요약(`GITHUB_STEP_SUMMARY`)에도 사유를 남기십시오.

### 2-3. 감시 Worker의 동작 변경을 명시적으로 선언하십시오

대조표의 "실패 처리" 항목이 원본은 "에러 무시/단순 이슈 생성", 신규는 `if (!listResp.ok) throw new Error(...)`로 되어 있습니다.

**이것은 일치가 아니라 변경입니다.** 대조표는 원본과 신규가 같음을 보이는 자료인데, 다른 항목이 같은 표에 아무 표시 없이 들어가 있습니다.

변경 자체는 옳습니다. 예외를 삼키지 않는 것이 이 프로젝트의 원칙입니다. 다만 **지시는 "변경 없이 옮기십시오"였으므로, 의도적으로 다르게 만들었다면 표에 "의도적 변경"으로 표시하고 사유를 적어야 합니다.**

대조표를 수정해 일치 항목과 변경 항목을 구분해 다시 제출하십시오. 변경 항목이 더 있는지도 함께 점검하십시오.

### 2-4. 휴장일 파일이 두 벌로 갈라졌습니다

`workers/market-daily-monitor/src/market_holidays.txt`가 `data/market_holidays.txt`의 복사본입니다.

**두 파일은 시간이 지나면 반드시 어긋납니다.** 운영자가 새 휴장일을 `data/`에 추가해도 Worker는 옛 목록을 그대로 씁니다. 그러면 감시 장치가 휴장일에 오탐하거나, 반대로 실제 누락을 휴장일로 오인해 넘어갑니다.

**감시 장치의 존재 이유가 누락 탐지인데 그 판정 기준이 낡는 것은 치명적입니다.**

세 가지 방안을 검토해 하나를 제안하십시오.

배포 시 `data/market_holidays.txt`를 Worker 소스로 복사하는 단계를 배포 절차와 `package.json` 스크립트에 넣는 방법이 있습니다.

Worker가 실행 시점에 공개 URL에서 휴장일 목록을 읽어오는 방법이 있습니다. 저장소가 private이므로 사이트 경유가 가능한지 확인이 필요합니다.

두 파일의 해시를 비교해 다르면 경고를 남기는 방법이 있습니다. 근본 해결은 아니지만 방치를 막습니다.

**어느 방안이든 Worker README에 "이 파일은 `data/market_holidays.txt`의 복사본이며 원본이 바뀌면 함께 갱신해야 한다"는 경고를 반드시 넣으십시오.**
