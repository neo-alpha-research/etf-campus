## 1. 배경

저장소를 일시적으로 public으로 전환하는 방안을 검토했으나 채택하지 않았습니다. 커밋 작성자 분포를 조회한 결과가 결정적이었습니다.

```
752건  Neo <kibaek.shin@gmail.com>
 37건  neo-alpha-research <...@users.noreply.github.com>
 29건  neo-alpha-research <neo.alpharesearch@gmail.com>
 27건  etf-campus-data-bot <...@users.noreply.github.com>
  7건  github-actions[bot]
```

**전체 커밋의 대다수가 운영자 실명 이메일로 작성되어 있습니다.** Neo는 자본시장법 §101 회피 전략과 맞물려 의도적으로 익명을 유지하는 페르소나이므로, 공개 시 그 연결고리가 영구히 드러납니다.

저장소가 private으로 유지되는 한 기존 이력의 실제 위험은 낮습니다. 다만 **앞으로의 커밋에 실명이 더 쌓이지 않도록 지금 차단합니다.**

---

## 2. 운영자가 직접 수행할 사항

아래 두 가지는 GitHub 개인 계정 설정이므로 운영자 몫입니다. 절차만 정리해 제시하고 대기하십시오.

**첫째, 이메일 비공개 설정.** GitHub Settings에서 Emails 항목으로 이동해 `Keep my email addresses private`를 활성화합니다. 이때 화면에 표시되는 `{숫자}+{사용자명}@users.noreply.github.com` 형식의 주소를 확인해 두어야 합니다. 아래 3번에서 사용합니다.

**둘째, 실명 노출 푸시 차단.** 같은 화면의 `Block command line pushes that expose my email`을 활성화합니다. 이 설정을 켜면 실명 이메일로 만든 커밋을 푸시할 때 GitHub이 거부합니다. **로컬 설정을 되돌리는 실수를 서버가 막아 주므로 이 항목이 실질적 방어선입니다.**

---

## 3. 당신이 수행할 사항

### 3-1. 로컬 git 작성자 정보 변경

운영자가 2번의 noreply 주소를 알려주면, 저장소 로컬 설정을 변경하십시오.

```
git config user.email "{운영자가 확인한 noreply 주소}"
git config user.name "neo-alpha-research"
```

**전역(`--global`) 설정이 아니라 저장소 로컬 설정으로 하십시오.** 다른 프로젝트에 영향을 주지 않아야 합니다.

작성자 이름도 `Neo`가 아니라 GitHub 사용자명과 일치시키는 편이 좋습니다. 현재 세 가지 identity가 섞여 있는데, 앞으로는 하나로 통일하십시오.

**주소를 추측하지 마십시오.** 기존 이력에 `3.09254007e+08+neo-alpha-research@users.noreply.github.com`라는 값이 있는데, 숫자가 지수 표기로 깨진 형태입니다. 어느 시점엔가 도구가 값을 변형한 흔적이므로 그대로 재사용하면 안 됩니다. 운영자가 GitHub 화면에서 확인한 값을 그대로 쓰십시오.

### 3-2. 변경 검증

설정 후 빈 커밋을 하나 만들어 작성자가 의도대로 기록되는지 확인하십시오.

```
git commit --allow-empty -m "chore: verify commit identity"
git log -1 --format='%an <%ae> | committer: %cn <%ce>'
```

**author와 committer 양쪽 모두** noreply 주소인지 확인하십시오. 한쪽만 바뀌는 경우가 있습니다.

확인 후 이 빈 커밋은 남겨두어도 되고 되돌려도 됩니다. 판단해 처리하고 보고하십시오.

### 3-3. 시크릿 스캔 (미수행 과제)

이전에 지시했으나 아직 수행되지 않은 항목입니다. 지금 처리하십시오.

gitleaks 또는 trufflehog로 **전체 커밋 이력**을 스캔하십시오. 현재 워킹 트리만이 아니라 과거 이력 전체가 대상입니다.

**보고 시 실제 시크릿 값을 붙여넣지 마십시오.** 탐지된 항목의 파일 경로, 커밋 해시, 시크릿 유형, 탐지 규칙명만 보고하십시오.

며칠 전 `gho_` 접두사 토큰이 명령줄에 평문으로 노출된 사례가 있었습니다. 그 값이 커밋에 포함되지 않았는지도 확인 대상에 넣으십시오.

탐지 항목이 있으면 **그 자체를 별도 과제로 보고하고 임의로 이력을 재작성하지 마십시오.** 이력 재작성은 위험 요소가 많아 별도 계획이 필요합니다.

---

## 4. 이력 재작성은 보류합니다

기존 752건의 실명 커밋을 정리하려면 `git filter-repo` 등으로 이력을 재작성해야 하나, 지금은 하지 않습니다. 이유는 다음과 같습니다.

**커밋 해시가 전부 바뀝니다.** 이 프로젝트는 `market_source_snapshot_manifest` 테이블에 `git_commit_sha`를 기록하고 `publish_market_source_snapshot.py`가 매일 그 값을 씁니다. 재작성하면 D1에 쌓인 SHA가 전부 고아가 되어 어느 커밋에서 발행된 데이터인지 추적할 수 없게 됩니다.

**강제 푸시가 필요하고 다른 클론이 어긋납니다.** 잘못 병합하면 지운 이력이 되살아납니다.

**완전히 제거되지도 않습니다.** GitHub은 강제 푸시 후에도 옛 객체를 일정 기간 보관합니다.

**저장소가 private으로 유지되는 한 실제 위험이 낮습니다.**

재작성은 실제로 공개 전환이 필요해지는 시점에 별도 계획으로 다룹니다. 그때는 D1의 `git_commit_sha` 처리 방안과 백업 절차를 함께 설계해야 합니다.
