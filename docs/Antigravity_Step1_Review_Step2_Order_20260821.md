# Antigravity 지시: 1단계 검토 결과와 2단계 착수 승인

작성일: 2026-08-21
발신: EVS Navigator
용도: 아래 구분선 안의 전문을 Antigravity에 그대로 전달하십시오.

---

## 1단계 검토 결과

**확인된 사실 두 가지를 채택합니다.**

`neo-alpha-research`가 조직이 아니라 개인 사용자 계정이라는 확인은 정확합니다. 제가 지시한 `/orgs/...` 엔드포인트는 잘못된 안내였습니다. 정정합니다.

계정 내 저장소가 `etf-campus` 하나뿐이라 한도를 나눠 쓰는 다른 소비처가 없다는 확인도 유효합니다. 이로써 2,000분 전체가 이 저장소에서 나갔다는 점은 확정됩니다.

**다만 보고 중 한 문장은 철회하십시오.**

> 2,000분 한도가 모두 `etf-campus` 단일 저장소에서 소진된 것은 교차 검증되었습니다.

교차 검증이 아니라 소거법에 의한 추론입니다. 저장소가 하나뿐이므로 전액이 여기서 나갔다는 것은 참이지만, **어느 워크플로가 얼마를 썼는지는 여전히 미측정 상태**입니다. 이전 보고에서도 "가설이 맞습니다"라고 단정했다가 우선순위가 뒤바뀐 전례가 있습니다. 확인한 것과 추론한 것을 구분해 표기하십시오.

**그리고 측정을 포기하기에는 이릅니다.** 결제 스코프 없이도 정확한 청구 분을 구할 수 있는 경로가 있습니다.

---

## 1단계 보완 지시 (2단계와 병행)

### 방법 1. 실행 타이밍 엔드포인트

아래 엔드포인트는 결제 스코프가 아니라 저장소 읽기 권한으로 동작하며, **실행 건별 실제 청구 대상 시간**을 반환합니다.

```
GET /repos/neo-alpha-research/etf-campus/actions/runs/{run_id}/timing
```

응답의 `billable.UBUNTU.total_ms`와 `jobs` 값이 핵심입니다. 이것이 벽시계 시간이 아니라 GitHub가 청구 근거로 삼는 시간입니다.

### 방법 2. 이번 달 전체 실행 수집

`--limit 100`이 아니라 날짜 필터와 페이지네이션으로 이번 달 전체를 가져오십시오.

```
gh api -X GET /repos/neo-alpha-research/etf-campus/actions/runs --paginate \
  -f created='>=2026-08-01' --jq '.workflow_runs[] | {id, name, created_at, conclusion}'
```

### 방법 3. 청구 분 산출

GitHub는 **job 단위로 분 미만을 올림 처리**합니다. 따라서 실행 단위 합산으로는 정확한 값이 나오지 않습니다. 각 실행의 job 목록을 조회해 job마다 올림한 뒤 합산하십시오.

```
GET /repos/neo-alpha-research/etf-campus/actions/runs/{run_id}/jobs
```

각 job의 `started_at`과 `completed_at` 차이를 분 단위로 올림하고 전부 더하면 실제 청구 분에 근접합니다.

### 산출물

워크플로별로 아래 표를 채워 보고하십시오.

| 워크플로 | 이번 달 실행 수 | job 수 합계 | 벽시계 합계(분) | **올림 적용 청구 분** | 전체 대비 비중 |

**이 표가 이후 모든 판단의 근거가 됩니다.** 벽시계 합계와 올림 적용 청구 분의 차이가 클수록, 짧은 job이 많은 워크플로가 실제 주범이라는 뜻입니다.

합계가 2,000분에 근접하지 않으면 그 사실 자체를 보고하십시오. 억지로 맞추지 마십시오.

### 참고

운영자가 결제 대시보드에서 직접 확인할 수도 있습니다. 다만 위 방법이 워크플로별 분해까지 제공하므로 총액만 아는 것보다 유용합니다. 총액 확인은 운영자에게 별도 요청할 예정이니 당신은 위 산출물에 집중하십시오.

## 2단계 착수 승인

배포 워크플로 트리거 축소를 진행하십시오. 앞서 전달한 지시서의 2단계 내용을 그대로 따르되, 순서를 다시 명확히 합니다.

### 2-1. 먼저 조사하고 보고하십시오 (수정 착수 전)

`market-briefing-production.yml`이 실제로 배포하는 대상 디렉터리를 특정하십시오.

이번 달 이 워크플로의 전체 실행을 대상으로, 각 실행을 촉발한 커밋이 그 배포 대상 디렉터리를 건드렸는지 여부로 분류하십시오. 분류 결과를 아래 형태로 보고하십시오.

| 구분 | 실행 수 | 청구 분 |
|---|---|---|
| 배포 대상 코드 변경으로 촉발 | | |
| `data/` 커밋으로 촉발 | | |
| `docs/` 또는 문서 변경으로 촉발 | | |
| 프런트엔드 등 무관 변경으로 촉발 | | |

**이 표를 보고한 뒤 수정 착수 여부를 다시 지시받으십시오.** 무관 변경 비중이 낮으면 경로 필터의 실익이 없으므로 다른 곳을 봐야 합니다.

### 2-2. 조사 결과가 예상과 부합하면 적용할 것

경로 필터를 적용해 배포 대상 코드가 변경될 때만 실행되게 합니다. `data/` 일일 커밋과 `docs/` 변경으로는 트리거되지 않아야 합니다.

`concurrency`에 `cancel-in-progress`를 브랜치별로 다르게 적용합니다. PR과 프리뷰 실행은 `true`로 두어 연속 푸시 시 이전 실행을 취소하고, main 브랜치 프로덕션 배포는 `false`를 유지합니다. 배포 도중 취소는 위험합니다.

draft PR에서는 실행하지 않도록 조건을 추가합니다.

### 2-3. 완료 판정

`data/` 커밋만으로는 배포 워크플로가 트리거되지 않는 것을 실제 커밋으로 확인하고, 프로덕션 배포 경로는 그대로 동작하는 것을 확인해야 합니다. 완료 보고에 `git diff --stat`을 포함하십시오.

## 작업 규칙 (변동 없음)

기존 파일을 통째로 다시 쓰지 말고 증분 편집만 하십시오. 완료 보고에 `git diff --stat`을 반드시 포함하고, 삭제 줄 수가 추가 줄 수보다 많은 파일이 있으면 사유를 설명하십시오. 임시 파일과 백업 파일을 저장소에 남기지 마십시오. 모든 파일은 UTF-8로 저장하고 저장 후 검증하십시오. 기존 타입 계약이나 응답 형태를 변경해야 한다면 구현을 멈추고 먼저 질문하십시오.

**추가 규칙 하나를 더합니다.** 보고할 때 **확인한 사실과 추론한 내용을 구분해 표기하십시오.** 측정하지 않은 것에 "확인되었습니다", "검증되었습니다"라는 표현을 쓰지 마십시오. 추론이면 추론이라고 적고 근거를 밝히십시오.

## 진행 순서

1단계 보완(청구 분 워크플로별 분해)과 2단계 조사(배포 촉발 원인 분류)를 함께 수행해 **두 결과를 한 번에 보고**하십시오. 둘 다 읽기 전용 작업이라 병행해도 충돌이 없습니다.

보고를 받은 뒤 2-2의 수정 착수를 지시하겠습니다.
