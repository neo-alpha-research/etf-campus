# Antigravity 지시: 2단계 조사 재해석과 수정 착수

작성일: 2026-08-21
발신: EVS Navigator
용도: 아래 구분선 안의 전문을 Antigravity에 그대로 전달하십시오.

---

## 측정은 채택합니다

이번 실측은 정확합니다. 430건 전수 순회, job 단위 올림 적용, 합계 2,110분으로 한도 2,000분과 정합합니다. 이전 384분 추정과의 격차도 해소되었습니다. 이 수치를 이후 판단의 기준으로 확정합니다.

배포 워크플로가 1,545분으로 전체의 73.2퍼센트라는 결론도 채택합니다.

---

## 그러나 2단계 조사의 해석은 무효입니다

`market-briefing-production.yml`의 트리거는 다음이 전부입니다.

```yaml
on:
  workflow_dispatch:
```

**push 트리거도 pull_request 트리거도 없습니다. 215회 전부 수동 실행입니다.**

따라서 "어떤 파일이 변경되어 촉발되었는가"라는 분류 자체가 성립하지 않습니다. 커밋에 무엇이 들어 있었는지를 본 것이지 무엇이 실행을 유발했는지를 본 것이 아닙니다. "98퍼센트가 정당한 실행"이라는 결론도 근거가 없습니다.

그리고 경로 필터는 애초에 적용할 대상이 없습니다. **2-2 수정 지시를 철회합니다.**

이번 건은 지시받은 분류 틀을 먼저 데이터에 맞춰 검증하지 않고 그대로 적용한 결과입니다. 앞으로 분류나 집계를 수행하기 전에 그 틀이 대상에 유효한지부터 확인하십시오.

---

## 재해석: 진짜 문제

수동 실행 215회를 21일로 나누면 **하루 약 10회**입니다. 프로덕션 배포를 하루 열 번 할 이유는 없습니다.

job 통계가 이유를 말해 줍니다. 워크플로는 `validate`, `migrate_d1`, `deploy_dispatcher`, `deploy_publisher`, `deploy_pages` 다섯 job이 순차 의존으로 묶여 있는데, 실측된 job 수는 215회 실행에 487개, 실행당 2.27개입니다. **대부분의 실행이 앞쪽 job에서 실패해 뒤쪽 job까지 가지 못했다는 뜻입니다.**

즉 지금 벌어지는 일은 배포가 아니라 검증입니다. 코드를 고치고 프로덕션 배포 워크플로를 돌려 lint와 test를 통과하는지 확인하고, 실패하면 고쳐서 다시 돌리는 흐름입니다. **프로덕션 배포 파이프라인이 개발 피드백 루프로 쓰이고 있습니다.**

같은 패턴이 데이터 워크플로에도 보입니다. `Daily ETF data refresh`(92회)와 `Daily ETF market data refresh`(32회)는 이름만 바뀐 동일 워크플로로 보이며 합계 124회입니다. 정기 실행은 하루 2회 × 영업일 21일 = 약 42회이므로, 나머지 80여 회는 수동 실행입니다.

**결론. 비용 문제의 원인은 잘못된 트리거 설정이 아니라 무거운 프로덕션 워크플로를 반복 수동 실행하는 작업 방식입니다.** 이 구조를 그대로 두면 어떤 필터를 걸어도 절감되지 않습니다.

## 수정 지시

아래를 순서대로 진행하고 각 단계 완료 후 보고하십시오.

### 수정 1. 경량 CI 워크플로 신설 (최대 효과)

`ci.yml`을 신설합니다. 목적은 프로덕션 배포를 돌리지 않고도 코드 검증을 끝내는 것입니다.

트리거는 `push`와 `pull_request`로 두되, `paths-ignore`로 `data/**`, `docs/**`, `**.md`를 제외하십시오. 데이터 커밋으로 CI가 돌 필요는 없습니다.

**단일 job으로 구성하십시오.** 여러 job으로 나누면 job마다 올림 청구가 붙습니다. 한 job 안에서 checkout, setup-node(캐시 활성화), `npm ci`, `npm run lint`, `npm test`, `npm run build`, 두 Worker의 `typecheck`를 순차 실행합니다.

`concurrency` 그룹을 브랜치 단위로 설정하고 `cancel-in-progress: true`를 적용하십시오. 연속 푸시 시 이전 실행이 취소되어야 합니다. 프로덕션 배포가 아니므로 중간 취소가 안전합니다.

```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

이 워크플로가 생기면 **프로덕션 배포 워크플로를 검증 용도로 실행할 이유가 사라집니다.**

### 수정 2. 프로덕션 배포 워크플로 경량화

`market-briefing-production.yml`을 아래 세 가지로 정리하십시오. 트리거(`workflow_dispatch`)와 `concurrency`의 `cancel-in-progress: false`는 그대로 유지합니다. 배포 도중 취소는 위험하며 현재 주석의 판단이 옳습니다.

**첫째, 빌드 중복을 제거하십시오.** 현재 `validate` job과 `deploy_pages` job이 각각 `npm ci`와 `npm run build`를 수행합니다. 같은 빌드를 두 번 합니다. `validate`에서 빌드한 `out/` 디렉터리를 artifact로 업로드하고 `deploy_pages`에서 내려받아 그대로 배포하십시오.

**둘째, job 수를 줄이십시오.** 현재 다섯 job이 각각 checkout과 의존성 설치를 반복하고, job마다 최소 1분이 청구됩니다. `deploy_dispatcher`와 `deploy_publisher`는 각각 작은 Worker 하나를 배포할 뿐이므로 `migrate_d1`과 함께 하나의 job으로 합치십시오. 목표 구성은 `validate`, `deploy`, `deploy_pages` 세 job입니다.

합치면서 순서(마이그레이션 → dispatcher → publisher → pages)는 반드시 유지하십시오. 그리고 중간 단계 실패 시 어디서 멈췄는지 로그로 명확히 드러나야 합니다.

**셋째, wrangler를 devDependency로 고정하십시오.** 현재 네 곳에서 `npx --yes wrangler@4.124.0`을 호출하는데, 이는 매번 npm 레지스트리에서 내려받습니다. `package.json`에 버전을 고정해 설치하면 npm 캐시가 적용됩니다. 버전은 현재와 동일하게 유지하십시오.

### 수정 3. 취소된 실행 22건의 정체 확인

실측 표의 "기타(실행 전 취소 등) 22건, job 0개"는 실행되기 전에 취소된 run입니다. 어떤 워크플로였는지 워크플로별로 집계해 보고하십시오.

`daily-market.yml`, `daily-distribution.yml`, `daily-fees.yml`은 모두 `concurrency: group: daily-etf-data`를 `cancel-in-progress: false`로 공유하며 현재 셋 다 `cron: "37 21,22"`로 같은 분에 시작합니다. 한 그룹에 실행 중 run과 대기 중 run이 있는 상태에서 새 run이 도착하면 대기 중이던 run이 취소됩니다.

이 22건에 일일 데이터 워크플로가 포함되어 있다면 **매일 세 작업 중 하나가 조용히 취소되어 데이터가 누락되고 있다는 뜻**이며, 보고하신 "작업 소실" 현상의 직접 원인입니다.

포함이 확인되면 세 워크플로의 시작 시각을 최소 15분씩 벌리십시오. `daily-market`은 `:07`, `daily-distribution`은 `:22`, `daily-fees`는 `:37`입니다. 공유 concurrency 그룹은 git push 충돌 방지를 위해 유지합니다.

### 수정 4. 수동 실행 워크플로 점검

`Backfill D1 ETF Prices` 25회, `Backfill ETF Price History` 9회로 이번 달 34회 실행되었습니다. 둘 다 수동 복구용 워크플로인데 한 달에 34회는 비정상적으로 잦습니다.

이 실행들이 무엇을 복구하려 한 것인지, D1 잠금 문제(4단계 과제)와 연관이 있는지 조사해 보고하십시오. 원인이 잠금이라면 4단계 수정이 이 실행 자체를 없앨 수 있습니다.

## 예상 효과

수정 1이 적용되면 프로덕션 배포 실행이 실제 릴리스 시점으로 한정되어 월 20회 안팎으로 줄어들 것으로 봅니다. 1,545분 중 상당 부분이 경량 CI로 옮겨 가고, CI는 단일 job에 캐시가 적용되므로 실행당 비용이 훨씬 낮습니다.

수정 2의 빌드 중복 제거와 job 통합은 남은 배포 실행의 단가를 낮춥니다.

두 수정을 합치면 월 2,110분이 절반 이하로 떨어질 것으로 예상합니다. 다만 이는 예측이므로, 적용 후 2주 시점에 같은 방법으로 재측정해 실제 효과를 확인하십시오.

## 작업 규칙

기존 파일을 통째로 다시 쓰지 말고 증분 편집만 하십시오. 완료 보고에 `git diff --stat`을 반드시 포함하고, 삭제 줄 수가 추가 줄 수보다 많은 파일이 있으면 사유를 설명하십시오. 임시 파일과 백업 파일을 저장소에 남기지 마십시오. `scratch/` 아래 분석 스크립트도 저장소에 커밋하지 마십시오. 모든 파일은 UTF-8로 저장하고 저장 후 검증하십시오.

보고할 때 확인한 사실과 추론한 내용을 구분해 표기하십시오. 측정하지 않은 것에 확인되었다는 표현을 쓰지 마십시오.

**추가 규칙.** 지시받은 분석 틀을 적용하기 전에 그 틀이 대상 데이터에 유효한지 먼저 확인하십시오. 유효하지 않으면 분석을 수행하지 말고 그 사실을 보고하십시오. 이번 트리거 분류가 그 사례입니다.
