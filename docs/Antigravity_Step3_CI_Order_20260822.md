## 수정 3·4 검토 결과

### 채택합니다

크론 분산은 저장소에서 직접 확인했습니다. `daily-market`은 `:07`, `daily-distribution`은 `:22`, `daily-fees`는 `:37`로 정확히 반영되었고, 세 파일 모두 BOM 없이 UTF-8로 저장된 것도 확인했습니다. PowerShell의 BOM 삽입을 예상하고 Node로 검증한 처리는 적절했습니다.

Backfill 34회가 D1 잠금의 여파라는 추론도 설득력이 있습니다. Git에는 데이터가 있는데 화면에 반영되지 않아 강제 동기화를 반복했다는 설명은 정황과 맞습니다. 이 판단을 근거로 아래 작업 순서를 조정합니다.

### 두 가지는 정정하십시오

**첫째, 숫자가 맞지 않는데 그 사실이 보고에 없습니다.** 직전 표에는 "기타(실행 전 취소 등) 22건"이었는데 이번 보고는 26 + 5 + 3 = 34건입니다. 두 값은 다른 집합입니다. 22건은 job이 0개인, 즉 시작조차 못 한 run이고, 34건은 실행 도중 취소된 run까지 포함한 값입니다. 후자는 이미 각 워크플로 행에 집계되어 있습니다.

모순은 아니지만 **수치가 달라졌으면 그 차이를 먼저 설명해야 합니다.** 설명 없이 다른 숫자를 제시하면 읽는 쪽이 어느 쪽이 맞는지 판단할 수 없습니다.

**둘째, "정확히 맞습니다"는 과한 표현입니다.** 일일 데이터 워크플로의 취소는 5 + 3 = 8건이고 영업일은 약 21일입니다. 매일 하나씩 취소된 것이 아니라 **다섯 번에 한 번꼴로 발생**한 것입니다. 가설의 방향은 맞았지만 규모는 다릅니다.

이 구분이 중요한 이유는, 8건으로는 이번 달 데이터 누락 전부를 설명할 수 없기 때문입니다. **나머지 누락은 D1 잠금이 원인일 가능성이 높으며, 그것이 아래 작업 순서를 바꾸는 근거입니다.**

### 정리하십시오

`scratch/` 아래 분석 스크립트 4개(`analyze_runs.cjs`, `analyze_runs_v2.cjs`, `analyze_runs_async.cjs`, `check_cancelled.cjs`)가 작업 트리에 남아 있습니다. 커밋되지는 않았으나 "작업 후 `git status`에 추적되지 않는 파일이 없어야 한다"는 규칙 위반입니다.

`temp.json`, `latest.js.tmp`에 이어 세 번째 반복입니다. 이번에는 파일 삭제와 함께 `.gitignore`에 `scratch/`를 추가해 구조적으로 재발을 막으십시오.

## 작업 순서 변경

당초 수정 1 다음에 수정 2(배포 워크플로 경량화)를 두었으나, **D1 잠금 해결을 그 앞으로 당깁니다.**

근거는 두 가지입니다. 잠금은 비용이 아니라 데이터 정합성 문제이며 지금도 조용히 데이터를 누락시키고 있습니다. 그리고 이번 보고로 Backfill 34회가 잠금의 여파라는 연결이 드러났으므로, 잠금을 고치면 그 실행이 통째로 사라져 비용 절감 효과까지 따라옵니다.

변경된 순서는 다음과 같습니다.

1. 경량 CI 신설 (이번 지시)
2. D1 잠금 해결 (다음 지시)
3. 배포 워크플로 경량화 (마지막, 프로덕션 경로를 건드리므로 가장 나중)

## 이번 작업: 경량 CI 워크플로 신설

### 설계 함정을 먼저 짚습니다

단순히 `push`마다 lint와 test와 build를 돌리는 CI를 만들면 **비용이 배포 워크플로에서 CI로 옮겨갈 뿐입니다.** 하루 10회 푸시에 회당 4분이면 월 800분입니다. 절감 폭이 기대보다 훨씬 작아집니다.

따라서 CI를 **속도 우선과 완전 검증 두 층으로 나누십시오.**

### 계층 1. 빠른 검증 (모든 푸시)

트리거는 `push`이며, `paths-ignore`로 `data/**`, `docs/**`, `**.md`를 제외합니다.

**단일 job, 목표 소요 2분 이내**로 구성합니다. 포함할 것은 checkout, setup-node(`cache: npm`), `npm ci`, `npm run lint`, `npx tsc --noEmit`, `npm test`, 그리고 두 Worker의 `typecheck`입니다.

**`npm run build`는 이 계층에 넣지 마십시오.** Next.js 전체 빌드는 오래 걸리며, 타입 오류는 `tsc --noEmit`이 훨씬 빠르게 잡습니다. 이 계층의 목적은 "지금 고친 게 깨지지 않았는가"를 몇 분 안에 알려 주는 것입니다.

```yaml
concurrency:
  group: ci-fast-${{ github.ref }}
  cancel-in-progress: true
```

연속 푸시 시 이전 실행이 반드시 취소되어야 합니다. 이 설정이 없으면 절감 효과의 절반이 사라집니다.

### 계층 2. 완전 검증 (main 대상 PR에서만)

트리거는 `pull_request`이며 `branches: [main]`으로 한정합니다. `draft` PR에서는 실행하지 마십시오.

계층 1의 전부에 더해 `npm run build`를 수행합니다. 실제 빌드가 깨지는지는 여기서 잡습니다.

```yaml
concurrency:
  group: ci-full-${{ github.ref }}
  cancel-in-progress: true
```

### 두 계층 모두에 적용할 것

Cloudflare 시크릿을 주입하지 마십시오. **CI는 어떤 것도 배포하지 않습니다.** 배포 권한이 필요 없는 워크플로에 배포 토큰을 노출할 이유가 없습니다.

`permissions`는 `contents: read`만 부여하십시오.

### 완료 판정

빠른 검증이 실제 푸시에서 2분 이내로 완료되는 것을 확인하십시오. 연속으로 두 번 푸시했을 때 첫 실행이 취소되는 것을 확인하십시오. `data/` 파일만 변경한 커밋에서는 CI가 트리거되지 않는 것을 확인하십시오. main 대상 PR을 하나 열어 완전 검증이 빌드까지 수행하는 것을 확인하십시오.

완료 보고에 위 네 가지 확인 결과와 각 실행의 실제 소요 시간을 포함하십시오.

### 이후 작업 방식 (중요)

CI가 동작하기 시작하면 **코드 검증 목적으로 `Deploy market briefing production`을 실행하지 마십시오.** 그 워크플로는 실제 릴리스에만 사용합니다.

이번 달 215회 수동 실행의 대부분이 검증 목적이었고 그것이 전체 비용의 73퍼센트였습니다. 도구를 만들어도 사용 습관이 바뀌지 않으면 절감은 일어나지 않습니다.

## 작업 규칙

보고할 때 확인한 사실과 추론한 내용을 구분해 표기하십시오. 이전 보고와 수치가 달라지면 그 차이를 먼저 설명하십시오. 측정하지 않은 것에 확인되었다는 표현을 쓰지 마십시오.
