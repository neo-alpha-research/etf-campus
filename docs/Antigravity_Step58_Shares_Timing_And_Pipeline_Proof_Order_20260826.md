## 2. 좌수 기준 시점이 확정되었습니다

**작업 A 를 전부 수행할 필요가 없어졌습니다.** 발신 측에서 세 거래일 마스터 CSV 를 교차 대조해 답을 얻었습니다.

### 2-1. 교차 대조 결과

`AUM / NAV` 의 기준일과 `shares` 의 기준일을 서로 다르게 조합해 불일치율을 측정했습니다.

```
AUM·NAV 기준일        shares 8/21   shares 8/24   shares 8/25
2026-08-21              25.8%          8.4%         26.7%
2026-08-24              33.6%         28.3%          7.8%
2026-08-25              38.0%         34.6%         25.9%
```

**같은 날끼리 맞추면 26 퍼센트가 어긋납니다. `shares` 를 하루 뒤 값으로 맞추면 8 퍼센트로 떨어집니다.**

8월 21일의 AUM 과 NAV 는 8월 24일의 `shares` 와 맞고, 8월 24일의 AUM 과 NAV 는 8월 25일의 `shares` 와 맞습니다. **두 쌍 모두에서 재현됩니다.**

### 2-2. NAV 는 당일 값입니다

`close` 대비 `nav` 괴리율 분포입니다.

```
중앙값            +0.004%
절댓값 0.5% 이내   73.1%
5 ~ 95 퍼센타일   -0.74% ~ +1.11%
```

**괴리율이 0 근처에 정상 분포합니다.** NAV 가 하루 밀려 있다면 하루치 가격 변동폭만큼 벌어져야 하는데 그렇지 않습니다.

### 2-3. 결론

```
close    T 시점
nav      T 시점
aum      T 시점
shares   T-1 시점
```

**`shares` 만 하루 지연된 값입니다.**

따라서 실측 좌수로 순유입을 계산하면 **T-2 에서 T-1 사이에 일어난 자금 흐름을 오늘 것으로 기록하게 됩니다.**

### 2-4. 순유입 계산 방식을 확정합니다

**역산 방식을 채택하십시오.**

```
좌수(T)   = AUM(T) / NAV(T)
순유입(T) = (좌수(T) - 좌수(T-1)) * NAV(T)
```

**직전 지시서 6-1 의 `net_flow_shares` 와 `net_flow_derived` 2중 적재는 그대로 유지하십시오.** `net_flow_method` 에 `'derived'` 를 넣으십시오.

**실측 좌수 컬럼을 지우지 마십시오.** 시점이 하루 밀렸을 뿐 값 자체는 원천 데이터이며, 나중에 좌수 이력이 쌓이면 검증 기준으로 쓸 수 있습니다.

### 2-5. 그래도 남는 확인 하나

**8 퍼센트 잔차가 설명되지 않습니다.** 시점을 맞춰도 어긋나는 종목이 있습니다.

**직전 지시서 3-2 의 외부 대조만 수행하십시오.** 069500 KODEX 200, 102110 TIGER 200, 428510 KODEX 차이나AI테크액티브 세 종목입니다.

운용사 공시 또는 KRX 정보데이터시스템 화면에서 특정 거래일의 상장좌수를 눈으로 확인해 숫자를 적어 보고하십시오. **`shares` 와 맞는지 `AUM / NAV` 와 맞는지만 알면 됩니다.**

**3-1 과 3-3 은 수행하지 마십시오.** 2-1 과 2-2 로 답이 나왔습니다.

## 4. 파이프라인이 실행되지 않았습니다

### 4-1. 무엇을 했는지

```
repopulate_latest_snapshot.py
repopulate_all_history_shares.py
apply_migration_0016.py
```

**세 스크립트 모두 D1 을 직접 수정합니다. 발행 파이프라인을 거치지 않았습니다.**

`asset_detail` 이 107에서 691로 오른 것도, `shares` 가 채워진 것도 **스크립트가 직접 UPDATE 한 결과입니다.**

### 4-2. 왜 문제인가

**우리가 오늘 하고 있는 일의 목적은 내일 아침 자동 실행이 제대로 도는지 확인하는 것입니다.**

D1 을 직접 고치면 화면은 정상으로 보입니다. **그러나 파이프라인이 같은 값을 만들어 내는지는 여전히 모릅니다.** 내일 아침 워크플로가 돌면서 잘못된 값으로 다시 덮어쓸 수 있습니다.

**`source_run_id` 와 `source_hash` 가 행 내용을 더 이상 설명하지 못합니다.** 어느 실행이 어느 값을 만들었는지 추적이 끊어졌습니다.

**이전에 `chunk_1.sql` 을 프로덕션 D1 에 직접 실행했던 것과 같은 방식입니다.**

### 4-3. 지시

**최신 거래일 하나에 대해 실제 발행 파이프라인을 한 번 돌리십시오.**

```
gh workflow run daily-market.yml -f target=<최신 거래일>
```

**실행 전에 해당 날짜의 `asset_detail` 과 `shares` 를 일부러 NULL 로 비우십시오.** 파이프라인이 스스로 채우는지 봐야 하기 때문입니다. **비우기 전에 현재 값을 파일로 백업하십시오.**

**실행 후 확인하십시오.**

```sql
SELECT COUNT(*) AS total,
       COUNT(NULLIF(asset_detail,'')) AS with_detail,
       COUNT(shares) AS with_shares,
       COUNT(DISTINCT source_run_id) AS runs
FROM briefing_etf_daily WHERE as_of_date = '<최신 거래일>' AND is_general_etf = 1;
```

**`with_detail` 이 691, `with_shares` 가 1,015 로 다시 나와야 합니다.** 스크립트가 아니라 파이프라인이 만들어야 합니다.

**나오지 않으면 다섯 지점 중 어딘가가 여전히 끊긴 것입니다.** 그 경우 스크립트로 메우지 말고 끊긴 지점을 보고하십시오.

**앞으로 D1 을 직접 UPDATE 하지 마십시오.** 진단용 SELECT 는 허용합니다. 값을 바꾸는 것은 파이프라인만 합니다. 예외가 필요하면 사유와 대상 행 수를 먼저 보고하고 승인을 받으십시오.
