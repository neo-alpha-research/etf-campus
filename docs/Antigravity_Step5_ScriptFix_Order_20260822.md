## 1. 채택하는 것

크론 분산 커밋과 `jobs.json` 정리는 확인했습니다. `git log`와 `git status`를 함께 제시한 보고 방식도 적절합니다.

**Cloudflare Pages가 GitHub 저장소와 연동되어 있다는 확인은 이번 조사의 가장 큰 수확입니다.** 이것이 사실이라면 사이트 갱신에 Actions가 필요 없고, 데이터가 저장소에 들어가기만 하면 서비스는 계속 돌아갑니다. 배포 워크플로의 `deploy_pages` job도 중복이 됩니다.

다만 이 결론을 확정하려면 아래 2-1의 한 가지를 더 확인해야 합니다.

---

## 2. 정정이 필요한 세 가지

### 2-1. Pages가 감시하는 브랜치를 확인하지 않았습니다

`Git Provider: Yes`만으로는 부족합니다. **Pages 프로젝트의 production branch가 무엇인지**가 핵심입니다.

지금 작성하신 서버 스크립트는 `git push origin dev`로 `dev` 브랜치에 커밋합니다. 만약 Pages가 `main`을 감시한다면 데이터가 프로덕션에 도달하지 않습니다. 자동 배포가 된다는 결론 자체가 성립하지 않습니다.

`etf-campus` Pages 프로젝트의 production branch, preview branch 설정, 그리고 빌드 명령과 출력 디렉터리 설정을 조회해 보고하십시오. 빌드 설정이 비어 있다면 Git 연동은 되어 있으나 실제 빌드는 수행하지 않는 상태일 수 있습니다.

또한 일일 데이터 커밋이 Pages 빌드를 트리거할 경우 월 빌드 횟수가 얼마나 되는지, 무료 한도 대비 여유가 있는지도 함께 확인하십시오.

### 2-2. 한도 초기화 시점은 추정입니다

계정 생성일이 7월 26일이라는 사실로부터 "매월 26일 초기화"를 도출하고 이를 "확인된 사실"로 표기하셨습니다. **이는 추론입니다.** 계정 생성일과 Actions 무료 분 초기화 주기가 일치한다는 근거가 제시되지 않았습니다.

이 값은 실무적으로 중요합니다. 초기화가 내일이면 하루만 기다리면 되고, 다음 달 1일이면 열흘간 서버 이전이 유일한 대안이 됩니다. **결정의 크기가 완전히 달라집니다.**

운영자가 GitHub 결제 화면에서 직접 확인할 사안이므로 당신은 추정치를 확정으로 보고하지 마십시오. 보고서에는 "추정"으로 표기를 고치십시오.

### 2-3. 서버 스크립트가 동작하지 않습니다

`scratch/run_daily_market.sh`를 검증했습니다. 아래 오류들이 있습니다.

**치명적 오류 하나.** 스크립트가 호출하는 `scripts/refresh_official_etf_data.py`는 **저장소에 존재하지 않습니다.** 실제 수집 명령은 `python scripts/update_daily_data.py`입니다. 워크플로의 스텝 이름 `Refresh official ETF data`를 파일명으로 옮기신 것으로 보입니다.

그리고 거기 붙인 플래그(`--retry-unverified --apply --apply-returns --apply-listing-cache --purge-nonrecent --throttle-seconds 1.5`)는 그 스텝의 것이 아니라 **별개의 조건부 스텝인 `rebuild_listing_reference_prices.py`의 인자**입니다. 서로 다른 두 스텝이 하나로 합쳐졌고, 그 결과 실제 수집기가 스크립트에서 통째로 빠졌습니다.

이 상태로 실행하면 첫 명령에서 실패하며 데이터는 한 건도 수집되지 않습니다.

**의존성 누락.** 워크플로는 `beautifulsoup4 certifi requests xlrd`를 설치하는데 스크립트는 `beautifulsoup4 xlrd`만 설치합니다. `requests`와 `certifi`가 빠졌습니다.

**조건 분기 소실.** 워크플로에서 `rebuild_listing_reference_prices.py`는 미검증 최근 상장 종목이나 오래된 캐시가 감지될 때만 실행됩니다. 스크립트에는 이 판정이 없습니다.

**재시도 부재.** 워크플로는 하루 두 번 실행되어 첫 시도에서 데이터가 아직 공개되지 않았으면 다음 rung이 받아 갑니다. 스크립트는 신선도 미달 시 `exit 1`로 끝나며 재시도 경로가 없습니다.

**동시 실행 보호 부재.** 두 실행이 겹치면 git 작업이 충돌합니다. 워크플로에는 `concurrency` 그룹이 있었지만 스크립트에는 대응 장치가 없습니다.

**버전 관리 밖에 있습니다.** `scratch/`는 방금 `.gitignore`에 추가한 디렉터리입니다. 프로덕션 데이터 수집을 담당할 스크립트가 버전 관리되지 않는 위치에 있으면 안 됩니다.

## 3. 이번 작업 지시

### 3-1. 수집 스크립트 재작성

**위치를 `scripts/run_daily_market.sh`로 옮기고 저장소에 커밋하십시오.** `scratch/`가 아닙니다.

**작성 방법을 바꾸십시오.** 워크플로 파일을 눈으로 읽고 옮겨 적지 말고, `daily-market.yml`의 각 `run:` 블록에 실제로 적힌 명령을 그대로 추출해 옮기십시오. 스텝 이름이 아니라 명령을 기준으로 삼아야 합니다. 옮긴 뒤 스크립트가 호출하는 모든 파일이 실제로 존재하는지 검증하고 그 결과를 보고에 포함하십시오.

**포함할 것.**

`update_daily_data.py` 실행이 첫 단계입니다. `TARGET_DATE` 환경변수가 있으면 `--target`과 `--require-exact-date`를 붙이고, 없으면 인자 없이 실행하는 워크플로의 분기를 그대로 유지하십시오.

최근 상장 참조가격 갱신은 워크플로의 판정 로직을 그대로 옮겨 조건부로 실행하십시오. 판정 없이 항상 실행하면 외부 API 호출이 불필요하게 늘고 스로틀 대기 때문에 실행 시간이 크게 늘어납니다.

신선도 판정, 분류 초안 갱신, 시장 지수 수집, 데이터 커밋, D1 적재, 스냅샷 발행은 워크플로 순서를 그대로 유지하십시오.

의존성 설치 목록을 `beautifulsoup4 certifi requests xlrd`로 맞추십시오.

**추가할 것.**

동시 실행 방지를 위해 `flock`으로 락 파일을 잡으십시오. 이미 실행 중이면 즉시 종료합니다.

푸시 대상 브랜치를 하드코딩하지 말고 환경변수 `TARGET_BRANCH`로 받되 기본값을 두십시오. 기본값은 2-1에서 확인한 Pages production branch와 일치시켜야 합니다.

신선도 미달 시 종료 코드를 분리하십시오. 데이터 미공개로 인한 정상적 미달과 실제 오류를 구분해야 이후 재시도 정책을 세울 수 있습니다.

**제외할 것.** 빌드와 배포는 넣지 마십시오. Pages가 처리합니다.

### 3-2. 실행 스케줄 설계

서버에서 워크플로의 재시도 사다리를 재현해야 합니다. 하루 두 번(KST 06:07, 07:07 상당)의 cron 항목을 두되, 첫 실행이 성공하면 두 번째는 신선도 판정에서 즉시 종료되도록 하십시오.

cron 항목 초안을 보고에 포함하고, 실제 서버 설치는 별도 지시로 진행합니다.

### 3-3. 완료 판정

스크립트가 호출하는 모든 스크립트 파일의 존재 여부 검증 결과를 표로 제시하십시오. `bash -n`으로 문법 검사를 통과해야 합니다. 워크플로의 각 `run:` 블록과 스크립트의 각 단계를 1대1로 대조한 표를 함께 제시하십시오. 빠진 단계가 없어야 합니다.

실제 실행은 서버 환경이 준비된 뒤이므로 이번에는 정적 검증까지만 수행하십시오.

## 4. D1 잠금 작업은 다음입니다

위 작업을 마친 뒤 착수합니다. 지시 내용은 이전과 동일합니다. 마이그레이션 `0009`에 `locked_at` 임대 시간(기본 30분, 환경변수 조정 가능), 멱등 재처리, 노후 잠금 알림, `(status, locked_at)` 복합 인덱스입니다.

이 작업은 `wrangler`를 로컬에서 실행할 수 있으므로 Actions 잠금과 무관하게 진행 가능합니다.

## 5. 작업 규칙

기존 파일을 통째로 다시 쓰지 말고 증분 편집만 하십시오.

완료 보고에 `git log --oneline -n 5`와 `git status --porcelain`을 함께 넣으십시오.

임시 산출물은 `scratch/` 안에서만 만들되, **프로덕션에서 사용할 스크립트는 `scripts/`에 두고 커밋하십시오.** 둘을 구분하십시오.

모든 파일은 UTF-8로 저장하고 BOM이 없는지 검증하십시오.

**보고 규칙을 하나 더합니다.** 다른 파일의 내용을 옮겨 적는 작업을 했다면, 옮긴 결과가 원본과 일치하는지 **기계적으로 대조한 결과를 보고에 포함하십시오.** 이번 스크립트는 눈으로 읽고 옮기는 과정에서 스텝 이름과 명령이 뒤바뀌었습니다. 파일 존재 확인만 했어도 즉시 발견되었을 오류입니다.
