## 1. 채택하는 것

Cloudflare Pages 조사는 정확하고 유용합니다. production branch가 `main`, preview가 전체 브랜치, `build_command`가 `npm run build`, `destination_dir`가 `out`이며 이번 달 빌드 25회로 월 500회 한도에 여유가 크다는 확인을 근거로 채택합니다.

이로써 **사이트 갱신에 GitHub Actions가 필요 없다는 결론이 확정되었습니다.** 배포 워크플로의 `deploy_pages` job과 `validate` job의 빌드는 중복입니다.

한도 초기화 시점을 추정으로 정정한 것도 적절합니다.

## 2. 스크립트에 버그 세 개가 있습니다

`bash -n`은 통과하지만 실행되지 않습니다.

### 2-1. 치명적: 내장 Python이 문법 오류입니다

54행부터 56행이 다음과 같습니다.

```python
print(fbrequired={str(bool(pending or stale_cache)).lower()}")
print(fbpending_count={len(pending)}")
print(fbstale_cache_count={len(stale_cache)}")
```

원본은 `print(f"required={...}")` 입니다. **`f"` 가 `fb` 로 깨졌습니다.** Python SyntaxError이며 즉시 실패합니다.

이 코드는 `LISTING_OUTPUT=$( ... )` 명령 치환 안에 있고 스크립트 최상단에 `set -e`가 걸려 있으므로, **치환 실패가 곧 스크립트 종료입니다.** 수집 첫 단계 직후 죽습니다. 결과적으로 지난번과 마찬가지로 데이터가 한 건도 처리되지 않습니다.

### 2-2. 변수명 오타

95행이 `FTESH="false"` 입니다. `FRESH` 여야 합니다.

바로 아래 `exit 2`가 있어 당장 동작에는 영향이 없으나, 이후 누가 이 분기를 수정하면 조용히 잘못 동작합니다. `bash -n`으로는 잡히지 않는 종류의 오류입니다.

### 2-3. 실패 은폐가 추가되었습니다

135행이 다음과 같습니다.

```bash
python scripts/publish_market_source_snapshot.py || true
```

**원본 워크플로에는 `|| true`가 없습니다.** 지시하지 않은 동작 변경이며, 하필 **D1 잠금 문제의 진원지로 지목된 바로 그 단계**에 실패 은폐를 붙였습니다.

이 파이프라인에서 우리가 제거하려는 것이 정확히 "실패했는데 성공한 것처럼 끝나는" 패턴입니다. 삭제하십시오.

### 2-4. 푸시 대상이 잘못 동작합니다

`TARGET_BRANCH` 기본값은 `main`인데, 커밋은 체크아웃된 브랜치(현재 `dev`)에 만들어집니다. 그 상태에서 `git push origin main`은 **로컬 `main` 참조를 밀어냅니다.** 방금 만든 커밋은 `dev`에 있으므로 원격에 반영되지 않습니다.

`git pull --rebase --autostash origin main` 역시 `dev` 위에서 실행되면 `dev`를 `main` 위로 리베이스합니다. 의도한 동작이 아닙니다.

푸시를 `git push origin HEAD:$TARGET_BRANCH` 형태로 바꾸거나, 스크립트 시작 시 대상 브랜치를 명시적으로 체크아웃하도록 하십시오. **서버의 작업 복사본은 `main`을 기준으로 두는 것을 권장합니다.**

## 3. 근본 원인과 구조적 수정

### 3-1. 원인

두 번 연속 같은 유형의 오류가 났습니다. 지난번은 존재하지 않는 파일명, 이번은 문자열 깨짐입니다. 공통점은 **원본 내용을 사람이 다시 타이핑하거나 base64로 재구성하는 과정에서 손상되었다는 것**입니다.

PowerShell의 인코딩 문제를 피하려고 base64 경유 방식을 쓰셨는데, base64 페이로드 자체를 손으로 만드는 과정에서 내용이 깨졌습니다. 우회 수단이 새로운 오류원이 된 셈입니다.

### 3-2. 구조적 수정: 내장 Python을 파일로 분리하십시오

`daily-market.yml`의 `Detect recent-listing reference-price work` 스텝에 있는 Python 코드를 **`scripts/detect_listing_reference_work.py`로 분리**하십시오.

그다음 워크플로와 셸 스크립트 양쪽이 그 파일을 호출하게 하십시오.

```bash
python scripts/detect_listing_reference_work.py "$AS_OF_DATE"
```

이렇게 하면 세 가지가 해결됩니다. 같은 코드가 두 곳에 중복되지 않고, 힘든 heredoc 이스케이프가 사라지며, 파일이므로 문법 검사와 테스트가 가능해집니다.

**워크플로 수정과 스크립트 수정을 같은 커밋에 넣어 두 경로가 항상 같은 코드를 쓰도록 하십시오.**

### 3-3. 파일 생성 방법을 바꾸십시오

base64 재구성을 쓰지 마십시오. 원본에서 내용을 그대로 복사하거나, 파일 편집 도구로 직접 수정하십시오. 재작성이 필요하면 원본 파일을 읽어 프로그램으로 변환하고, 변환 결과를 원본과 기계적으로 대조하십시오.

## 4. 검증 방법 교정

이번에 수행하신 검증은 이 실패를 잡을 수 없었습니다.

`bash -n`은 **heredoc 내부를 파싱하지 않습니다.** 그 안의 Python이 어떻게 깨져 있든 통과합니다.

"기계적 대조"라고 하신 것은 **파일 존재 확인**이었습니다. 파일이 있는지만 봤을 뿐 내용이 올바른지는 보지 않았습니다.

**앞으로 다음 세 가지를 모두 수행하고 결과를 보고에 포함하십시오.**

첫째, `bash -n`으로 셸 문법을 검사합니다.

둘째, **스크립트가 실행하는 모든 Python 파일을 `python -m py_compile`로 컴파일 검사합니다.** 내장 코드를 파일로 분리하면 이 검사에 자동으로 포함됩니다.

셋째, **`--dry-run` 모드를 스크립트에 추가하십시오.** 환경변수 `DRY_RUN=1`이면 외부 API 호출과 git 푸시를 건너뛰고 각 단계의 명령만 출력합니다. 실제 실행 없이 전체 경로가 끝까지 도달하는지 확인할 수 있습니다.

`DRY_RUN=1`로 스크립트를 끝까지 실행한 로그를 보고에 첨부하십시오. **이것이 이번 완료 판정의 핵심 근거입니다.**

## 7. 작업 규칙

기존 파일을 통째로 다시 쓰지 말고 증분 편집만 하십시오. base64 재구성 방식을 쓰지 마십시오.

완료 보고에 `git log --oneline -n 5`와 `git status --porcelain`을 함께 넣으십시오.

지시하지 않은 동작 변경을 하지 마십시오. `|| true` 추가가 그 사례입니다. 원본과 다르게 만들어야 할 이유가 있다면 먼저 질문하십시오.

모든 파일은 UTF-8로 저장하고 BOM이 없는지 검증하십시오.
