## 1. 운영자 제안에 대한 답을 수정합니다

**직전 지시서에서 "법령 기준 세 종류 중 하나만 로직화 가능하다" 고 했습니다. 예외 조항이 확인되면서 그 판단이 바뀝니다.**

### 1-1. 예외 조항은 관측 가능한 조건으로 되어 있습니다

```
조건 1   배율이 1배일 것          risk_type 으로 판정 가능
조건 2   기초자산이 증권일 것       asset_class 로 판정 가능 (원자재·통화 제외)
조건 3   합성형일 것              종목명 "(합성)" 은 표준 표기
```

**세 조건 모두 우리가 가진 데이터로 판정할 수 있습니다.**

**따라서 합성 ETF 에 대해서는 이름 추측이 아니라 법령 조건의 직접 구현이 가능합니다. 운영자 제안이 이 영역에서 성립합니다.**

### 1-2. 판정 영역을 넷으로 다시 나누십시오

```
영역 A  레버리지·인버스        예외 조항이 명시적으로 배제      확정 불가    103종목
영역 B  1배 증권형 합성        2016 예외 조항 충족            확정 가능    검토 대상 74종목
영역 C  선물형                예외 조항 없음. 40% 기준 적용    구조상 불가  33종목
영역 D  커버드콜              옵션 매도. 산정 방식이 다름      회색지대     62종목
```

**A 와 B 는 법령 조건을 직접 구현할 수 있으므로 신뢰도 높음이 정당합니다.**

**C 는 예외 조항이 없어 40퍼센트 기준이 그대로 적용됩니다. 선물로 지수를 추종하면 명목 노출이 100퍼센트에 가까우므로 초과가 구조적으로 거의 확실합니다. 다만 국채선물을 일부만 편입한 채권형처럼 예외가 있을 수 있으므로 신뢰도는 보통을 유지하십시오.**

**D 가 진짜 회색지대입니다. 커버드 구조에서 옵션 매도의 위험평가액이 어떻게 산정되는지가 관건입니다. 보통을 유지하십시오.**

### 1-3. 지시

**영역 B 의 판정 조건을 엔진에 명시적으로 구현하십시오.**

```
if 배율 1배 and 기초자산 증권 and 합성형:
    편입 가능
    pension_source     = "법령조건직접판정"
    pension_confidence = "높음"
    pension_reason     = "퇴직연금감독규정 1배 증권형 합성 ETF 예외 (2016.9.21 의결)"
```

**조건 판정에 쓰는 값을 이름 문자열이 아니라 컬럼으로 만드십시오.**

**"(합성)" 표기가 표준인지 먼저 확인하십시오.** 99종목 전부에 괄호 표기가 있는지, 예외 표기가 있는지입니다. **하나라도 다르면 이름 기반을 쓸 수 없습니다.**

**기초자산이 증권이 아닌 합성 ETF 가 있는지 확인하십시오.** 원자재나 통화를 스왑으로 추종하는 상품입니다. 있으면 예외 조항 대상이 아니므로 별도 처리해야 합니다.

**두 확인 결과를 먼저 보고하십시오. 구현은 그 뒤입니다.**

## 3. 보고되지 않은 커밋이 프로덕션 워크플로를 바꿨습니다

### 3-1. 무슨 일이 있었는가

**보고서 1단계에 "반영 커밋 `f28ba57`" 이라고만 적혀 있습니다.**

**그 커밋의 실제 내용입니다.**

```
f28ba57 fix(ci): unify Node.js setup to .node-version and allow manual bypass in daily workflow guards

.github/workflows/book-curation.yml       2 +-
.github/workflows/daily-distribution.yml  5 ++++-
.github/workflows/daily-holdings.yml      7 +++++--
.github/workflows/kofia-fee-sync.yml      2 +-
.gitignore                                5 +++++
```

**민감 파일 차단이라는 보안 조치가, 전혀 무관한 CI 작업 커밋 안에 5줄로 묻혔습니다.**

**그리고 그 커밋은 매일 아침 도는 프로덕션 워크플로 두 개를 바꿨습니다. 보고서에 언급이 없습니다.**

### 3-2. 변경 내용 자체는 타당합니다

```diff
- if python scripts/check_workflow_success_today.py --workflow daily-distribution.yml; then
+ if [ "${{ github.event_name }}" = "workflow_dispatch" ]; then
+   echo "Manual run requested. Bypassing already-succeeded guard."
+   echo "already_run=false" >> "$GITHUB_OUTPUT"
+ elif python scripts/check_workflow_success_today.py --workflow daily-distribution.yml; then
```

**수동 실행일 때만 중복 실행 가드를 우회합니다. 스케줄 실행은 가드를 그대로 지킵니다.**

**설계가 옳습니다. 문제 삼는 것은 내용이 아니라 보고입니다.**

### 3-3. 왜 문제인가

**첫째, 커밋 메시지가 내용을 설명하지 않습니다.** 나중에 "요청 원문 차단 패턴이 언제 왜 들어갔는지" 찾으려면 CI 커밋을 뒤져야 합니다.

**둘째, 직전 지시서가 "다른 작업의 변경분을 커밋하지 마십시오. 규제 작업과 분리하십시오" 라고 명시했습니다.** 그런데 제가 1단계로 지시한 보안 조치가 오히려 다른 작업에 흡수되었습니다.

**셋째, 프로덕션 워크플로 변경은 그 자체로 보고 대상입니다.** 내일 아침 실행에 영향을 주는 파일입니다.

### 3-4. 지시

**이번에는 되돌리지 마십시오. 변경 내용이 타당하고 이미 커밋되었습니다.**

**대신 다음을 하십시오.**

**`f28ba57` 에 포함된 워크플로 변경 4건의 목적과 영향 범위를 보고하십시오.** `book-curation.yml` 과 `kofia-fee-sync.yml` 의 Node 버전 변경도 포함입니다.

**앞으로 `.github/workflows/` 변경은 다른 작업과 섞지 말고 단독 커밋으로 하십시오. 그리고 반드시 보고서 본문에 적으십시오.**

**보안 관련 변경도 단독 커밋으로 하십시오.** 무엇이 왜 차단되었는지 커밋 하나로 추적되어야 합니다.
