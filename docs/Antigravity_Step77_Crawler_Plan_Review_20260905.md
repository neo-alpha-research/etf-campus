## 0. 결론

**Phase 1 만 승인합니다. Phase 2 와 Phase 3 은 보류합니다.**

**아키텍처 설계 자체는 훌륭합니다.** GitOps 분리, `repository_dispatch` 경유, 불일치 격리 로그, 판정은 리포지토리 안의 단일 엔진이 수행하는 구조 전부 옳습니다.

**문제는 설계 품질이 아니라 문제 정의입니다. 92건을 위해 서버를 세울 필요가 없습니다.**

## 1. 얻는 것이 무엇인지 다시 보십시오

**회색지대 92건의 현재 화면 상태입니다.**

```
선물형 33건    이미 "연금불가" 로 표시. 사용자가 매수 대상으로 보지 않음
커버드콜 59건  이미 "편입 가능" 으로 표시. "확인권장" 배지만 추가로 붙어 있음
```

**33건을 승격하면 "연금불가" 옆의 "정책확인" 배지가 사라집니다. 판정은 그대로입니다.**

**59건을 승격하면 "확인권장" 배지가 사라집니다. 판정은 그대로입니다.**

**즉 92건 전부를 승격해도 사용자가 보는 판정 결과는 한 건도 바뀌지 않습니다. 배지만 사라집니다.**

**월 3만원에서 4만원의 인프라와 구축 유지보수 시간을 배지 제거에 쓰는 것이 맞는지 먼저 판단하십시오.**

**배지가 붙어 있는 것이 오히려 정직한 상태입니다.** 우리가 확인하지 못한 것을 확인하지 못했다고 표시하는 것입니다.

---

## 2. 크롤링 대상이 실재하는지 확인되지 않았습니다

**계획서는 "주요 증권사의 퇴직연금 매매가능 ETF 리스트(공식 공시/홈페이지 제공)" 를 전제합니다.**

**그런데 Step71 5단계 조사에서 본인이 이렇게 보고하셨습니다.**

> 각 증권사는 자체 웹사이트/MTS 공지사항을 통해 **비정기 엑셀 파일**로 게시합니다.

**"비정기 엑셀 파일" 을 Playwright 로 정기 수집하는 파이프라인은 성립하기 어렵습니다.** 파일 위치와 형식이 증권사마다 다르고 수시로 바뀝니다.

**인프라를 세우기 전에 다음을 확인하십시오.**

**미래에셋과 삼성 두 곳만 보십시오.** 퇴직연금 적격 ETF 목록이 실제로 공개 URL 로 존재하는지, 로그인 없이 접근 가능한지, 최근 갱신일이 언제인지입니다.

**존재하지 않거나 로그인이 필요하면 Phase 2 는 착수 자체가 불가능합니다.**

---

## 3. 약관 검토가 빠졌습니다

**계획서의 컴플라이언스 검토가 자본시장법 §101 만 다뤘습니다.**

**크롤링 대상 사이트의 이용약관은 검토되지 않았습니다.**

**증권사 웹사이트를 자동화 도구로 수집하는 것은 대부분 이용약관에서 금지합니다.**

**오늘 하루 KRX Open API 약관 제6조 제2항, 공공누리 유형별 상업적 이용 제한, §101 경계선을 그렇게 보수적으로 다뤘습니다. 그 결론이 증권사 사이트를 봇으로 긁는 것이 되면 일관성이 없습니다.**

**Phase 2 착수 전에 대상 사이트의 이용약관과 `robots.txt` 를 확인해 원문을 인용 보고하십시오.**

---

## 4. "WAF 회피" 는 설계 목표가 될 수 없습니다

**계획서 인프라 검토의 문장입니다.**

> 해외 리전에서 발생하는 국내 증권사 WAF 차단(403 Forbidden)을 NHN Cloud 한국 리전 고정 공인 IP 로 **100% 회피 가능**합니다

**WAF 차단은 자동 수집을 원치 않는다는 사업자의 의사표시입니다.**

**그것을 우회하기 위해 국내 IP 인프라를 세우는 것이 이 계획의 핵심 근거로 적혀 있습니다.**

**차단을 우회하는 것을 인프라 도입 사유로 삼지 마십시오.**

**그리고 "100퍼센트 회피 가능" 은 근거 없는 단정입니다.** WAF 는 IP 만 보지 않습니다. User-Agent, 요청 빈도, 헤더 조합, 브라우저 지문을 함께 봅니다. **오늘 여러 차례 지적한 무출처 단정과 같은 형태입니다.**

## 5. 본인이 추천했던 더 싼 경로가 있습니다

**Step72 5단계에서 이렇게 보고하셨습니다.**

> 경로 3: 운용사 상품 페이지의 퇴직연금 적격 공식 태그
> **가장 현실적 / 최저 비용 / 최고 신뢰도 (강력 추천)**
> 운용사 법무 컴플라이언스가 투자설명서와 거래소 협의를 마친 최종 결론 정보

**그런데 이번 계획서는 증권사 크롤링으로 갔습니다. 왜 바뀌었는지 설명이 없습니다.**

**운용사 경로가 더 나은 이유입니다.**

**5개사가 시장의 90퍼센트를 차지합니다.** 삼성, 미래에셋, KB, 신한, 한국투자입니다. 증권사보다 대상이 적습니다.

**상품 페이지는 공개이며 로그인이 필요 없습니다.**

**퇴직연금 적격 표기는 운용사가 책임지는 확정 정보입니다.** 증권사 전산 목록은 각 사의 취급 정책이 섞입니다.

### 5-1. 그리고 오늘 더 나은 도구가 생겼습니다

**프로덕션 홀딩스 API 로 구성종목 비중을 실측할 수 있습니다.**

```
https://etf-campus.pages.dev/api/holdings/{ticker}
```

**오늘 밤 `0086C0`, `0138Y0`, `0184N0` 세 종목을 이 경로로 5분 만에 판정했습니다.**

**커버드콜 59건 중 상당수는 구성종목 비중만 봐도 옵션 비중과 기초자산 구성이 드러납니다. 외부 크롤링 없이 우리 데이터로 판정 가능한 부분이 있습니다.**

**Phase 1 에 이 경로를 먼저 넣으십시오.**

## 6. Phase 1 은 승인하되 범위를 바꾸십시오

**순서가 옳습니다.** 스키마와 대조 스크립트를 먼저 확립해야 자동화 노드를 낭비 없이 설계할 수 있습니다.

**다만 다음을 바꾸십시오.**

**`data/regulatory/broker_pension_universe.csv` 를 수동 채움으로 시작하십시오.** 크롤러 없이 사람이 열어 보고 채웁니다.

**컬럼에 `source_type` 을 추가하십시오.**

```
ticker, source_type, source_name, pension_eligible_limit, effective_date, source_url, verified_by

source_type   운용사공시 | 증권사목록 | 홀딩스실측 | 투자설명서
```

**출처 종류가 섞이면 나중에 신뢰도 차등을 못 줍니다.**

**`SAMPLE_VERIFIED_TICKERS` 하드코딩을 CSV 참조로 바꾸는 것은 승인합니다.** 지금 5종목이 코드에 박혀 있는 것이 맞지 않습니다.

**`verify_broker_pension.py` 는 승격 로직이 아니라 대조 리포트로 먼저 만드십시오.** 자동 승격은 대조 실적이 쌓인 뒤입니다.

## 7. Phase 1 을 마치면 Phase 2 가 필요 없을 수 있습니다

**92건을 수동으로 대조하는 데 걸리는 시간을 실측하십시오.**

**운용사 5개사 페이지에서 92건을 확인하는 것은 하루 안에 끝날 작업으로 보입니다. 한 번 끝내면 이후에는 신규 상장분만 월 5건에서 10건입니다.**

**월 10건을 위해 서버를 유지하는 것과, 월 10건을 손으로 확인하는 것 중 무엇이 나은지는 실측 후에 판단하십시오.**

**Phase 1 완료 후 다음을 보고하십시오.**

```
92건 수동 대조에 실제로 걸린 시간
운용사 페이지에서 확인 가능했던 종목 수
확인 불가로 남은 종목 수와 그 이유
월 신규 상장 ETF 평균 건수
```

**이 네 숫자가 Phase 2 착수 여부를 결정합니다. 지금은 결정할 근거가 없습니다.**
