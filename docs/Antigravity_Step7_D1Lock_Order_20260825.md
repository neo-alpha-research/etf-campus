## 1. 검증 결과: 네 가지 수정 모두 확인했습니다

저장소를 직접 확인한 결과는 다음과 같습니다.

`scripts/detect_listing_reference_work.py`가 존재하고 `py_compile`을 통과합니다. `daily-market.yml` 77행이 이 파일을 호출하며 heredoc은 제거되었습니다. 셸 스크립트에서 `FTESH` 오타와 `|| true`가 사라졌고, 164행 푸시가 `HEAD:$TARGET_BRANCH` 형태로 교정되었습니다.

base64 재구성을 버리고 직접 편집으로 전환한 것, 그리고 `py_compile`과 `DRY_RUN` 검증을 실제로 수행한 것도 적절했습니다.

### 1-1. 두 가지만 보완하십시오

**`.run_daily_market.lock`을 `.gitignore`에 추가하십시오.** 스크립트가 실행될 때마다 작업 디렉터리에 생성되므로 매번 추적되지 않는 파일로 남습니다. 이번에는 수동으로 지우셨지만 서버에서 매일 돌면 반복됩니다.

**`DRY_RUN` 검증의 범위를 정확히 표기하십시오.** 현재 구현은 `LISTING_REQUIRED`, `FRESH`, `SNAPSHOT_CHANGED`, `PUBLISHABLE_CHANGED`를 모두 `true`로 고정합니다. 따라서 이 실행이 증명한 것은 **모든 조건이 참일 때의 경로가 끝까지 도달한다는 사실 하나**입니다.

신선도 미달 시의 `exit 2` 경로, 변경 없음 분기, 참조가격 갱신 생략 분기는 여전히 미검증입니다. "모든 단계가 누락 없이 트리거됨을 증명"이라는 표현은 과합니다. 향후 `DRY_RUN` 모드에서 각 분기 값을 환경변수로 주입할 수 있게 하면 나머지 경로도 검증할 수 있습니다. 이번에 당장 할 필요는 없으나 보고 표기는 정정하십시오.

### 1-2. 날짜 확인

오늘은 **2026년 8월 25일**입니다. 이전 지시서 일부를 08-21, 08-22로 잘못 기재한 것은 발신 측 오류입니다.

이것이 중요한 이유는, 초기화 시점이 매월 26일이라는 추정이 맞다면 **Actions 한도 복구가 내일**이기 때문입니다. 운영자가 결제 화면에서 이를 확인하는 즉시 서버 이전의 긴급도가 크게 달라집니다.

## 2. 서버 이전은 일시 보류합니다

한도 복구가 임박했을 가능성이 있으므로, 서버 설치와 cron 등록은 초기화 시점이 확정된 뒤에 진행합니다. 스크립트는 이미 준비되었으므로 언제든 착수할 수 있습니다.

**대신 지금은 D1 잠금 문제를 해결합니다.** 이 작업은 `wrangler`를 로컬에서 실행하므로 Actions 잠금과 무관하며, 지난 네 라운드에 걸쳐 계속 미뤄져 온 근본 문제입니다.

## 3. D1 잠금 해결 착수

### 3-1. 먼저 조사하고 보고하십시오 (코드 수정 전)

지난 라운드들에서 확인했듯, 문서에 적힌 전제를 검증 없이 적용하면 오류가 납니다. 마이그레이션을 작성하기 전에 아래를 실측해 보고하십시오.

**첫째, 대상 테이블의 실제 스키마를 확인하십시오.** `market_data_readiness`와 `market_source_consumer_runs`가 어느 마이그레이션에서 생성되었는지, 현재 컬럼 구성이 무엇인지, 인덱스가 있는지를 `PRAGMA table_info`와 `PRAGMA index_list`로 조회해 보고하십시오.

**둘째, 상태 값의 실제 어휘를 확인하십시오.** `processing`, `skipped_duplicate` 외에 어떤 값이 쓰이는지 실제 데이터에서 `SELECT DISTINCT status, COUNT(*)`로 집계하십시오. 문서에 언급된 두 값만 있다고 가정하지 마십시오.

**셋째, 이 상태를 읽고 쓰는 코드를 전부 찾으십시오.** `scripts/publish_market_source_snapshot.py`, `workers/market-event-dispatcher`, `workers/market-briefing-publisher` 세 곳이 후보이나 다른 곳이 있을 수 있습니다. 각 위치에서 어떤 조건으로 상태를 전이시키는지 정리해 표로 제시하십시오.

**넷째, 현재 잠긴 레코드가 실제로 있는지 확인하십시오.** 프로덕션 D1에서 `processing` 또는 `skipped_duplicate` 상태로 남아 있는 행과 그 생성 시각을 조회하십시오. 있다면 그것이 지금도 파이프라인을 막고 있는 증거입니다.

**이 네 가지를 보고한 뒤 구현 착수를 다시 지시받으십시오.**

### 3-2. 구현 사양 (조사 후 착수)

조사 결과가 전제와 크게 다르면 사양을 조정할 것이므로, 아래는 현재 이해를 기준으로 한 초안입니다.

**마이그레이션 `0009`에 다음을 포함합니다.**

상태 레코드에 `locked_at` 컬럼을 추가합니다. 텍스트 타임스탬프로 두고 기존 행에는 `NULL`을 허용합니다.

`(status, locked_at)` 복합 인덱스를 생성합니다. `0008`에 인덱스가 하나도 없었던 문제를 반복하지 마십시오.

기존에 잠긴 채 남아 있는 행이 있다면 마이그레이션에서 어떻게 처리할지 명시하십시오. 일괄 해제할지, 그대로 두고 임대 만료 로직이 처리하게 할지는 조사 결과를 보고 판단합니다.

**코드 변경은 다음 세 가지입니다.**

`processing` 상태로 진입할 때 `locked_at`에 현재 시각을 기록합니다.

상태를 읽는 쪽에서 현재 시각과 `locked_at`의 차이가 임계치를 넘으면 잠금이 만료된 것으로 간주해 회수하고 재처리 가능 상태로 되돌립니다. 임계치 기본값은 30분이며 환경변수로 조정 가능해야 합니다.

`skipped_duplicate`가 남은 상태에서 같은 기준일을 다시 처리할 때 안전하게 통과하거나 명시적으로 실패해야 합니다. 조용히 무시되어서는 안 됩니다. 재처리 시도와 결과를 로그로 남기십시오.

**모니터링을 추가합니다.**

`monitor-market-daily-pipeline.yml`에 임계치를 넘긴 `processing` 레코드 존재 여부 검사를 추가하고, 존재하면 워크플로를 실패시키고 이슈를 생성하십시오. 이 워크플로는 이미 매일 실행되므로 추가 비용이 없습니다.

### 3-3. 완료 판정

인위적으로 `processing` 상태를 임계치 이상 남긴 뒤, 다음 파이프라인 실행이 잠금을 회수하고 정상 진행하는 것을 테스트로 확인하십시오.

경계 조건 테스트를 반드시 포함하십시오. 임계치 직전(29분)에는 회수되지 않고, 직후(31분)에는 회수되어야 합니다.

`skipped_duplicate` 상태에서 같은 기준일을 재처리했을 때 조용히 무시되지 않는 것을 확인하십시오.

노후 잠금이 있을 때 모니터 워크플로가 실패하는 것을 확인하십시오. Actions가 잠겨 있으면 로컬에서 해당 검사 로직만 실행해 확인하고, 워크플로 통합 검증은 한도 복구 후로 미루되 그 사실을 미검증으로 표기하십시오.

## 4. 이 작업이 갖는 의미

이 문제를 고치면 세 가지가 동시에 해결됩니다.

데이터가 조용히 누락되는 현상이 사라집니다. 자원 부족은 실행이 안 된 사실이 드러나지만, 잠금은 정상 종료된 것처럼 보이면서 데이터를 잃습니다.

`Backfill D1 ETF Prices`와 `Backfill ETF Price History`의 월 34회 수동 실행이 사라집니다. 이 실행들은 잠금 때문에 화면에 데이터가 반영되지 않아 강제 동기화를 반복한 결과로 보고된 바 있습니다.

앞의 두 가지 결과로 Actions 소모도 함께 줄어듭니다.

## 5. 작업 규칙

기존 파일을 통째로 다시 쓰지 말고 증분 편집만 하십시오. base64 재구성을 쓰지 마십시오.

완료 보고에 `git log --oneline -n 5`와 `git status --porcelain`을 함께 넣으십시오.

지시하지 않은 동작 변경을 하지 마십시오. 원본과 다르게 만들어야 할 이유가 있으면 먼저 질문하십시오.

모든 파일은 UTF-8로 저장하고 BOM이 없는지 검증하십시오.

확인한 사실과 추론을 구분하고, 검증하지 못한 항목은 완료가 아니라 미검증으로 표기하십시오. **검증 범위를 실제보다 넓게 표현하지 마십시오.**
