```

```

**거래일 다음날 새벽에 도는 것이 시점상 정확합니다.** 당일 마스터(08:07)와 당일 홀딩스(22:53)를 둘 다 본 뒤이고, 홀딩스 적재 실패 시 3시간 여유가 있습니다.

**정각을 피한 판단도 옳습니다.** 저장소의 다른 워크플로가 07분과 22분에 흩어져 있는 것과 일관됩니다.

## 2. 이슈 생성 조건을 좁히십시오

**매일 이슈를 만들면 며칠 만에 아무도 안 봅니다.**

### 2-1. 신규 탐지만 이슈로 올리십시오

**전일 실행 결과와 대조해 새로 나타난 종목이 있을 때만 이슈를 생성하십시오.**

**`0218J0` 처럼 드리프트가 계속 큰 종목이 매일 이슈를 만들면 안 됩니다.**

**전일 결과는 `holdings_audit_history.csv` 로는 부족합니다. 직전 탐지 종목 목록을 `data/reports/holdings_anomaly_last.json` 에 유지하고 이것만 커밋하십시오.** 종목 코드 목록이므로 가볍습니다.

### 2-2. 항목별 처리

```
항목 1  dominant 불일치      신규 탐지 시 이슈 생성        순수 오분류 후보
항목 2  설계 비중 괴리        이력에 기록만. 이슈 없음      시장 변동이 대부분
항목 3  안전자산 위험 초과     신규 탐지 시 이슈 생성        규제 영향
```

**항목 2는 이슈를 만들지 마십시오.** 오늘 확인했듯 20퍼센트포인트를 넘는 종목이 0건이었고, 넘더라도 대부분 정상 드리프트입니다. **이력에 최대값만 남기면 추이가 보입니다.**

### 2-3. 이슈 본문

**티커, 종목명, 현재 `asset_class`, 실측 최대 자산군과 비중, `unknown` 비중을 표로 넣으십시오.**

**제목에 날짜와 건수를 넣으십시오.** 예를 들어 `[홀딩스 감시] 2026-09-06 신규 이상 2건` 입니다.

**라벨을 하나 붙이십시오.** 나중에 필터링에 씁니다.

## 3. 스크립트를 정식화하십시오

**`scripts/rules/audit_holdings_composition.py` 를 신설하십시오.**

**`scratch/` 에 있는 전수 실행 스크립트를 옮겨 정리하는 것입니다. 워크플로가 `scratch/` 를 호출할 수 없습니다.**

### 3-1. 임계값을 상수로 두고 근거를 주석에 남기십시오

```python
DERIVATIVE_EXCLUSION_PCT = 20.0    # 일반 ETF 유동성 관리용 선물은 통상 10% 미만
CASH_MARGIN_PCT = 90.0             # 증거금 구조 판정. holdings_count <= 5 와 함께 적용
DOMINANT_THRESHOLD_PCT = 60.0      # 50% 경계 진동으로 인한 거짓 경보 차단
DRIFT_THRESHOLD_PCT = 25.0         # 2026-09-05 실측 최대 드리프트 14.49%p 를 여유 있게 포용
SAFE_ASSET_RISK_PCT = 70.0         # 감독규정 안전자산 요건을 명백히 벗어나는 수준
UNKNOWN_LIMIT_PCT = 10.0           # 실측 신뢰 하한
```

**`holdings_asset_classifier.py` 는 그대로 두고 import 하십시오.** 판정기와 감사 로직을 분리하십시오.

### 3-2. API 실패 처리

**동시 호출 8건을 유지하십시오.**

**실패한 종목은 건너뛰고 `api_failed` 에 세십시오.**

**실패율이 5퍼센트를 넘으면 그날 탐지 결과를 신뢰 불가로 표시하고 이슈를 만들지 마십시오.** 부분 데이터로 오탐을 내면 안 됩니다.

**전량 실패면 이슈를 만들되 내용은 "홀딩스 API 응답 없음" 입니다.**

### 3-3. 종료 코드

**항상 0 으로 종료하십시오.**

**탐지 결과가 워크플로를 실패시키면 안 됩니다.** 며칠 만에 무시하게 됩니다.

**스크립트 자체의 예외는 예외입니다.** 코드 오류나 파일 없음은 실패로 처리하십시오.

## 4. 워크플로

**`.github/workflows/holdings-audit.yml` 을 신설하십시오.**

```yaml
on:
  schedule:
    - cron: "17 17 * * 1-5"
  workflow_dispatch:
```

**`workflow_dispatch` 를 반드시 넣으십시오.** 수동 확인이 필요합니다.

**커밋 대상은 두 파일뿐입니다.**

```
data/reports/holdings_audit_history.csv
data/reports/holdings_anomaly_last.json
```

**커밋 메시지에 `[skip ci]` 를 넣으십시오.** CI 를 다시 돌릴 이유가 없습니다.

**`git add` 에 경로를 명시하십시오. `git add .` 을 쓰지 마십시오.**

**변경이 없으면 커밋하지 마십시오.** 빈 커밋이 쌓이면 안 됩니다.

**Node 버전은 `.node-version` 을 쓰십시오.** 어제 D1 적재 실패 원인이었습니다.

**타임아웃을 10분으로 두십시오.** 예상 실행 시간이 1분 20초이므로 충분하고, 무한 대기를 막습니다.

**구현 후 `workflow_dispatch` 로 한 번 수동 실행하십시오.**

**확인할 것입니다.**

```

holdings_audit_history.csv 에 한 행이 추가되었는지
탐지 0건이면 이슈가 생성되지 않는지
artifact 에 실측 CSV 가 올라갔는지
```

**탐지 0건일 것으로 예상합니다.** 오늘 전수 조사에서 항목 1은 6건을 수정했고 항목 2와 3은 0건이었습니다. **탐지가 나오면 오늘 수정이 반영되지 않았거나 로직에 문제가 있는 것입니다.**

**첫 실행은 `holdings_anomaly_last.json` 이 없으므로 모든 탐지가 신규로 잡힙니다. 첫 실행에서는 이슈를 만들지 말고 기준선만 저장하도록 하십시오.**
