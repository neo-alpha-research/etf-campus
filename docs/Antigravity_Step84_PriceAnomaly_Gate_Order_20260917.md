`python scripts/verify_split_adjustment.py` 실행 결과 일일 등락 40% 이상이 **29건** 검출됩니다. 그중 **22건이 2026-07-31 하루에 집중**되어 있습니다.

**KRX 일일 가격제한폭은 ±30%입니다. +46.76%, +60.00%는 정상 체결가로 발생할 수 없습니다.** 따라서 다음 둘 중 하나입니다.

- (A) 2026-07-31에 액면분할·병합 등 기업행위가 있었으나 원장에 등재되지 않음
- (B) 해당 일자의 수집 데이터가 잘못됨

**이미 서비스 수치를 오염시키고 있습니다.** `data/etf_returns_draft.csv` 기준 `122630`의 `r_3m = -51.03%` 인데 `r_6m = +26.23%` 입니다. 성립하려면 4~6개월 구간이 +157%여야 합니다. 시계열에서 직접 계산해도 3M −52.79% / 6M +21.22%로 동일하게 오염돼 있습니다. 즉 **차트와 표가 같은 값으로 함께 틀립니다.** 122630은 국내 거래대금 최상위 ETF이고, 2026-07-31은 3M·6M·1Y 조회 창에 모두 들어갑니다.

### 수행 항목

2. 각 종목·일자에 대해 **KRX 원천(Open API 또는 KIND 공시)** 을 재조회해 (A)인지 (B)인지 판정하십시오. 추측으로 분류하지 마십시오.
3. (A)로 판정된 건은 `data/corporate_actions/etf_corporate_actions.csv` 에 `action_type`, `effective_date`, `ratio_numerator/denominator`, `source_id`, `verification_status='official_verified'` 로 등재하십시오.

## STEP 2 — 캐시 버전 동적화

`components/compare/compare-client.tsx:126` 이 `?v=20260916` 을 **하드코딩**하고 있습니다. `public/data/series/v2/manifest.json` 은 생성만 되고 앱에서 읽히지 않습니다.

- 이대로면 내일 파이프라인이 돌아 파일이 바뀌어도 URL이 동일해, 엣지·브라우저 캐시가 옛 데이터를 계속 서빙합니다.
- 반대로 버전을 올릴 방법이 없으므로 `immutable` 장기 캐시도 걸 수 없습니다.

수정: 앱 기동 시 `/data/series/v2/manifest.json` 을 한 번 fetch해 `asOf` 를 받고, 각 종목 요청에 그 값을 붙이십시오(`manifest.tickers[ticker]` 가 있으면 종목별 값 우선). manifest 자체는 `no-cache` 또는 짧은 TTL로 두십시오.

**게이트**: manifest의 `asOf` 를 바꾼 뒤 요청 URL이 실제로 바뀌는지 확인하는 테스트 1건.

## STEP 3 — `filled` 생성

`scripts/generate_series_v2.py` 에 결측 탐지·LOCF 로직이 없어 `filled` 배열이 한 번도 생성되지 않습니다. 소비 측(`normalize-series.ts`, 차트)은 이 필드를 읽도록 구현돼 있습니다.

- 런타임 `normalizeMulti` 가 합집합 달력 기준으로 `isFilled` 를 자체 계산하므로 점선 표시 자체는 동작합니다. 다만 **원천 단계의 결측(거래정지 등)** 은 여전히 표시되지 않습니다.
- 생성기에서 KRX 거래일 달력 대비 누락일을 찾아 LOCF로 채우고 그 인덱스를 `filled` 에 기록하거나, 채우지 않기로 결정했다면 **데이터 계약 문서와 타입에서 `filled` 를 제거**하십시오. 둘 중 하나로 정리하고 어느 쪽을 택했는지 보고하십시오.
