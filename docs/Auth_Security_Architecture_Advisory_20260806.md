# 커뮤니티 인증·보안 아키텍처 자문 (1인 운영 / Next.js 16)

작성일 2026-08-06 · 대상: 운영자 의사결정 + 구현 에이전트
전제: 30일 챌린지 커뮤니티. 기존 ETF캠퍼스 본체는 `output: "export"` 정적 사이트(Cloudflare Pages).

> 면책: 본 문서는 아키텍처·실무 관점의 정리이며 법률 자문이 아닙니다. 개인정보 처리방침·국외이전 고지 문안과 신고 의무 판단은 공개 전 변호사 검토를 받으십시오.

---

## 0. 결론

**Supabase를 채택하십시오.** 근거는 취향이 아니라 아래 3가지 구조적 사실입니다.

1. **어차피 DB가 필요합니다.** 게시글·인증 제출·완주율·배지·신고 이력은 전부 저장이 필요합니다. Clerk은 인증 전용이므로 Clerk을 골라도 DB를 따로 붙여야 하고, 그때 **Clerk JWT를 DB의 RLS에 연동하는 작업이 추가로 발생**합니다. 1인 운영에서 벤더를 둘로 늘리는 것은 비용이 아니라 장애 지점을 늘리는 선택입니다.
2. **카카오 로그인이 기본 제공됩니다.** Supabase Auth는 `signInWithOAuth({ provider: 'kakao' })`로 카카오를 공식 지원합니다. Clerk은 사전 제공 목록에 카카오가 없어 **커스텀 OIDC로 직접 구성**해야 합니다(플랜별 제약 여부는 대시보드에서 확인 필요). 국내 서비스에서 카카오는 선택이 아니라 사실상 필수입니다.
3. **서울 리전(ap-northeast-2)을 선택하면 개인정보 국외이전 이슈를 원천 회피합니다.** 이 항목은 §4-2에서 따로 다루며, 1인 운영자에게는 실무 부담 차이가 가장 큰 항목입니다.

무료 한도는 두 서비스가 사실상 대등합니다(둘 다 5만 MAU급). 따라서 무료 한도는 판단 근거가 되지 못하며, 위 3가지가 결정합니다.

## 1. 먼저 해결해야 할 선행 문제 — 현재 아키텍처와 정면 충돌

제안하신 4번 항목("Server Actions / Route Handlers 내부에서만 DB 접근")은 원칙적으로 정확합니다. 다만 **현재 ETF캠퍼스 본체에서는 그 코드가 아예 동작하지 않습니다.**

`next.config.ts`가 `output: "export"`입니다. 정적 export 빌드에는 서버 런타임이 없으므로 **Server Actions·Route Handlers·미들웨어가 존재하지 않습니다.** 인증 세션 검증, 서버 측 린터 재검증, DB 쓰기를 넣을 자리가 현재 프로젝트에는 없습니다.

### 권장: 배포 대상 분리 (본체는 정적 유지)

```
etf-campus.pages.dev        ← 기존 정적 사이트. 그대로 유지 (SEO·비용 0·빌드 안정)
community.<도메인>          ← 신규 Next.js 앱. SSR 런타임 필요 (Server Actions 사용)
```

- 본체를 SSR로 전환하면 1,150여 개 ETF 상세 페이지의 정적 생성 이점과 현재의 0원 운영이 함께 무너집니다. **본체는 건드리지 마십시오.**
- 커뮤니티는 별도 저장소·별도 배포로 시작하는 편이 롤백도 쉽고 장애 격리도 됩니다.
- 배포처 선택: Cloudflare Pages에서 Next.js SSR을 돌리려면 `@opennextjs/cloudflare` 어댑터가 필요합니다. **초기에는 Vercel 무료 티어로 커뮤니티만 배포하는 편이 마찰이 적습니다.** 두 서비스가 서로 다른 호스팅에 있어도 서브도메인으로 묶으면 사용자 경험상 문제 없습니다.
- 세션 쿠키를 공유하려면 두 앱이 같은 상위 도메인(`*.etfcampus.kr`)이어야 합니다. 도메인 확정 전이라면 커뮤니티는 독립 로그인으로 시작하십시오.

## 2. Clerk vs Supabase 비교 (판단 근거)

| 항목 | Clerk | Supabase |
|---|---|---|
| 무료 한도 | 5만 MRU (2026-02-05 상향), Pro $25/mo | 5만 MAU, DB 500MB, 스토리지 1GB, 대역폭 5GB, 프로젝트 2개 |
| DB 포함 | ❌ 별도 필요 | ✅ PostgreSQL 포함 |
| 카카오 로그인 | 사전 제공 없음 → 커스텀 OIDC 구성 | ✅ 공식 지원 |
| RLS 연동 | 외부 DB에 JWT 수동 연동 필요 | ✅ `auth.uid()` 네이티브 |
| 파일 스토리지 | ❌ | ✅ Storage + RLS (인증 캡처 이미지에 필요) |
| 데이터 소재지 | 리전 선택 제약 | ✅ 서울 리전 선택 가능 |
| UI 컴포넌트 | ✅ 완성도 높음 (`<SignIn/>` 즉시 사용) | 기본 UI 빈약, 직접 구현 |
| MFA·봇 방어 | ✅ 기본 탑재 | 일부는 직접 구성 |
| 치명적 제약 | — | **7일간 DB 쿼리가 없으면 프로젝트 자동 일시정지** |

### Supabase의 유일한 실질 단점과 해결책

무료 티어는 7일간 DB 활동이 없으면 프로젝트가 일시정지되고, 복구 전까지 접속이 불가능합니다. 챌린지 기수 사이의 공백기에 정확히 이 상황이 발생합니다.

**해결책은 이미 갖고 계십니다.** `.github/workflows/daily-data.yml`이 매일 실행되고 있으므로, 여기에 Supabase 헬스체크 테이블에 1행 upsert 하는 스텝 한 줄만 추가하면 정지되지 않습니다. 별도 크론이 필요 없습니다.

```yaml
- name: Keep Supabase project awake
  run: |
    curl -s -X POST "$SUPABASE_URL/rest/v1/heartbeat" \
      -H "apikey: $SUPABASE_SERVICE_ROLE_KEY" \
      -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY" \
      -H "Content-Type: application/json" \
      -d '{"id":1,"pinged_at":"'"$(date -u +%FT%TZ)"'"}' \
      -H "Prefer: resolution=merge-duplicates"
  env:
    SUPABASE_URL: ${{ secrets.SUPABASE_URL }}
    SUPABASE_SERVICE_ROLE_KEY: ${{ secrets.SUPABASE_SERVICE_ROLE_KEY }}
```

실사용자가 생기면 Pro($25/mo)로 올려 일시정지를 완전히 제거하십시오. 유료 챌린지라면 참가자 1명분 참가비로 회수되는 금액입니다.

### 하이브리드(Clerk 인증 + Supabase DB)를 권하지 않는 이유

기술적으로 가능하지만 Clerk JWT를 Supabase RLS가 신뢰하도록 JWKS·클레임 매핑을 직접 구성해야 합니다. **RLS 정책의 오설정은 곧 데이터 유출이며, 이 배선이 늘어날수록 1인 운영자가 검증하기 어려워집니다.** 벤더를 하나로 유지하십시오.

## 3. 제안하신 4단계 전략 검증

### ✅ 그대로 유지할 것

- **자체 비밀번호 DB 배제 / 소셜 로그인 전용** — 정확합니다. 비밀번호를 보관하지 않으면 유출 사고의 최대 범주가 사라집니다.
- **수집 항목을 이메일 + UID로 제한** — 방향 정확합니다(단 §4-1 함정 확인).
- **RLS 강제** — 필수입니다. 다만 "정책 작성"만으로는 부족하며 §5 체크리스트를 반드시 통과시키십시오.
- **`NEXT_PUBLIC_` 접두사 분리** — 정확합니다. 특히 Supabase의 `service_role` 키는 **RLS를 전부 우회하는 마스터 키**이므로 클라이언트 번들에 절대 들어가면 안 됩니다.
- **DB 접근을 서버에 캡슐화** — 원칙은 맞으나 §1의 선행 문제를 먼저 해결해야 실행 가능합니다.

### ⚠️ 보완이 필요한 것

**(1) "익명성 보장 = 닉네임만 사용"은 자동으로 되지 않습니다.**
Google·Kakao OAuth는 기본적으로 **실명과 프로필 사진을 함께 반환**합니다. 아무 처리도 하지 않으면 실명이 DB에 그대로 적재됩니다. 가입 콜백에서 `full_name`·`avatar_url`을 **명시적으로 버리고** 닉네임 설정 화면으로 강제 이동시키는 로직이 필요합니다. 실명 미수집은 선언이 아니라 구현 사항입니다.

**(2) MFA는 일반 회원이 아니라 운영자 계정에 적용하십시오.**
1인 운영에서 최대 단일 장애점은 **운영자 계정 탈취**입니다. 탈취되면 전 회원 데이터에 접근 가능합니다.
- 운영자 계정 MFA 필수
- Supabase 대시보드 계정·GitHub 계정에도 MFA
- **일반 이용용 계정과 관리자 계정을 분리**(관리자 권한을 평소 쓰는 계정에 부여하지 않음)

**(3) 서버 캡슐화의 진짜 목적은 "로직 유출 방지"가 아니라 "권한 검증"입니다.**
비즈니스 로직 은닉은 부차적입니다. 핵심은 **클라이언트가 보낸 값을 절대 신뢰하지 않는 것**입니다. 특히 이전 설계서(`Community_Board_Compliance_UX_Spec_20260806.md`)의 컴플라이언스 린터는 클라이언트 검사만으로는 개발자도구로 우회됩니다. **동일 규칙을 서버에서 재실행**해야 합니다.

## 4. 제안에서 누락된 리스크

### 4-1. 카카오 이메일 함정 (설계 전제를 무너뜨림)

카카오 OAuth의 `account_email` 수집은 **비즈니스 채널 등록·검수를 마친 앱에만 허용**되며, 그마저도 사용자가 선택 동의를 거부할 수 있습니다. 즉 **"이메일 + UID"라는 최소 수집 전제가 카카오에서는 성립하지 않을 수 있습니다.**

선택지 2개 — 착수 전 결정하십시오.

| 선택 | 내용 | 영향 |
|---|---|---|
| A. 이메일 없이 운영 (권장) | Supabase 카카오 설정의 "이메일 없는 사용자 허용" 활성화. 식별자는 UID만, 연락 수단은 사이트 내 알림으로 대체 | 개인정보 수집량 최소 = 리스크 최소. 단 **이메일 리마인드 발송 불가** → §2-5 이탈 리마인드 기능 재설계 필요 |
| B. 카카오 비즈니스 채널 검수 | 사업자 정보 등록 후 이메일 수집 권한 획득 | 리마인드·뉴스레터 연계 가능. 검수 기간과 사업자 요건 필요 |

**챌린지 운영에 이메일 리마인드가 핵심 장치라면 B가 사실상 강제됩니다.** 이 판단이 §2-5 기능 설계를 좌우하므로 먼저 확정하십시오.

### 4-2. 개인정보 국외이전 (Supabase 서울 리전을 반드시 선택할 것)

이메일은 개인정보이며, 해외 리전에 저장하면 **국외이전**에 해당해 처리방침 공개·고지 등 추가 요건이 발생합니다. 프로젝트 생성 시 리전을 **Seoul (ap-northeast-2)로 지정**하면 이 문제 대부분을 회피합니다.

**주의: 리전은 프로젝트 생성 시점에만 정할 수 있고 이후 변경이 사실상 불가능합니다.** 잘못 만들면 전체 마이그레이션이 필요하니 최초 클릭에서 확인하십시오.

다만 관리 콘솔·지원 인력 접근 등으로 완전한 국내 한정이 되지는 않으므로, 처리방침에는 **수탁·이전 사실을 성실히 기재**하십시오.

### 4-3. 개인정보보호법 실무 의무 (1인 운영도 예외 아님)

- **개인정보 처리방침 수립·공개**: 수집 항목, 목적, 보유기간, 파기 절차, 수탁사(Supabase 등), 국외이전 여부를 기재해 상시 접근 가능한 위치에 게시
- **회원 탈퇴 = 실제 삭제**: `deleted_at` 소프트 삭제만으로는 부족합니다. 탈퇴 시 계정·게시물·업로드 이미지의 실제 파기 흐름을 구현하고, 커뮤니티 유지가 필요한 게시물은 **작성자 식별정보를 분리(익명화)** 하는 방식으로 처리
- **접속기록 보관**: 개인정보처리시스템 접속기록은 1년 이상 보관 요건이 있습니다. Supabase 무료 티어의 로그 보존은 7일이므로, **관리자 열람·처분 기록만이라도 자체 테이블(`admin_audit_log`)에 남기십시오.** 이전 설계서 §1-9의 감사 로그가 여기에 그대로 대응됩니다.
- **유출 사고 대응**: 유출 인지 시 72시간 내 통지·신고 요건이 있습니다. 사고 발생 후 절차를 찾기 시작하면 늦으므로, 1페이지짜리 대응 절차 문서를 미리 만들어 두십시오.

### 4-4. 이미지 업로드 보안 (인증 캡처 = 최고 위험 자산)

계좌 캡처는 계좌번호·평가금액이 담긴 **가장 민감한 데이터**입니다.

- 버킷을 **private**으로 두고, 조회는 짧은 만료(예: 5분)의 **signed URL**로만 제공. public 버킷 금지
- Storage RLS: 업로드 경로를 `submissions/{auth.uid()}/...`로 강제하고 타인 경로 쓰기 차단
- **클라이언트가 보낸 MIME 타입을 신뢰하지 마십시오.** 서버에서 매직 넘버 검증 + 이미지 재인코딩(EXIF·위치정보 제거 겸용) + 용량·해상도 상한
- 마스킹은 클라이언트 canvas 결과만 업로드(원본 미전송)하되, **서버는 그것이 마스킹되었는지 알 수 없다**는 점을 인지하고 §2-3 관리자 큐에서 이미지 포함 건은 항상 `REVIEW`로 두십시오

### 4-5. 봇 가입·스팸 방어

소셜 로그인만 허용해도 자동 가입은 가능합니다. 1인 운영에서 스팸이 유입되면 대응이 불가능합니다.

- **Cloudflare Turnstile**(무료)을 가입·글쓰기에 적용. 이미 Cloudflare를 쓰고 계셔서 궁합이 좋습니다
- 서버 측 rate limit: 신규 계정 24시간 내 글쓰기 N건 제한, 동일 IP 가입 제한
- 가입 후 일정 시간(예: 1시간) 경과 전 외부 링크 포함 글 작성 금지

### 4-6. 백업

무료 티어의 백업 보장은 제한적입니다. **주 1회 `pg_dump`를 GitHub Actions로 실행해 비공개 저장소나 오브젝트 스토리지에 보관**하십시오. 단, 백업 파일 자체가 개인정보 사본이므로 보관 위치의 접근 통제와 보유기간(예: 4주 롤링)을 함께 정하십시오.

## 5. RLS 실전 체크리스트 (여기서 사고가 납니다)

정책을 작성했다는 사실과 안전하다는 사실은 다릅니다. 배포 전 아래를 실제로 시험하십시오.

- [ ] **모든 테이블에 `ENABLE ROW LEVEL SECURITY`가 켜져 있는가** — 새 테이블을 추가하고 RLS 활성화를 잊는 것이 가장 흔한 사고입니다
- [ ] RLS를 켰지만 정책이 하나도 없는 테이블은 없는가(전면 차단되어 기능이 조용히 죽습니다)
- [ ] `SELECT`뿐 아니라 **`INSERT`/`UPDATE`/`DELETE` 각각에 정책이 있는가**
- [ ] `INSERT` 정책에 `WITH CHECK (auth.uid() = user_id)`가 있는가 — 없으면 **타인 명의로 글 작성이 가능**합니다
- [ ] `UPDATE` 정책에 `USING`과 `WITH CHECK`가 **둘 다** 있는가 — `USING`만 있으면 자기 글을 타인 소유로 바꿔치기할 수 있습니다
- [ ] 게시물 테이블에 이메일·UID 등 식별정보 컬럼이 섞여 있지 않은가(프로필 테이블로 분리하고 공개 뷰에서 제외)
- [ ] `service_role` 키가 클라이언트 번들·저장소·로그에 없는가 (`grep -r "service_role" .` 및 빌드 산출물 검사)
- [ ] 블라인드 처리된 게시물이 **API 직접 호출로 조회되지 않는가** (화면에서만 가리면 무의미)
- [ ] 관리자 판별을 클라이언트 상태가 아니라 **DB의 역할 컬럼 + 정책**으로 하고 있는가
- [ ] 실제 검증: 회원 A의 토큰으로 회원 B의 row `UPDATE`/`DELETE`를 시도해 **실패하는 것을 눈으로 확인**했는가

마지막 항목은 반드시 수동으로라도 시험하십시오. RLS는 "작성했으니 됐다"가 통하지 않는 영역입니다.
