## 0. 당신이 해야 할 일

본 문서는 구현 지시가 아니라 **구현 프롬프트를 만들기 위한 입력**입니다. Phase 0부터 Phase 7까지 순차 프롬프트를 작성하되, 각 프롬프트에는 수정 대상 파일의 정확한 경로, 유지해야 할 기존 계약, 새로 추가할 필드와 화면, 완료 판정 기준, 그리고 §12의 작업 규칙이 반드시 포함되어야 합니다.

Phase 7(결제·환급)은 운영자 결정과 법률 검토 이후에 착수하므로 프롬프트만 준비하고 실행 지시는 보류하십시오.

## 1. 전체 그림

이번 작업은 30일 챌린지 기능 하나가 아니라 **커뮤니티를 개설하고 운영 가능한 상태로 만드는 전체 범위**입니다. 순서는 다음과 같습니다.

```
Phase 0  기반 정리        인코딩 복구, 잔재 제거, 스키마 현황 확인
Phase 1  공지·고정 체계    notice 카테고리, 고정 게시물, 시드 등록 도구
Phase 2  콘텐츠 시딩       저자 완주 기록 30건, 공지, Q&A 초기 답변
Phase 3  리드마그넷·뉴스레터  이메일 수집과 온보딩 시퀀스
Phase 4  기수·참가자        cohort와 participant 관리
Phase 5  기록 게시판        challenge-30 작성 폼과 목록
```

Phase 2가 Phase 3보다 먼저인 이유는 명확합니다. 리드마그넷으로 사람을 불러들였을 때 커뮤니티가 비어 있으면 그 유입이 전부 낭비됩니다. 콘텐츠가 먼저 있어야 합니다.

## 2. Phase 0: 기반 정리 (최우선, 다른 작업 전에 반드시 완료)

### 2-1. 커뮤니티 API 파일 6개의 인코딩이 손상되어 있습니다

아래 파일들이 UTF-8로 디코딩되지 않습니다. 사용자에게 나가는 한글 에러 메시지가 깨진 상태로 전송되고 있을 가능성이 높습니다.

```
functions/api/community/auth/account.js
functions/api/community/auth/config.js
functions/api/community/auth/profile.js
functions/api/community/posts/index.js
functions/api/community/posts/[slug]/comments.js
functions/api/community/posts/[slug]/comments/[commentId].js
```

실제 확인된 손상 예시입니다. `posts/index.js`의 에러 메시지가 다음과 같습니다.

```js
return errorResponse(503, "UNAVAILABLE", "커�??�티 글??불러?????�습?�다.");
```

원래 문구는 "커뮤니티 글을 불러올 수 없습니다"였을 것으로 보입니다. 같은 파일에 이런 문자열이 3건, 다른 파일에도 다수 존재합니다.

**복구 방법.** 각 파일의 바이트를 cp949로 디코딩해 원문이 복원되는지 확인한 뒤 UTF-8로 재저장하십시오. cp949로도 복원되지 않으면 이중 인코딩된 경우이므로, 해당 문자열만 원문 의미에 맞게 수동으로 다시 작성하십시오. 코드 로직은 건드리지 말고 문자열만 복구해야 합니다.

**복구 후 검증.** 모든 대상 파일에 대해 UTF-8 디코딩이 성공하고 U+FFFD가 0건인지 확인하십시오. 이 검증을 완료 보고에 포함해야 합니다.

**재발 방지.** 저장소 전체를 대상으로 UTF-8 검증을 수행하는 스크립트를 `scripts/`에 추가하고 CI에서 실행하십시오. 이 프로젝트는 한글 문자열이 코드 곳곳에 있으므로 인코딩 회귀가 반복될 수 있습니다.

### 2-2. 저장소 잔재를 제거하십시오

루트의 `temp.json`, 그리고 지난 작업에서 남은 `functions/api/briefings/latest.js.tmp`를 삭제하십시오. 작업 후 `git status`에 추적되지 않는 파일이 남아 있으면 안 됩니다.

### 2-3. 완료 판정

대상 6개 파일이 UTF-8로 정상 디코딩되고, 에러 메시지 한글이 사람이 읽을 수 있는 상태이며, 잔재 파일이 제거되었고, UTF-8 검증 스크립트가 CI에서 동작하면 완료입니다.

## 3. 저장소 아키텍처 (착수 전 필수 확인)

이 프로젝트는 저장소가 두 개로 나뉘어 있습니다. 잘못 선택하면 조인이 불가능해집니다.

| 도메인 | 저장소 | 근거 |
|---|---|---|
| 커뮤니티 회원·게시글·댓글 | **Supabase (Postgres)** | `posts/index.js`가 `community_public_posts` 뷰와 `create_community_post` RPC를 호출 |
| ETF 가격·브리핑·관리자 인증 | **D1 (SQLite)** | `migrations/0001~0008`, `admin_users` 등 |

따라서 **기수, 참가자, 챌린지 기록 게시물, 판정 결과는 전부 Supabase에 두어야 합니다.** v2 문서에서 "D1 마이그레이션 0009"라고 지시한 부분은 오류이니 폐기하십시오.

게시글 생성이 `create_community_post(p_category_slug, p_title, p_body_text)` RPC를 경유하므로, 구조화 필드를 추가하려면 **Postgres 함수 자체를 수정**해야 합니다. 프런트엔드나 Workers 코드만 고쳐서는 필드가 저장되지 않습니다. 이 점을 Phase 5 프롬프트에 명시하십시오.

착수 전에 Supabase 쪽 현재 스키마(`community_posts` 원본 테이블, `community_public_posts` 뷰, `create_community_post` 함수 정의)를 조회해 실제 컬럼 구성을 확인하고, 그 결과를 근거로 확장 설계를 확정하십시오. 추측으로 진행하지 마십시오.

## 4. Phase 1: 공지·고정 체계와 시드 등록 도구

### 4-1. 현재 없는 기능

카테고리는 `pension-etf-qna`, `etf-questions`, `challenge-30`, `feedback` 네 개뿐이며 **공지 카테고리가 없습니다.** 기수 모집 공고와 게시판 규칙을 올릴 자리가 없다는 뜻입니다.

목록 정렬도 `created_at` 내림차순으로 고정되어 있고 고정 게시물 개념이 없습니다. 규칙 안내가 하루 만에 아래로 밀려 내려갑니다.

### 4-2. 추가할 것

**`notice` 카테고리를 추가합니다.** 작성 권한은 `moderator`와 `admin` 역할로 제한합니다. 역할 체계는 이미 `contracts.ts`에 정의되어 있으므로(`guest | member | moderator | admin`) 재사용하십시오.

**고정 게시물 기능을 추가합니다.** 게시물에 `is_pinned` 플래그를 두고, 목록 조회 시 고정 게시물을 상단에 먼저 정렬한 뒤 나머지를 최신순으로 정렬합니다. 고정 설정은 moderator 이상만 가능합니다.

고정은 카테고리별로 최대 3건까지만 허용하십시오. 상한이 없으면 목록 상단이 공지로 가득 차 실제 게시물이 밀립니다.

**저자 시드 게시물 구분 표시를 추가합니다.** `challenge-30`에 운영자가 올릴 완주 기록은 실제 참가자 기록과 시각적으로 구분되어야 합니다. `is_author_seed` 플래그를 두고 목록과 상세에서 "저자 기록" 배지를 표시하십시오. 이 게시물은 기수 진행률이나 완주 판정 집계에서 제외되어야 합니다.

**시드 일괄 등록 도구를 만듭니다.** 30건을 관리자 화면에서 하나씩 입력하는 것은 비효율적입니다. 마크다운 파일 묶음을 읽어 게시물로 등록하는 스크립트를 `scripts/`에 두십시오. 파일명 규칙으로 Day 번호를 판별하고, 프런트매터로 제목과 숫자 값을 받는 방식이면 충분합니다.

### 4-3. 완료 판정

`notice` 카테고리에 moderator 권한으로 글을 쓸 수 있고, 고정 게시물이 목록 최상단에 노출되며, 저자 시드 배지가 표시되고 집계에서 제외되며, 일괄 등록 스크립트가 동작하면 완료입니다.

## 5. Phase 2: 콘텐츠 시딩 (커뮤니티 개설의 핵심)

### 5-1. 왜 필요한가

커뮤니티 실패의 가장 흔한 원인은 기능 부족이 아니라 **첫 방문자가 본 빈 화면**입니다. 게시물이 0건인 게시판을 본 사람은 다시 오지 않습니다. 1기 챌린지가 시작되기 전에 이미 읽을 것이 있어야 합니다.

이 작업은 코드가 아니라 콘텐츠 생산이므로 운영자 작업이 대부분입니다. 다만 등록 도구와 화면 구성은 개발 범위이므로 프롬프트에 포함하십시오.

### 5-2. 시드 콘텐츠 4종

**1. 저자 완주 기록 30건 (`challenge-30`, 최우선)**

저자 Neo가 30일 과제를 먼저 완주한 기록입니다. 이것이 시딩의 핵심입니다. 효과가 세 가지입니다. 빈 게시판 문제가 해결되고, 각 Day의 작성 예시가 placeholder 문구가 아니라 실물 게시물로 존재하게 되며, "저자가 먼저 해봤다"는 신뢰가 생깁니다.

생산 부담은 크지 않습니다. 전자책 본문에 각 Day의 서사와 실제 계좌 경험이 이미 서술되어 있으므로, 새로 쓰는 것이 아니라 발췌하고 기록 형식으로 재구성하는 작업입니다.

**주의 사항이 있습니다.** 브랜드 고정 수치는 그대로 사용하되 새로운 수치를 만들어내면 안 됩니다. 계좌수익률 최고점 +21.31%(2021년 3월), 저점 -25.38%(2022년 6월 30일), DB형에서 DC형 전환 시점 2017년 하반기가 확정 수치입니다. 계좌수익률에 "연간"이라는 수식어를 붙이지 마십시오. 그 외 구체적 수치가 필요하면 운영자에게 확인하십시오.

**2. 게시판 공지 3건 (`notice`, 고정)**

기수 모집 공고, 게시판 이용 규칙, 30일 챌린지 진행 방식 안내입니다. 이용 규칙에는 지난 설계에서 정한 발언 제한(특정 종목 매수 매도 권유 금지, 수익률 자랑성 게시 금지, 실시간 시황 단정 금지)과 판정 범위 고지(제출 여부와 형식만 확인하며 내용의 옳고 그름은 평가하지 않음)를 포함하십시오.

**3. 운영자 답변형 Q&A 초기 10건 (`pension-etf-qna`)**

질문만 쌓이고 답변이 없는 게시판이 커뮤니티 인상에 가장 치명적입니다. 개설 시점에 이미 답변된 질문 10건이 있으면 게시판이 살아 있다는 신호가 됩니다.

질문 소재는 전자책의 "독자의 질문" 섹션과 30일 과제에서 자연스럽게 파생됩니다. DC형과 DB형의 차이, 디폴트옵션이 무엇인지, IRP 계좌 수수료 확인 방법 같은 실무 질문이 적합합니다.

세법 해석이 필요한 질문에는 일반적 제도 설명까지만 하고 개별 사안은 세무 전문가 상담을 안내하는 정형 문구를 두십시오.

**4. ETF 기초 질문 시드 5건 (`etf-questions`)**

총보수와 실부담비용의 차이, 괴리율이 무엇인지, 환헤지형과 환노출형의 차이 같은 개념 질문입니다. 이 카테고리는 검색 유입 자산으로도 기능합니다.

### 5-3. 시드 콘텐츠 공개 일정

전부 한 번에 올리지 말고 모집 기간에 나누어 공개하십시오. 매일 새 글이 올라오는 게시판으로 보이는 것이 중요합니다.

| 시점 | 공개 내용 |
|---|---|
| D-14 | 공지 3건 고정, Q&A 10건, ETF 질문 5건 |
| D-13 ~ D-1 | 저자 완주 기록 30건을 하루 2~3건씩 순차 공개 |
| D-Day | 1기 시작, 참가자 기록 시작 |

이 일정은 운영 지침이므로 개발 범위는 "예약 발행" 기능 여부만 결정하면 됩니다. 1기 규모에서는 예약 발행 없이 운영자가 수동으로 올려도 무방합니다. 과설계를 피하십시오.

### 5-4. 시딩 이후의 상시 운영 리듬

기수 진행 중에는 주 1회 운영자 회고를 `notice`에 올리고, `pension-etf-qna`에 주 1회 답변을 답니다. 이 리듬만 지켜도 게시판이 죽지 않습니다. 이는 운영 지침이며 개발 범위가 아닙니다.

## 8. Phase 5: 기록 게시판

### 8-1. 목록 페이지

**30칸 상태 그리드.** Day 1부터 30까지를 격자로 표시하고 각 칸을 달성·지각 달성·미달성·예정 네 상태로 표시합니다. 민원 방지의 핵심 장치입니다.

**기수 진행 스트립.** 같은 기수 참가자의 오늘 제출 현황을 점으로 압축 표시합니다. 제출자는 채워진 점, 미제출자는 빈 점이며 닉네임은 표시하지 않습니다.

**필터 칩.** 전체, 내 기수, 오늘의 Day, 저자 기록, 내 글 다섯 개를 둡니다. 인기순과 추천순은 만들지 않습니다.

```
[Day 12]  닉네임 · 40대 · 연속 8일                       2시간 전
오늘 확인한 원리금보장 비중은 62%였습니다. 생각보다 높아서...
                                              댓글 3   응원 5
```

핵심 원칙은 **필수 입력 2개, 나머지 전부 선택**입니다.

**Day (자동 채움, 수정 가능).** 기수 시작일과 오늘 날짜로 자동 계산합니다. 마감이 지난 Day는 선택 시 "마감된 날짜입니다"로 안내하고 달성으로 집계하지 않습니다.

**오늘의 과제 (읽기 전용 카드).** 선택된 Day의 과제 문구를 표시합니다. 과제 원문 30건은 `D:\Pension_ETF\Reports\30일_챌린지_인증과제_설계제안_20260806.md` §3이 단일 진실이며 임의로 각색하지 마십시오. 백지 공포를 제거하는 핵심 장치이므로 접거나 숨기지 마십시오.

**본문 (필수, 30~1000자).** placeholder에 해당 Day의 작성 예시를 넣습니다. Phase 2의 저자 완주 기록이 있으면 "저자 기록 보기" 링크를 함께 두십시오. 실물 예시가 가장 강력한 템플릿입니다.

**하단 고정 바.** 좌측에 진행 표시와 마감 카운트다운, 우측에 제출 버튼을 둡니다. 모바일에서 키보드가 올라와도 가려지지 않게 고정합니다.

**제출 전 자동 점검.** 금칙 표현이 있으면 차단합니다. 절대금액 패턴(만원·억 단위)이 있으면 차단하지 않되 "금액 대신 비율로 적어 주시면 더 안전합니다"를 한 번 노출합니다. 직전 기록과 본문이 완전히 동일하면 반려합니다. 서버에서도 동일 검사를 수행합니다.

**반복 작성 마찰 제거.** 두 번째 게시물부터는 지난 선택 입력값을 기본값으로 불러옵니다. 작성 화면 진입 시 Day와 과제가 이미 채워져 있어야 합니다.

## 9. 컴플라이언스와 용어 규칙 (전 Phase 공통)

### 9-1. 절대 위반 금지 5개

첫째, **절대금액을 어떤 필드에서도 입력받지 않습니다.** 평가금액, 매수금액, 분배금액 모두 금지하며 비율만 받습니다.

둘째, **개별 종목명을 구조화 필드로 받지 않습니다.** 본문 자유 서술은 허용하되 집계·정렬·랭킹 대상 필드에는 종목이 들어가면 안 됩니다. 집계 가능한 순간 추천 목록이 됩니다.

셋째, **인기순 정렬과 추천 게시물 기능을 만들지 않습니다.** 정렬은 고정 게시물 우선, 그다음 최신순입니다.

넷째, **`metric_key`는 사전 정의된 화이트리스트만 허용합니다.**

다섯째, **금칙 표현 검사를 클라이언트와 서버 양쪽에 둡니다.**

### 9-2. 용어 규칙

화면 어디에도 "인증"을 쓰지 않고 **"기록"으로 통일**합니다. 목록 상단에 다음을 고정 노출하십시오.

> 게시물의 수치는 작성자 본인이 입력한 값이며 서비스가 검증하지 않습니다.

### 9-3. 비교 축 규칙

노출 허용 지표는 연속 기록일수, 이번 달 기록 횟수, 기수 내 진행률 세 가지뿐입니다. 프로필 뱃지는 회원 300명 미만 구간에서 **연령대 10년 단위만** 노출하고, 업종은 재식별 위험 때문에 300명 이후로 미룹니다. 자산 규모 관련 뱃지는 어느 단계에서도 만들지 않습니다.

### 9-4. 미완성 도서 안내 문구 (신청 화면과 보상 안내에 고정)

> 2편과 3편은 현재 집필 중이며 출간 시기가 확정되지 않았습니다. 출간 시점에 완주자에게 무료로 제공되며, 신청 시 이 점에 동의한 것으로 봅니다.

## 10. Phase 6: 자동 판정 배치와 관리자 화면

### 10-1. 우리 설계의 구조적 이점

스크린샷 업로드를 받지 않으므로 사진 메타데이터 조작 위험이 존재하지 않습니다. 판정 대상이 구조화된 게시글이라 전부 기계적으로 결정 가능합니다.

### 10-2. 달성 판정 조건 (전부 AND)

1. 서버 시간 기준 해당 Day의 마감 시각 이전에 작성되었을 것
2. `day_number`가 유효 범위이고 참가자의 기수 일정과 정합할 것
3. `body_text`가 최소 글자수(30자)를 충족할 것
4. 해당 Day에 숫자 과제가 정의되어 있으면 `metric_value`가 입력되어 있고 허용 범위 안일 것
5. 금칙 표현을 포함하지 않을 것
6. 같은 Day에 이미 인정된 기록이 없을 것
7. `is_author_seed`가 false일 것

### 10-3. 시간 판정 규칙

**클라이언트 시간을 절대 신뢰하지 마십시오.** `created_at`은 서버가 기록하고 KST 변환은 판정 시점에 서버에서 수행합니다.

- 정시 제출: 해당 Day 당일 KST 23:59:59까지
- 지각 제출: 익일 KST 12:00:00까지, 달성으로 인정하되 지각 표시
- 그 이후: 미달성 확정, 소급 불가

**확정 시각은 매일 12:05 KST이며 일 1회 배치로 판정합니다.** 확정 결과는 변경 불가 로그로 저장하고 판정 시각, 규칙 버전, 제출 시각, 마감 시각을 함께 기록합니다.

### 10-4. 어뷰징 방어

**동일 내용 반복 제출**은 직전 기록과의 본문 유사도를 검사합니다. 공백과 문장부호를 제거해 정규화한 뒤 완전 일치면 반려하고, 유사도가 임계치를 넘으면 경고 후 재작성을 요구합니다.

**몰아쓰기**는 Day별 독립 마감으로 자동 차단됩니다.

**대리 작성**은 검증 불가능하므로 약관에 금지 사항으로 명시하고 적발 시 처리 기준만 두십시오. 검증하려 시도하지 마십시오.

**판정은 형식 충족 여부까지만** 하고 내용의 우열은 평가하지 않습니다. 운영자가 내용 품질을 판정하면 개별 투자 판단에 대한 피드백이 되어 컴플라이언스 경계에 닿습니다.

### 10-5. 투명성 장치 (CS를 없애는 실질적 수단)

민원의 대부분은 "몰랐다"에서 발생합니다. 30칸 상태 그리드(§8-1), 마감 카운트다운, 미달성 확정 즉시 이메일 통지, 마일스톤 여유 일수 2일 이하 시 경고 발송 네 가지를 구현하면 사후 분쟁이 거의 사라집니다. 알림은 기존 뉴스레터 발송 경로를 재사용하십시오.

### 10-6. 운영자 개입 예외

서비스 장애 구간을 지정해 마감을 일괄 연장하는 기능과, 참가자 소명 접수 기능만 수동으로 남깁니다. 소명 승인 기준은 서비스 장애로 한정하고, 개인 사정은 결석 허용 일수로 이미 흡수된다는 점을 약관에 명시하십시오.

### 10-7. 관리자 화면

기수별 참가자 목록에 구간별 제출 수, 마일스톤 달성 여부, 지급 처리 상태를 표로 표시합니다. 지급 완료는 운영자가 수동 체크하는 방식이면 충분합니다. **기존 관리자 인증 체계(`admin_users`, `admin_user_sessions`)를 재사용하고 새 인증 체계를 만들지 마십시오.**

## 11. Phase 7: 결제와 환급 (운영자 결정 이후 착수)

### 11-1. 보상 모델 권고안 (운영자 승인 대기)

외부 분석은 예치금 30만원을 받고 완주 시 전액 환급하되 미환급 예치금을 영업이익으로 삼는 모델을 권고했습니다. 전환율 효과와 체리피커 필터링 효과는 타당하나, 미환급분을 수익원으로 삼는 부분은 다음 세 가지 이유로 권하지 않습니다.

첫째, **구조적 이해충돌입니다.** 미환급 예치금이 주 수익원이면 회사 이익과 참가자 성공이 반대 방향을 향합니다. 마감을 더 빡빡하게, 알림을 덜 보내는 모든 결정이 수익을 늘립니다. "종목을 팔지 않는 사람"이라는 신뢰가 차별점인 브랜드에서 회복 불가능한 손상이 될 수 있습니다.

둘째, **약관으로 청약철회권을 배제할 수 없습니다.** 전자상거래법상 청약철회권은 강행규정이며 사업자의 환불 불가 안내가 있어도 무효입니다. "예외 없는 인증 실패 기준을 약관에 명시하면 된다"는 전제는 성립하지 않습니다. 도입을 결정한다면 반드시 변호사 검토를 받으십시오.

셋째, **1인 운영 부담과 PG 리스크입니다.** 국내 대표 환급형 챌린지 서비스는 환급 시 카드 취소 수수료 협의가 이루어지지 않아 특정 카드사 결제를 지원하지 못하고 있습니다. 참고로 해당 서비스의 환급 기준도 100퍼센트가 아니라 85퍼센트입니다.

**권고 구조는 예치금을 받되 미완주분을 몰수하지 않는 것입니다.**

| 구분 | 처리 |
|---|---|
| 완주 시 | 예치금 전액 환급 + 전자책 3권 제공 |
| 미완주 시 | 환급 없음. 예치금 상당의 콘텐츠로 전환 지급 |

미완주자 지급물은 즉시 제공 가능한 자산으로 구성합니다. 1편 전자책 정식판, DC Alpha Scanner 정식판, 다음 기수 재참여권입니다. 집필 중인 2·3편은 완주자 전용으로 두어 차등을 유지합니다.

이 구조에서는 참가자가 실패해도 회사가 재화를 제공해야 하므로 실패를 유도할 유인이 없고, 민원의 성격이 "돈을 못 받는다"에서 "책으로 받는다"로 바뀌며, 회계도 실제 재화 제공이 있어 콘텐츠 매출로 단순하게 인식됩니다.

**1기 예치금은 5만원에서 10만원 구간을 권고합니다.** 1기의 목적은 매출이 아니라 판정 시스템과 약관과 환급 프로세스의 검증입니다.

### 11-2. 마일스톤 구조 (모델과 무관하게 유지)

| 마일스톤 | 판정 기준 | 즉시 지급물 |
|---|---|---|
| Day 10 | 1~10일 중 8일 이상 기록 | 1편 전자책 정식판 |
| Day 20 | 11~20일 중 8일 이상 기록 | DC Alpha Scanner 정식판 |
| Day 30 | 21~30일 중 8일 이상 기록 | 예치금 환급 + 2·3편 출간 시 제공 확약 |

세 구간을 모두 달성하면 완주이며 총 24일 이상, 80퍼센트 기준입니다.

### 11-3. 구현 범위

PG 연동, 예치금 결제, 환급 프로세스, 미완주자 콘텐츠 전환 지급, 선수금 회계 처리 구분입니다. 환급은 카드 결제 취소 방식과 계좌 직접 송금 방식을 모두 준비해야 합니다. **이 Phase 착수 전에 약관과 환불 정책에 대한 변호사 검토가 선행되어야 합니다.**

## 12. Antigravity 작업 규칙 (모든 프롬프트에 포함)

지난 작업에서 파일 재작성 스크립트로 인해 공개 API 두 개가 회귀한 사고가 있었습니다.

첫째, **기존 파일을 통째로 다시 쓰지 말고 증분 편집만 하십시오.** 파일 전체를 생성하는 스크립트 방식을 금지합니다. 단 Phase 0의 인코딩 복구는 예외이며, 이 경우에도 문자열만 교체하고 로직은 건드리지 마십시오.

둘째, **완료 보고에 `git diff --stat`을 반드시 포함하십시오.** 삭제 줄 수가 추가 줄 수보다 많은 파일이 있으면 사유를 별도로 설명해야 합니다.

셋째, **임시 파일과 백업 파일을 저장소에 남기지 마십시오.**

넷째, **기존 타입 계약을 변경하지 마십시오.** 프런트엔드 훅이 소비하는 응답 형태를 바꿔야 한다면 구현을 멈추고 운영자에게 먼저 질문하십시오.

다섯째, **모든 파일은 UTF-8로 저장하고 저장 후 검증하십시오.** 한글 문자열이 코드에 포함되므로 인코딩 회귀가 반복될 수 있습니다.

여섯째, **각 Phase 완료 시 회귀 테스트를 함께 추가하십시오.** 특히 Phase 6의 판정 로직은 경계 조건 테스트가 필수입니다. 마감 1초 전, 마감 1초 후, 지각 마감 경계, 구간 경계일(Day 10, 11, 20, 21)을 반드시 포함하십시오.

일곱째, **문서에 없는 결정이 필요하면 임의로 정하지 말고 질문하십시오.**

## 14. 운영자 승인이 필요한 항목

Phase 0부터 Phase 5까지는 아래 결정 없이도 착수 가능합니다. Phase 7만 결정에 묶여 있습니다.

첫째, **§11-1의 미완주자 콘텐츠 전환 구조**입니다. 미환급 예치금을 수익으로 인식할 것인지, 콘텐츠 제공으로 전환할 것인지의 선택입니다.

둘째, **§11-1의 1기 예치금 5만원에서 10만원 구간**입니다. 30만원을 유지할 경우 변호사 검토와 PG 사전 협의가 선행되어야 합니다.

셋째, **§11-2의 구간별 80퍼센트 완주 기준**입니다.

넷째, **인기순 정렬과 추천 게시물을 만들지 않는다는 원칙**입니다. 성장 레버 하나를 스스로 포기하는 선택이므로 명시적 승인이 필요합니다.

다섯째, **§5-2의 저자 완주 기록 30건 생산**입니다. 운영자 직접 집필이 필요한 콘텐츠 작업이므로 착수 시점 결정이 필요합니다.
