## 3. 백로그에 없는 항목 네 가지 (먼저 추가하십시오)

정리해 주신 백로그에 빠져 있으나 우선순위가 더 높은 항목이 있습니다.

### 3-1. 커뮤니티 API 파일 6개의 인코딩이 손상되어 있습니다 [P0]

아래 파일들이 UTF-8로 디코딩되지 않습니다.

```
functions/api/community/auth/account.js
functions/api/community/auth/config.js
functions/api/community/auth/profile.js
functions/api/community/posts/index.js
functions/api/community/posts/[slug]/comments.js
functions/api/community/posts/[slug]/comments/[commentId].js
```

`posts/index.js`의 실제 저장 상태입니다.

```js
return errorResponse(503, "UNAVAILABLE", "커�??�티 글??불러?????�습?�다.");
```

원래 "커뮤니티 글을 불러올 수 없습니다"였을 문구입니다. 사용자에게 깨진 한글이 그대로 나가고 있을 가능성이 높습니다.

**이 항목은 백로그의 `error.code` 전환과 직결됩니다.** 지금 not-found 판정을 한글 문구 비교로 하고 있는데, 한글 문자열 자체가 깨져 있으면 그 비교가 언제 어긋날지 모릅니다. 인코딩 복구와 `error.code` 전환을 한 묶음으로 처리하십시오.

복구 방법은 각 파일 바이트를 cp949로 디코딩해 원문이 복원되는지 확인한 뒤 UTF-8로 재저장하는 것입니다. 복원되지 않으면 이중 인코딩이므로 해당 문자열만 의미에 맞게 다시 작성하십시오. **로직은 건드리지 말고 문자열만 복구해야 합니다.** 복구 후 전 파일 UTF-8 디코딩 성공과 U+FFFD 0건을 검증해 보고에 포함하십시오.

재발 방지를 위해 저장소 전체 UTF-8 검증 스크립트를 `scripts/`에 추가하고 CI에 넣으십시오.

### 3-2. 공지 카테고리와 고정 게시물 기능이 없습니다 [P0]

카테고리가 `pension-etf-qna`, `etf-questions`, `challenge-30`, `feedback` 네 개뿐이라 기수 모집 공고와 게시판 규칙을 올릴 자리가 없습니다. 목록 정렬도 `created_at` 내림차순 고정이라 규칙 안내가 하루 만에 밀려 내려갑니다.

`notice` 카테고리(작성 권한 moderator 이상)와 `is_pinned` 플래그를 추가하십시오. 고정은 카테고리별 최대 3건으로 제한합니다.

### 3-3. 저장소 잔재가 남아 있습니다 [P0, 비용 거의 없음]

루트의 `temp.json`, 그리고 `functions/api/briefings/latest.js.tmp`를 삭제하십시오. 후자는 직전 회귀 사고의 흔적입니다.

### 3-4. 저장소 아키텍처 확인이 선행되어야 합니다 [P0]

커뮤니티는 D1이 아니라 **Supabase**를 씁니다. `posts/index.js`가 `community_public_posts` 뷰와 `create_community_post` RPC를 호출합니다. 반면 ETF 가격·브리핑·관리자 인증은 D1입니다.

따라서 기수, 참가자, 챌린지 기록은 전부 Supabase에 두어야 합니다. 그리고 게시글 생성이 RPC를 경유하므로 구조화 필드를 추가하려면 **Postgres 함수 자체를 수정**해야 합니다. Workers 코드만 고쳐서는 필드가 저장되지 않습니다.

착수 전 Supabase 실제 스키마(원본 테이블, 뷰, 함수 정의)를 조회해 확인하고 그 결과를 근거로 설계하십시오. 추측으로 진행하지 마십시오.

### 4-1. 페이지네이션이 P0인 이유

시딩 계획만으로 게시물이 48건입니다. 저자 완주 기록 30건, 공지 3건, Q&A 10건, ETF 기초 질문 5건입니다. 여기에 1기가 시작되면 하루 30건씩 쌓입니다.

`limit` 상한 50에 커서가 없으면 **챌린지 이틀째에 시드 콘텐츠가 도달 불가 영역으로 밀려납니다.** 저자 완주 기록은 신규 참가자가 매일 참조해야 하는 자산인데 접근이 막히면 시딩 투자가 통째로 무의미해집니다.

커서 기반 페이지네이션과 "더보기"를 Phase 1 범위에 포함하십시오. 카테고리 필터와 함께 동작해야 합니다.

### 4-2. 모더레이션 화면이 P0인 이유

커뮤니티를 열면 부적절 게시물은 반드시 발생합니다. 그중 종목 매수 권유나 수익률 자랑성 게시물은 자본시장법 §101 방어선과 직결되므로 즉시 내려야 합니다.

지금은 admin이 글을 숨기려면 DB를 직접 조작해야 합니다. 1인 운영에서 이는 사실상 대응 불가라는 뜻입니다.

**전체 모더레이션 도구를 만들 필요는 없습니다.** 게시물과 댓글에 "숨김" 토글 하나만 있으면 됩니다. 삭제가 아니라 숨김이어야 분쟁 시 원본이 남습니다. 기존 관리자 인증 체계(`admin_users`, `admin_user_sessions`)를 재사용하십시오.

### 4-3. pg_cron 증빙이 P0인 이유

30일 물리삭제 스케줄이 실제로 도는지 미확인이라는 것은, **탈퇴 회원 데이터의 파기 의무 이행 여부가 확인되지 않았다는 뜻**입니다. 개인정보보호법 관련 사안이므로 추정으로 두면 안 됩니다.

확인 비용은 쿼리 한 번입니다. `cron.job`과 `cron.job_run_details`를 조회해 스케줄 등록 여부와 최근 실행 이력을 확인하고 결과를 보고하십시오. 돌고 있지 않으면 그 자체가 별도 P0 과제가 됩니다.

### 4-4. 알림은 용도에 따라 우선순위가 갈립니다

**챌린지 알림은 P0입니다.** 미달성 확정 통지와 마일스톤 여유 일수 경고는 CS를 없애는 핵심 장치입니다. 민원의 대부분은 "몰랐다"에서 발생하므로, 이 알림이 없으면 자동 판정 시스템 전체의 효과가 절반으로 떨어집니다.

**댓글 알림은 P1입니다.** 발송 인프라를 챌린지 알림 용도로 먼저 만들고, 댓글 알림은 그 위에 얹으십시오. 기존 뉴스레터 발송 경로를 재사용할 수 있는지 먼저 확인하십시오. 새 발송 인프라를 만들지 마십시오.

### 4-5. noindex는 제거가 아니라 카테고리별 분기입니다

`read/page.tsx`의 `robots: noindex`를 일괄 해제하지 마십시오. 참가자의 연금 계좌 상태 기록이 검색에 노출되는 것은 프라이버시 문제입니다.

카테고리별로 나누십시오.

| 카테고리 | 색인 | 근거 |
|---|---|---|
| `notice` | index | 공지, 노출 문제 없음 |
| `pension-etf-qna` | index | 검색 유입 자산으로 설계된 축 |
| `etf-questions` | index | 동일 |
| `challenge-30` | **noindex 유지** | 개인 연금 상태 기록 포함 |
| `feedback` | noindex | 내부 피드백 |

`challenge-30`은 `visibility` 필드로 기수 공개와 전체 공개를 구분하므로, 전체 공개 게시물이라도 색인은 막는 것이 안전합니다. 공개 범위와 검색 색인은 다른 개념입니다.
