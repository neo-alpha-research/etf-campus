# 인프라 방향 결정: Actions 한도 초과 대응과 자체 서버 활용 범위

작성일: 2026-08-21
작성 주체: EVS Navigator
검토 대상: ETF Campus 에이전트 실측 보고(2026-08-21)
성격: 기안. 운영자 승인 후 실행합니다.

## 총평

보고서의 방향(코어 서비스는 이전하지 않고 자체 서버는 오케스트레이션과 백오피스로만 사용)은 옳습니다. 다만 **측정값이 실제 청구 분을 대표하지 못하며, 그 결과 권고안의 우선순위가 뒤바뀌어 있습니다.** 지금 손대야 할 것은 데이터 수집 워크플로가 아니라 배포 워크플로입니다.

## 1. 보고서에서 바로잡아야 할 세 가지

### 1-1. 측정값이 2,000분을 설명하지 못합니다

보고된 소모량 합계는 다음과 같습니다.

| 워크플로 | 실행 | 측정 소모 |
|---|---|---|
| Deploy market briefing production | 63회 | 약 322분 |
| Daily ETF market data refresh | 15회 | 약 42분 |
| 기타 3종 | 각 3~15회 | 대부분 1분 미만 |
| **합계** | | **약 384분** |

**한도는 2,000분인데 측정값은 384분입니다. 19퍼센트만 설명됩니다.** 나머지 1,600분의 출처가 확인되지 않은 상태에서 절감 계획을 세우면 엉뚱한 곳을 최적화하게 됩니다.

측정 방법에 세 가지 결함이 있습니다.

첫째, `gh run list --limit 100`은 **최근 100건**이지 이번 달 전체가 아닙니다. Antigravity가 활발히 푸시하는 기간에는 100건이 며칠치에 불과합니다.

둘째, GitHub는 **job 단위로 과금하며 분 단위로 올림 처리**합니다. 10초짜리 job도 1분으로 청구됩니다. "대부분 1분 미만"이라고 기록된 실행들이 실제로는 각각 최소 1분씩 청구되고 있습니다.

셋째, `updatedAt - startedAt`은 워크플로 실행 수준의 벽시계 시간이라 **다중 job 워크플로에서 병렬 job의 합산을 놓칩니다.**

**재측정 지시.** 아래 API로 계정 수준의 실제 청구 분을 조회하십시오. 이것이 유일하게 권위 있는 숫자입니다.

```
GET /orgs/neo-alpha-research/settings/billing/actions
```

응답의 `total_minutes_used`, `included_minutes`, `minutes_used_breakdown`을 그대로 보고하십시오. API가 동작하지 않으면 GitHub 결제 대시보드에서 직접 확인하십시오.

**함께 확인할 것.** 2,000분 한도는 저장소가 아니라 **계정 또는 조직 단위로 공유**됩니다. `neo-alpha-research` 조직에 다른 private 저장소가 있고 그쪽에서 Actions를 쓰고 있다면 같은 풀을 소모합니다. 조직 내 전체 저장소의 Actions 사용 현황을 확인하십시오.

### 1-2. 권고안의 우선순위가 뒤바뀌어 있습니다

보고서는 스스로 `Deploy market briefing production`을 "주범"(63회, 322분)으로 지목해 놓고, 권고안 첫 항목에서는 `daily-market.yml`의 `npm run build` 제거를 제시했습니다. 두 항목의 규모가 다릅니다.

`daily-market.yml`의 빌드 스텝은 `steps.changes.outputs.changed == 'true'` 조건이 붙어 있어 **데이터가 실제로 갱신된 rung에서만 실행됩니다.** 하루 1회, 3.85분, 영업일 22일 기준 월 약 85분입니다. 전체 한도의 4퍼센트입니다.

반면 배포 워크플로는 확인된 것만 322분이고, 푸시 트리거라 개발 활동량에 비례해 무한히 늘어납니다. **여기가 진짜 지렛대입니다.**

빌드 스텝 제거 자체는 옳은 판단이니 함께 실행하되, 그것이 1순위라는 서술은 정정합니다.

### 1-3. public 전환 반대는 결론은 맞고 근거는 틀렸습니다

보고서의 반대 근거는 "과거 커밋 이력에 포함되었을지 모르는 잠재적 설정값"입니다. **"모르는"은 측정이 아니라 추정입니다.** 확인을 요청했는데 확인하지 않고 추정으로 답한 것이므로 그대로 채택할 수 없습니다.

다만 **결론에는 동의합니다.** 더 확실한 근거 두 가지가 있습니다.

첫째, **Neo의 익명성입니다.** 저장소를 공개하면 커밋 작성자 이름과 이메일이 전부 노출됩니다. Neo는 자본시장법 §101 회피 전략과 맞물려 의도적으로 익명을 유지하는 페르소나이며, 커밋 이력에 실명 계정이 남아 있다면 공개 즉시 연결됩니다. 이는 브랜드 설계의 근간을 흔드는 문제입니다.

둘째, **연금 편입 가능 목록 대조 데이터가 실질적 해자입니다.** 운용사별 공식 자료를 대조해 축적한 자산이며 경쟁자가 단기간에 복제하기 어렵습니다. 공개는 이를 무상 제공하는 것과 같습니다.

**추가 지시.** public 전환 여부와 무관하게 **커밋 이력 시크릿 스캔을 1회 수행하십시오.** private 저장소도 협업자 추가나 실수로 노출될 수 있습니다. gitleaks 또는 trufflehog로 전체 이력을 스캔하고 결과를 보고하십시오.

## 2. 보고서에서 가장 중요한 발견: D1 잠금 문제

분량은 짧지만 이번 보고에서 가장 값진 발견입니다.

> 수집은 되었으나 이벤트 발행 단계에서 멈추면 `market_data_readiness`나 `market_source_consumer_runs`에 `processing` 또는 `skipped_duplicate` 상태로 잠금이 남습니다. 이후 시스템이 복구되어도 이 잠금 때문에 다음 파이프라인이 영구적으로 무시됩니다.

**이것은 Actions 분보다 심각한 문제입니다.** 분이 부족하면 실행이 안 되고 그 사실이 드러나지만, 잠금이 남으면 파이프라인이 정상 종료된 것처럼 보이면서 데이터가 조용히 누락됩니다. 24일자 누락이 실제 사례라고 보고되었습니다.

이는 앞선 파이프라인 검토에서 지적한 "조용한 실패"의 전형이며, 자원을 아무리 늘려도 해결되지 않습니다.

**해결 방향 세 가지를 지시합니다.**

첫째, **`processing` 상태에 임대 시간(lease)을 부여하십시오.** 상태 레코드에 `locked_at`을 두고, 현재 시각과의 차이가 임계치(30분 권고)를 넘으면 잠금이 만료된 것으로 간주해 자동 회수합니다. 프로세스가 죽어도 잠금이 영구화되지 않습니다.

둘째, **재처리를 멱등하게 만드십시오.** `skipped_duplicate`가 남은 상태에서 같은 기준일을 다시 처리해도 안전하게 통과하거나 명시적으로 실패해야 합니다. 지금처럼 조용히 무시되면 안 됩니다.

셋째, **잠금 노후 알림을 추가하십시오.** `monitor-market-daily-pipeline.yml`이 이미 매일 10:15에 돌고 있으므로, 여기에 "임계치를 넘긴 `processing` 레코드가 있는가" 검사를 추가하면 추가 비용 없이 조기 탐지가 됩니다.

우선순위는 Actions 절감과 동급의 P0입니다.

## 3. 확정 방향

### 3-1. 즉시 실행 (오늘, 비용 0원)

**배포 워크플로의 트리거를 좁히십시오.** 이것이 가장 큰 절감입니다.

- 경로 필터를 적용해 브리핑 관련 코드가 바뀔 때만 실행합니다. `data/` 커밋이나 문서 변경으로 배포가 도는 일이 없어야 합니다.
- `concurrency` 그룹에 `cancel-in-progress: true`를 적용합니다. 연속 푸시 시 이전 실행을 취소해 중복 소모를 없앱니다. 단 main 브랜치 배포에는 적용하지 마십시오. 배포 도중 취소는 위험합니다.
- draft PR에서는 실행하지 않도록 조건을 추가합니다.

**`daily-market.yml`에서 `npm run build`를 제거하십시오.** Cloudflare Pages가 커밋마다 자체 인프라에서 다시 빌드하므로 중복입니다. 실패 이력 분석 결과 이 스텝이 오류를 걸러낸 사례가 없다는 보고를 근거로 채택합니다.

**`npm test`와 `python -m unittest`는 유지하십시오.** 수 초 수준이라 절감 효과가 없고, 데이터 검증 게이트 역할은 남겨야 합니다.

**세 일일 워크플로의 시작 분을 다시 분산하십시오.** 현재 셋 다 `:37`로 동일해 완전히 겹칩니다. 공통 `concurrency` 그룹이 있어 직렬화되므로 큐 대기가 발생합니다. 최소 10분 간격으로 벌리십시오.

### 3-2. 단기 실행 (1주 내)

D1 잠금 해제 메커니즘 세 가지(§2)를 구현합니다.

계정 수준 실제 청구 분을 재측정하고(§1-1), 조직 내 다른 저장소의 소모를 확인합니다.

커밋 이력 시크릿 스캔을 1회 수행합니다(§1-3).

재측정 결과 여전히 한도 초과가 예상되면 그때 유료 전환(월 4달러 수준의 Team 플랜 또는 분 추가 구매)을 검토합니다. **이전 작업 공수를 감안하면 소액 유료화가 자체 서버 이전보다 합리적인 선택일 수 있습니다.** 이 판단은 재측정 이후로 미룹니다.

### 3-3. 자체 서버 활용 범위

보고서의 "코어는 옮기지 않는다"는 원칙에 동의합니다. 다만 **한 가지 모순을 짚습니다.**

보고서는 자체 서버를 "언제든 꺼져도 되는 작업"에만 쓰라고 하면서, 동시에 n8n이 일일 데이터 수집을 GitHub Actions로부터 넘겨받도록 권고했습니다. **일일 수집은 매일 반드시 도는 작업이므로 꺼지면 안 되는 작업입니다.** 1개월 뒤 서버가 회수되면 파이프라인이 멈춥니다.

**해결책은 이중 스케줄러 안전망입니다.**

수집 실행을 n8n으로 옮기되, **GitHub Actions cron을 비활성화하지 말고 그대로 두십시오.** 앞서 권고한 조기 종료 가드(수집 전에 목표 거래일 데이터 보유 여부를 먼저 판정)를 적용하면, n8n이 이미 수집을 마친 날의 Actions 실행은 몇 초 만에 종료됩니다. 비용이 거의 들지 않는 안전망이 됩니다.

이 구조에서 서버가 회수되거나 장애가 나면 Actions가 자동으로 이어받습니다. 되돌리기 작업이 필요 없습니다.

**도입 순서는 다음과 같습니다.**

| 순서 | 앱 | 용도 | 손실 허용도 |
|---|---|---|---|
| 1 | Grafana | 파이프라인 상태와 D1 잠금 모니터링 | 높음. 꺼져도 서비스 무영향 |
| 2 | appsmith | 커뮤니티 모더레이션, 챌린지 판정 확인, 브리핑 검수 | 높음. 대체 경로 존재 |
| 3 | n8n | 일일 수집 오케스트레이션 | 낮음. Actions 안전망 필수 |

**1번과 2번을 먼저 하십시오.** 둘은 지금 구조에서 만들기 어렵거나 개발 비용이 큰 기능을 추가해 주는 순수 이득이며, 서버가 회수돼도 잃을 것이 없습니다. 특히 Grafana는 §2의 잠금 문제를 조기에 발견하는 도구라 우선순위가 높습니다.

3번은 **이용 기간 연장 가능 여부를 확인한 뒤에 착수하십시오.** 연장이 불가능하면 n8n 이전은 하지 않는 편이 낫습니다.

Superset, Airbyte, ELK, RAGFlow, SIM이 현 규모에 과설계라는 판단에 동의합니다. 추가 승인을 신청하지 마십시오.

## 4. 하지 않기로 한 것

**Cloudflare 이전을 하지 않습니다.** D1이 용량 1.8퍼센트, 쓰기 11.8퍼센트로 한도에 여유가 큽니다. 서버리스의 무중단성과 CDN 가속을 포기할 이유가 없습니다.

**저장소 public 전환을 하지 않습니다.** 근거는 §1-3입니다.

**데이터 SSOT를 Git에서 옮기지 않습니다.** 177MB는 여전히 가벼우며, 매일 CSV를 커밋하는 구조는 무료 백업이자 버전 이력이고 연금 태그 수작업 자산의 단일 장애점을 제거합니다. n8n으로 수집을 옮기더라도 최종 산출물은 계속 Git에 커밋합니다.

## 5. 운영자 결정이 필요한 사항

첫째, **자체 서버 이용 기간 연장 가능 여부 확인**입니다. n8n 이전 여부가 여기에 달려 있습니다.

둘째, **재측정 결과 한도 초과가 구조적이라면 GitHub 유료 전환을 수용할 것인지**입니다. 월 소액 지출과 자체 서버 이전 공수를 비교하는 판단입니다.

셋째, **Neo 익명성 관점에서 커밋 작성자 정보 점검 범위**입니다. 시크릿 스캔과 함께 커밋 author 이메일 노출 여부를 확인할지 결정이 필요합니다.

## 6. 다음 지시로 넘길 작업 목록

에이전트에게 아래를 순차 지시할 예정입니다.

1. 계정 수준 청구 분 재측정과 조직 내 저장소별 소모 확인
2. 배포 워크플로 트리거 축소(경로 필터, cancel-in-progress, draft 제외)
3. `daily-market.yml` 빌드 스텝 제거와 일일 워크플로 시작 분 재분산
4. D1 잠금 임대 시간, 멱등 재처리, 노후 알림 구현
5. 커밋 이력 시크릿 스캔
6. 조기 종료 가드 적용(이중 스케줄러 안전망의 전제)
7. Grafana 설치와 파이프라인 대시보드 구성
8. appsmith 설치와 관리자 화면 구성

7번과 8번은 서버 작업이므로 저장소 코드 변경과 분리해 진행합니다.
