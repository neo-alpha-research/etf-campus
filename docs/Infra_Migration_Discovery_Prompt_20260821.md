# ETF Campus 에이전트 질의: 인프라 현황 조사와 자체 클라우드 이전 검토

작성일: 2026-08-21
발신: EVS Navigator
용도: 아래 구분선 안의 전문을 ETF Campus 담당 에이전트에게 그대로 전달하십시오. 회신을 받아 Navigator가 이전 계획을 수립합니다.

---

## 배경

오늘 GitHub Actions 월간 무료 한도 2,000분을 초과해 일일 업데이트가 정상 동작하지 않았습니다. 기능과 데이터가 늘면서 파이프라인이 느려지고, Antigravity에서 GitHub, Cloudflare로 이어지는 구간에서 작업이 소실되거나 끊기는 문제도 반복되고 있습니다.

정부 지원 프로그램으로 아래 자원을 확보했습니다. 이를 활용해 일부 작업을 자체 서버로 옮기고 GitHub와 Cloudflare 의존을 줄이는 방안을 검토하려 합니다.

```
클라우드   CPU 2core / RAM 16GB / Disk 100GB
운영체제   Rocky Linux 8.10 (rocky-8.10-base)
이용 기간  기본 1개월 지원
승인 완료 앱  appsmith, Grafana, n8n
추가 승인 가능  SIM, Airbyte, ELK, Superset, RAGFlow
```

당신에게 요청하는 것은 **현황 조사 결과와 이전 가능성에 대한 의견**입니다. 실제 이전 작업은 이 회신을 검토한 뒤 별도 지시로 진행합니다. 지금은 코드를 수정하지 마십시오.

추정하지 말고 실측하십시오. 확인하지 못한 항목은 "확인 불가"로 표시하고 왜 확인할 수 없었는지 적으십시오. 숫자에는 측정 방법을 함께 적으십시오. 이 회신을 근거로 계획을 세우므로, 근거 없는 수치가 섞이면 계획 전체가 어긋납니다.

## 1. GitHub Actions 사용량 실측 (최우선)

다음을 실제 데이터로 확인해 주십시오.

첫째, **저장소가 public인지 private인지** 알려주십시오. public이면 Actions 분이 무제한이므로 이번 문제의 성격 자체가 달라집니다.

둘째, **워크플로별 이번 달 소모 분과 실행 횟수**를 표로 정리하십시오. GitHub의 Billing 화면 또는 API로 조회 가능합니다. 어떤 워크플로가 한도를 소진했는지가 이후 판단의 출발점입니다.

셋째, **`daily-market.yml`의 1회 실행 소요 시간을 단계별로** 알려주십시오. 특히 `npm ci`, `python -m unittest`, `npm test`, `npm run build` 네 스텝이 각각 몇 분을 쓰는지 확인이 필요합니다.

넷째, 아래 가설을 검증해 주십시오.

> **가설 1.** Actions 분 소모의 대부분은 데이터 수집이 아니라 `daily-market.yml` 안의 빌드·테스트 스텝이다. 그리고 커밋이 푸시되면 Cloudflare Pages가 어차피 다시 빌드하므로, 같은 빌드를 하루에 두 번 하고 있다.

이 가설이 맞다면 Actions에서 빌드 스텝을 제거하는 것만으로 상당한 절감이 가능합니다. 다만 빌드가 데이터 검증 게이트 역할을 겸하고 있다면 단순 제거가 위험하므로, 현재 그 스텝이 실제로 어떤 오류를 잡아 왔는지도 함께 알려주십시오.

## 2. Cloudflare 사용 실태

Pages 빌드 횟수, Workers 요청 수, KV 읽기·쓰기, D1 읽기·쓰기·저장 용량을 각각 이번 달 실적과 무료 한도 대비 비율로 알려주십시오.

Cloudflare가 실제로 한도에 근접했는지, 아니면 문제는 GitHub Actions에만 있는지 판별이 필요합니다. 이 구분에 따라 이전 대상이 완전히 달라집니다.

## 3. 일일 파이프라인 전체 목록

현재 매일 도는 모든 작업을 아래 항목으로 정리하십시오.

| 작업명 | 실행 시각(KST) | 평균 소요 | 호출하는 외부 API | 산출물 | 실패 시 영향 |

`daily-market`, `daily-distribution`, `daily-fees`, `monitor-market-daily-pipeline` 외에 다른 정기 작업이 있으면 모두 포함하십시오. Cloudflare Workers의 Cron Trigger나 Supabase의 pg_cron 스케줄도 빠뜨리지 마십시오.

## 5. 소실·끊김 현상의 구체적 증상

"중간에 작업이 소실되거나 끊긴다"는 문제를 재현 가능한 형태로 특정해 주십시오.

어느 구간에서 발생하는지(Antigravity 작업물이 커밋에 반영되지 않음, 커밋은 됐는데 Pages 배포가 안 됨, 배포는 됐는데 사이트에 반영 안 됨 등), 빈도는 어느 정도인지, 발생 시 로그에 남는 오류는 무엇인지 알려주십시오.

원인이 자원 한도가 아니라 워크플로 설계나 동시성 문제일 수 있으므로, 자원 이전으로 해결될 문제인지 아닌지를 먼저 가려야 합니다.

## 7. 승인된 앱의 활용 가능성

각 앱이 현재 구조에서 실제로 쓸모가 있는지, 있다면 어떤 역할로 쓸 수 있는지 평가해 주십시오. 억지로 용도를 만들지 말고 불필요하면 불필요하다고 적으십시오.

**n8n**은 GitHub Actions cron을 대체해 일일 수집 파이프라인을 오케스트레이션할 수 있는지가 핵심 질문입니다. 재시도, 실패 알림, 단계별 의존성 관리가 현재 워크플로 수준으로 가능한지 판단해 주십시오.

**Grafana**는 파이프라인 실행 상태와 서버 자원을 모니터링하는 용도입니다. 현재 `monitor-market-daily-pipeline.yml`이 하는 일을 대체하거나 보강할 수 있는지 평가하십시오.

**appsmith**는 관리자 화면 용도입니다. 커뮤니티 모더레이션, 챌린지 마일스톤 판정 확인, 브리핑 검수 같은 내부 도구를 직접 개발하지 않고 구성할 수 있는지 판단하십시오.

**Superset, Airbyte, ELK, RAGFlow, SIM**은 추가 승인이 필요한 앱입니다. 현재 규모에서 실익이 있는지, 아니면 과설계인지 의견을 주십시오. SIM은 정확히 어떤 도구인지 확인되지 않았으므로 조사 결과를 함께 알려주십시오.

## 8. 반드시 검증해야 할 위험 가설

아래 세 가지에 대해 명확한 의견을 주십시오. 동의든 반대든 근거를 함께 적으십시오.

> **가설 2.** 저장소를 public으로 전환하면 Actions 분이 무제한이 되어 이번 문제가 비용 없이 즉시 해결된다. 코드가 공개되는 대가로 지불할 만한 거래인가?

이 판단에는 저장소에 공개되면 곤란한 내용이 있는지 확인이 필요합니다. 시크릿은 GitHub Secrets에 있으니 노출되지 않지만, 코드 자체나 `data/`의 내용, 커밋 이력에 민감한 정보가 있는지 점검해 주십시오.

> **가설 3.** 자체 서버는 GitHub와 Cloudflare를 대체하는 것이 아니라 보완하는 용도로 써야 한다. 이용 기간이 기본 1개월이므로, 운영 중인 일일 파이프라인의 핵심 경로를 여기에 옮기면 한 달 뒤 다시 이전해야 하는 위험이 생긴다.

이용 기간 연장이 가능한지, 연장 조건이 무엇인지 먼저 확인해 주십시오. 이 답에 따라 이전 범위가 완전히 달라집니다.

> **가설 4.** 데이터의 단일 진실은 Git에 유지해야 한다. 매일 CSV를 커밋하는 구조는 무료 백업이자 버전 이력이며, 연금 태그처럼 수작업이 들어간 자산의 단일 장애점을 제거하는 장치다. 수집 실행을 자체 서버로 옮기더라도 결과물은 계속 Git에 커밋하는 편이 안전하다.

이 가설에 동의하는지, 반대한다면 대안 백업 전략은 무엇인지 답해 주십시오.

## Navigator 메모 (에이전트 전달 대상 아님)

질의 설계의 근거입니다.

**이번 사태는 예견되었던 것입니다.** 2026-08-20 파이프라인 검토(`docs/Pipeline_Architecture_Review_20260820.md`) §4-4에서 "리포지토리가 private이면 무료 한도 월 2,000분에 근접하거나 초과할 수 있다"고 지적하고, 재시도 사다리의 조기 종료 가드를 비용 측면 최우선 과제로 제시한 바 있습니다.

**그 이후 개선은 일부 반영되었습니다.** 재시도 사다리가 4단에서 2단으로 줄었고(`cron: "37 21,22"`), 세 워크플로에 공통 `concurrency: daily-etf-data` 그룹이 적용되었으며, `git pull --rebase` 재시도 루프도 들어갔습니다. 다만 세 워크플로가 모두 같은 분(:37)에 시작하도록 바뀌어 실행이 완전히 겹치게 되었고, `daily-market.yml`의 `npm ci`·`npm test`·`npm run build`는 그대로 남아 있습니다.

**따라서 가설 1이 가장 유력합니다.** 실행 횟수는 하루 7회 수준으로 이미 줄었는데도 2,000분을 넘겼다면, 회당 소요 시간이 길다는 뜻이고 그 원인은 빌드·테스트일 가능성이 높습니다. Cloudflare Pages가 커밋마다 자체 인프라에서 다시 빌드하므로 동일 빌드를 이중으로 수행하는 구조일 수 있습니다.

**가설 2(public 전환)가 실현 가능하면 이번 문제는 오늘 해결됩니다.** 비용 0원, 이전 작업 0건입니다. 자체 서버 이전보다 먼저 검토해야 할 선택지입니다.

**이용 기간 1개월은 결정적 제약입니다.** 앞서 클라우드 신청 시 3개월을 선택하도록 안내했으나 실제 승인이 1개월이라면, 운영 중인 파이프라인의 핵심 경로를 옮기는 것은 위험합니다. 연장 가능 여부 확인이 계획 수립의 선결 조건입니다.

**자체 서버의 진짜 가치는 대체가 아니라 확장에 있을 가능성이 큽니다.** n8n으로 파이프라인을 시각적으로 관리하고, Grafana로 상태를 보고, appsmith로 관리자 화면을 코드 없이 구성하는 것은 현재 구조로는 만들기 어렵거나 개발 비용이 큰 기능입니다. 회신을 받아 이 방향으로 계획을 정리할 예정입니다.
