## 총평

스케줄링과 상태 관리 자체는 1인 운영 규모에서 보기 드물게 잘 설계되어 있습니다. 다만 지금 파이프라인의 실질적 위험은 효율성이 아니라 **데이터 출처의 적법성과 조용한 실패**에 있으며, 이 둘을 먼저 정리하지 않으면 스케줄을 아무리 다듬어도 서비스 전체가 한 번에 멈출 수 있습니다.

## 0. 스케줄링보다 먼저 처리해야 할 3가지

### 0-1. 선언한 데이터 원칙이 이미 무너져 있습니다 [최우선]

요청서에는 "공식 API, 공공데이터, 공식 CSV만 사용하고 화면 수집은 하지 않는다"고 되어 있으나, 현재 코드는 그렇지 않습니다.

`scripts/refresh_fees.py`는 `finance.naver.com/item/coinfo.naver`의 HTML을 파싱해 펀드보수를 추출합니다. 요청 헤더에 `User-Agent: Mozilla/5.0`을 넣어 브라우저인 것처럼 보내고, `ThreadPoolExecutor`로 전 종목을 동시 요청합니다. 커밋 이력에도 `feat: add daily ETF fee scraper via Naver Finance`, `data: refresh ETF fees via Naver crawler`가 그대로 남아 있습니다.

가격 백필 경로도 마찬가지입니다. 커밋 `fix: switch backfill script to use Naver fchart API to bypass KRX blocking`이 보여 주듯, KRX 차단을 만나자 `fchart.stock.naver.com/sise.nhn`이라는 비공식 내부 엔드포인트로 우회했습니다.

문제는 세 가지입니다. 첫째, 네이버 금융 데이터는 네이버가 제3자로부터 공급받아 자사 서비스에 제공하는 것이며, 이를 크롤링해 상업적 웹서비스에 재배포하는 것은 네이버 이용약관 위반 소지가 큽니다. 둘째, 브라우저 위장과 차단 우회는 분쟁 발생 시 고의성 정황으로 읽힙니다. 셋째, 기술적으로도 비공식 엔드포인트는 예고 없이 사라지므로 서비스의 단일 장애점입니다. GitHub Actions의 공용 IP 대역은 차단 대상이 되기 쉬워, KRX에서 이미 겪은 일이 네이버에서 반복될 가능성이 높습니다.

권고는 이렇습니다. 총보수는 네이버 대신 공공데이터포털 금융위원회 계열 API나 금융투자협회 전자공시 같은 공식 경로로 대체 가능한지 먼저 조사하십시오. 대체 경로가 없으면 총보수 항목을 화면에서 잠정 제거하는 편이, 출처를 밝힐 수 없는 값을 계속 노출하는 것보다 안전합니다. 가격 백필도 네이버 fchart를 걷어내고 공공데이터포털 경로로 돌아가야 합니다.

### 0-2. KRX Open API 키가 상업 서비스에서 쓰이고 있습니다

`daily-market.yml`은 `KRX_OPEN_API_KEY`를 세 개 스텝에 주입합니다. KRX Data Marketplace OPEN API 이용약관(2025년 12월 26일 시행) 제6조 제2항은 "비상업적인 목적으로만 이용할 수 있으며"라고 명시하고, 제11조 제2항은 제공받은 정보의 제3자 제공을 금지합니다. 제10조 제3항은 화면에 한국거래소 통계정보 사용 사실을 명시하도록 요구합니다.

또한 약관 제8조 제4항은 키당 1일 10,000회 제한을 둡니다. 아래 0-3에서 설명하는 재시도 구조 때문에 실제 호출량이 필요량의 약 4배로 나가고 있어, 한도 여유가 불필요하게 줄어듭니다.

공공데이터포털 금융위원회 계열 API로 대체 가능한 항목은 모두 옮기고, KRX 키 의존을 단계적으로 제거하는 것을 권합니다.

### 0-3. 재시도 사다리가 성공 후에도 전체 수집을 반복합니다

`daily-market.yml`의 주석은 "새 데이터를 찾은 첫 실행이 커밋하고, 이후 실행은 no-op으로 조기 종료한다"고 설명하지만 실제 스텝 순서는 그렇지 않습니다. 06:13에 성공해도 07:13, 08:13, 09:13 실행은 checkout, Python 설치, 의존성 설치, `update_daily_data.py` 전체 수집을 그대로 다시 수행합니다. 조기 종료는 수집이 끝난 뒤 커밋 단계에서만 일어납니다.

즉 정상적인 날에도 외부 API 호출이 4배로 나갑니다. 수정은 간단합니다. 수집 스텝 앞에 이미 목표 거래일 데이터를 보유했는지 판정하는 가드 스텝을 두고, 보유 중이면 이후 스텝 전체를 `if`로 건너뛰게 하십시오.

```yaml
- name: Short-circuit when the target close is already committed
  id: guard
  run: |
    python scripts/check_data_freshness.py && echo "done=true" >> "$GITHUB_OUTPUT" || echo "done=false" >> "$GITHUB_OUTPUT"

- name: Refresh official ETF data
  if: steps.guard.outputs.done != 'true'
  ...
```

이 한 가지 변경으로 외부 API 호출량, Actions 실행 시간, 차단 위험이 동시에 약 4분의 1로 줄어듭니다.

## 1. 효율성 검토

### 1-1. 3분 간격 스태거는 의존성 관리 수단이 될 수 없습니다

`daily-market`은 :13, `daily-distribution`은 :16, `daily-fees`는 :19에 시작합니다. 그런데 `daily-market`은 데이터 변경이 감지되면 `npm ci`, `python -m unittest`, `npm test`, `npm run build`를 순차 실행합니다. 이 구간만으로도 3분을 넘기는 것이 정상이며, timeout은 30분으로 잡혀 있습니다. 결과적으로 세 워크플로는 거의 매일 동시 실행됩니다.

시간 오프셋은 "보통은 안 겹치겠지"라는 기대일 뿐 보장이 아닙니다. 최근 커밋 이력에 하루 동안 `ci: offset daily schedules to bypass top-of-hour congestion and run sequentially`, `ci: align daily-fees schedule with staggered market and distribution updates` 등 스케줄 조정이 반복된 것은, 근본 결합 문제를 시간 오프셋으로 덮고 있다는 신호로 보입니다.

선택지는 둘입니다. 세 작업 사이에 실제 데이터 의존이 있다면 단일 워크플로의 순차 job으로 합치거나 `workflow_run` 트리거로 체이닝하십시오. 의존이 없다면 오프셋을 3분이 아니라 30분 이상으로 벌리고, 아래 1-2의 push 안전장치를 반드시 넣으십시오.

### 1-2. git push 경합이 방치되어 있습니다

세 워크플로 모두 같은 브랜치에 `git push`를 하는데, 어디에도 `git pull --rebase`가 없습니다. 동시 실행 시 뒤에 push하는 쪽이 non-fast-forward로 실패합니다. `concurrency` 그룹은 `daily-market.yml`에만 설정되어 있고 나머지 둘에는 없어, 워크플로 간 직렬화도 이루어지지 않습니다.

최소 조치는 두 가지입니다. 세 워크플로에 동일한 `concurrency` 그룹을 부여해 데이터 커밋을 직렬화하고, push를 재시도 가능한 형태로 감싸십시오.

```yaml
concurrency:
  group: etf-data-commit
  cancel-in-progress: false
```

```bash
for i in 1 2 3; do
  git pull --rebase --autostash && git push && break
  sleep 5
done
```

### 1-3. `daily-fees.yml`에 쓰기 권한 선언이 없습니다

`daily-market.yml`과 `daily-distribution.yml`에는 `permissions: contents: write`가 있으나 `daily-fees.yml`에는 없습니다. 리포지토리 기본 토큰 권한이 read로 설정되어 있으면 push 단계에서 실패합니다. 지금 동작하고 있다면 리포 기본값이 read/write라는 뜻이며, 이는 다른 워크플로에도 필요 이상의 권한이 열려 있다는 의미이기도 합니다. 명시적으로 선언하는 편이 안전합니다.

### 1-4. 실행 환경이 워크플로마다 다릅니다

Python 버전이 market과 distribution은 3.13, fees는 3.11입니다. 의존성도 각각 `beautifulsoup4 certifi requests xlrd`와 `beautifulsoup4 lxml requests`로 인라인 나열되어 있고 버전 고정이 없습니다. 어느 날 상위 패키지의 파괴적 변경이 배포되면 아무 코드 변경 없이 파이프라인이 깨집니다.

`requirements.txt`를 하나 만들어 버전을 고정하고, 세 워크플로가 동일한 Python 버전과 동일한 파일을 참조하게 하십시오. 동시에 `setup-python`의 캐시를 켜면 실행당 20초에서 40초가 절약됩니다. 하루 12회 기준으로는 무시할 수 없는 양입니다.

```yaml
- uses: actions/setup-python@v5
  with:
    python-version-file: ".python-version"
    cache: pip
```

### 1-5. 커밋 분산이 재빌드 횟수를 늘립니다

세 워크플로가 각자 커밋하므로 하루에 최대 세 번 Cloudflare Pages 재빌드가 발생합니다. 데이터 신선도 관점에서 세 번 배포할 이유가 없다면, 커밋은 모으고 배포는 하루 한 번으로 묶는 편이 빌드 쿼터와 캐시 효율 모두에 유리합니다.

### 1-6. 에러 격리 관점의 평가

분리 자체는 옳은 판단입니다. 크롤링 기반인 분배금·수수료 수집이 실패해도 시세 갱신은 살아남아야 하며, 현재 구조는 그 목적을 달성합니다. 다만 격리의 근거가 "워크플로가 분리되어 있어서"가 아니라 "실행 시각이 다를 것 같아서"에 머물러 있는 것이 문제입니다. 1-1과 1-2를 적용하면 분리의 이점은 유지하면서 결합 위험만 제거할 수 있습니다.

## 2. 효과성 검토

### 2-1. 시장 데이터의 무결성 전략은 잘 설계되어 있습니다

`check_data_freshness.py`로 신선도를 판정하고, 스테일이면 마지막에 `exit 1`로 실패 표시를 남겨 "green인데 실제로는 옛 데이터"라는 최악의 상태를 방지한 설계는 정확합니다. 조용히 성공하는 파이프라인이 가장 위험하다는 점을 이미 인지하고 계신 것으로 보입니다.

### 2-2. 그런데 분배금과 수수료에는 같은 장치가 없습니다

`daily-distribution.yml`은 진단 리포트를 요약에 쓰고 아티팩트로 올리지만, 수집 실패 자체를 워크플로 실패로 만들지 않습니다. `daily-fees.yml`은 더 취약합니다. `refresh_fees.py`의 수집 함수가 `except Exception: pass`로 모든 예외를 삼키고 `None`을 반환하기 때문입니다.

네이버가 IP를 차단하거나 마크업을 바꾸면 전 종목 수수료가 조용히 `None`이 되고, 변경 사항이 없으니 커밋도 없고, 워크플로는 초록색으로 끝납니다. 화면에는 옛 수수료가 언제까지고 남습니다. 이것이 지금 파이프라인에서 가장 발견하기 어려운 실패 유형입니다.

최소 조치는 수집 성공률 임계선을 두는 것입니다.

```python
success_rate = collected / max(total, 1)
if success_rate < 0.9:
    raise SystemExit(f"fee collection degraded: {collected}/{total}")
```

분배금 워크플로도 진단 리포트의 `failed` 건수가 임계치를 넘으면 실패로 종료하도록 바꾸십시오.

### 2-3. 재시도 사다리의 실패 등급이 구분되지 않습니다

06:13 실패와 09:13 실패는 의미가 다릅니다. 앞의 셋은 "아직 안 나왔다"이고 마지막 하나는 "오늘은 못 받았다"입니다. 지금은 넷 다 동일하게 빨간색으로 표시되어, 정상적인 지연에도 알림이 반복되고 결국 알림을 무시하게 됩니다.

`github.event.schedule` 값으로 마지막 rung을 식별해, 중간 rung은 경고로만 남기고 마지막 rung에서만 실패 처리하십시오. 휴장일 미등록으로 하루 4회 실패 메일이 오는 현재 상황도 함께 해소됩니다.

### 2-4. 휴장일 관리가 수동입니다

`data/market_holidays.txt`를 사람이 관리하는 구조라, 미등록 휴장일마다 알림이 한 번씩 발생합니다. 워크플로 주석에도 그렇게 적혀 있습니다. 공공데이터포털의 특일 정보 API로 연 1회 자동 갱신하면 이 잡음이 사라집니다.

### 2-5. 알림 경로가 GitHub 이메일뿐입니다

브리핑 발송용 Cloudflare Workers를 이미 운영 중이므로, 파이프라인 실패 시 동일 경로로 운영자에게 알림을 보내는 것은 추가 비용이 거의 없습니다. 최종 rung 실패, 수집 성공률 임계선 미달, 3거래일 연속 실패 세 가지만 알림 대상으로 두면 충분합니다.

## 3. 웹사이트 속도 검토

### 3-1. 사전 빌드 방식의 이점

이 서비스에는 정적 사전 빌드가 구조적으로 잘 맞습니다. 데이터가 하루 한 번만 바뀌는 읽기 전용 서비스이므로 요청마다 DB를 조회할 이유가 없습니다. 요청은 CDN 엣지에서 끝나 TTFB가 최소화되고, DB 커넥션 풀이나 콜드 스타트 문제가 존재하지 않으며, 트래픽이 급증해도 비용과 지연이 선형으로 증가하지 않습니다. 주 유입 채널이 Threads 인앱 브라우저라는 점을 감안하면 이 이점은 더 큽니다. 모바일 인앱 브라우저는 네트워크 조건이 나쁜 경우가 많아 서버 렌더링 지연이 체감으로 직결됩니다. 보안 공격면이 정적 자산 수준으로 축소되는 것도 1인 운영에서는 실질적 이득입니다.

### 3-2. 한계와 현재 상태의 불일치

한계는 세 가지입니다. 첫째, 빌드 시간이 종목 수에 비례합니다. 전 종목 상세 페이지를 정적 생성하면 이미 1천 페이지 규모이고, 여기에 미국 자산군이 더해지면 빌드가 파이프라인의 새로운 병목이 됩니다. 둘째, 데이터 정정 반영이 재배포에 묶입니다. 오류를 발견해도 즉시 고칠 수 없습니다. 셋째, 잘못된 데이터가 커밋되면 그대로 배포됩니다. 현재 `npm test`와 `npm run build`가 게이트 역할을 하고 있으나, 이는 형식 오류를 잡을 뿐 값의 타당성은 검증하지 않습니다.

더 중요한 지적이 있습니다. 설계 기준서 `ETF_Platform_Design_Baseline_20260716.md` 제10-A.7은 Phase 1을 데이터베이스 없는 완전 정적 구조로 규정했지만, 현재 파이프라인에는 D1 적재 스텝(`backfill_api.py`, `validate_d1_status.py`, `PRICE_INGEST_ENDPOINT`)이 있고 커밋 이력에는 Supabase 인증 코드가 다수 들어와 있습니다. 즉 이미 정적 원칙을 벗어난 하이브리드 상태입니다.

이 자체가 잘못은 아닙니다. 다만 설계 문서가 현실과 어긋난 채 방치되면, 앞으로의 판단 기준이 사라집니다. 문서를 현행 구조에 맞게 개정하거나, 정적 원칙으로 되돌릴 범위를 명시적으로 결정하십시오. 특히 D1과 Supabase 두 저장소를 동시에 두는 이유가 무엇인지, 하나로 합칠 수 있는지 점검할 시점으로 보입니다.

### 3-3. 권고

전 종목 상세 페이지는 완전 정적 생성 대신 ISR이나 온디맨드 생성으로 전환하는 것을 검토하십시오. 접근이 몰리는 상위 종목만 사전 생성하고 나머지는 첫 요청 시 생성해 캐시하면, 빌드 시간이 종목 수에서 분리됩니다. 대시보드와 브리핑처럼 모든 방문자가 보는 페이지는 지금처럼 완전 정적으로 유지하는 것이 맞습니다.

## 4. 확장성 검토

### 4-1. 현재 구조의 확장 한계

지금은 데이터 종류가 하나 늘 때마다 워크플로 파일이 하나 늘고, 스케줄 오프셋을 손으로 조정하고, 커밋 경합 지점이 하나 더 생깁니다. 자산군까지 늘어나면 워크플로 수가 소스 수와 자산군 수의 곱으로 증가합니다. 이미 3개 워크플로에서 스케줄 조정을 하루에 네 번 반복한 것을 보면, 이 방식은 5개에서 6개를 넘기기 어렵습니다.

### 4-2. 권장 구조: 수집기 표준화와 매트릭스 실행

수집 로직을 공통 인터페이스로 맞추고, 워크플로는 오케스트레이터 하나로 줄이는 방향을 권합니다. 각 수집기가 동일한 계약(입력은 목표일, 출력은 표준 결과 객체와 성공률, 실패 시 예외)을 지키면 워크플로는 매트릭스로 돌리기만 하면 됩니다.

```yaml
jobs:
  collect:
    strategy:
      fail-fast: false
      matrix:
        collector: [market, distribution, fees]
    steps:
      - run: python -m collectors.${{ matrix.collector }}
      - uses: actions/upload-artifact@v4

  commit:
    needs: collect
    steps:
      - uses: actions/download-artifact@v4
      - run: git add data && git commit && git push
```

이 구조의 이점은 세 가지입니다. `fail-fast: false`로 수집기 간 에러 격리가 시간 오프셋이 아니라 구조로 보장됩니다. 커밋 지점이 하나로 모이므로 push 경합이 원천 제거되고 재빌드도 하루 한 번으로 정리됩니다. 새 데이터 소스 추가가 매트릭스 항목 한 줄 추가로 끝납니다.

### 4-3. 미국 자산군 추가 시 고려사항

미국 시장은 마감 시각이 다릅니다. 미 동부 기준 장 마감은 한국시간 익일 새벽이므로, 현재의 한국시간 아침 사다리에 그대로 얹을 수 없습니다. 시장별로 스케줄 축을 분리하되 커밋 지점은 공유하는 형태가 자연스럽습니다.

또한 미국 지수와 종목 데이터는 국내 공공데이터와 이용조건이 근본적으로 다릅니다. 지수값은 지수 제공기관의 지식재산이고 공개 웹 표시는 통상 별도 계약 대상입니다. 자산군 확장의 실질적 제약은 기술이 아니라 라이선스이므로, 아키텍처 설계보다 이용조건 확인을 먼저 끝내십시오.

### 4-4. Actions 사용량 한계 확인 필요

현재 하루 12회 실행이며, 데이터 변경이 있는 날의 market 워크플로는 `npm ci`와 빌드까지 포함해 실행 시간이 깁니다. 리포지토리가 private이면 무료 한도 월 2,000분에 근접하거나 초과할 수 있습니다. public이면 무제한이므로 문제가 없습니다. 어느 쪽인지 확인하고, private이라면 0-3의 조기 종료 가드가 비용 측면에서도 최우선 과제가 됩니다.

## 5. 우선순위 실행 목록

### P0: 이번 주

첫째, 네이버 크롤링 의존(수수료 수집, fchart 백필)의 대체 경로를 조사하고, 대체 불가하면 해당 항목의 화면 노출을 잠정 중단하십시오. 둘째, `refresh_fees.py`의 `except Exception: pass`를 제거하고 수집 성공률 임계선을 도입하십시오. 셋째, 재시도 사다리에 조기 종료 가드를 넣어 외부 API 호출량을 4분의 1로 줄이십시오.

### P1: 2주 내

세 워크플로에 동일 `concurrency` 그룹을 부여하고 push를 `pull --rebase` 재시도로 감싸십시오. `daily-fees.yml`에 `permissions`를 명시하십시오. `requirements.txt`로 의존성과 Python 버전을 통일하고 pip 캐시를 켜십시오. 마지막 rung에서만 실패 처리하도록 알림 등급을 분리하십시오.

### P2: 1개월 내

수집기 인터페이스를 표준화하고 매트릭스 오케스트레이터로 통합하십시오. 종목 상세 페이지를 ISR로 전환해 빌드 시간을 종목 수에서 분리하십시오. 설계 기준서를 현행 하이브리드 구조에 맞게 개정하거나 정적 원칙 복귀 범위를 결정하십시오. D1과 Supabase의 역할 중복 여부를 점검하십시오.
