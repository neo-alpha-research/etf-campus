성격: 현황 정리. 개별 지시서 16건의 결과를 한 문서로 요약합니다.

## 1. 이번 작업에서 확정된 사실

다음은 실측으로 확인된 내용입니다. **앞으로 이 항목들을 다시 가정하거나 재조사하지 마십시오.**

**저장소 구조.** 커뮤니티 회원·게시글·댓글은 Supabase(PostgreSQL)에 있고, ETF 가격·브리핑·관리자 인증은 Cloudflare D1에 있습니다. 게시글 생성은 `create_community_post` RPC를 경유하므로 필드 추가 시 Postgres 함수 자체를 수정해야 합니다.

**Cloudflare Pages는 저장소와 연동되어 있습니다.** production branch는 `main`, preview는 전체 브랜치, `build_command`는 `npm run build`, `destination_dir`는 `out`입니다. 이번 달 빌드 25회로 월 500회 한도에 여유가 큽니다. **사이트 갱신에 GitHub Actions가 필요 없습니다.**

**D1 잠금 문제는 존재하지 않았습니다.** `market_data_readiness`에는 `processing` 상태를 쓰는 코드가 없고, `market_source_consumer_runs`의 `processing`은 다음 실행이 재점유하므로 영구 잠금이 아닙니다. 매니페스트의 고아 `collecting` 행은 조회 대상이 아니라 파이프라인을 막지 않습니다. `0009` 마이그레이션은 취소되었습니다.

**진짜 원인은 스케줄이었습니다.** 예약 실행이 KST 06:07과 07:07이었는데 실제 데이터 도달은 08:08 이후였습니다. 관측된 4일 모두 마지막 예약 실행보다 늦게 도착했습니다. 그래서 매일 수동 개입이 필요했고, 수동 실행이 Actions 한도를 소진했으며, 한도가 소진되자 감시 장치까지 함께 죽었습니다.

**조기 종료 가드는 작동하지 않았습니다.** `steps.guard.outputs.already_run`을 참조하는 조건들만 있고 `id: guard` 스텝 정의가 없어, 모든 실행이 매번 전체 수집을 수행했습니다.

**Actions 소모 실측.** 이번 달 2,110분(한도 2,000분). 배포 워크플로가 1,545분으로 73.2퍼센트를 차지하며, 215회 전부 수동 실행입니다. 이 워크플로는 `workflow_dispatch` 트리거만 있어 경로 필터를 적용할 대상이 없습니다.

## 2. 완료된 변경

**스케줄 재설계.** `daily-market`을 KST 08:07, 09:07, 10:07, 11:07, 12:07 다섯 단계로 옮겼습니다. `daily-distribution`은 13:07, `daily-fees`는 13:22로 하루 한 번씩만 실행합니다. 모니터는 14:15입니다.

**동시성 그룹 분리.** 세 워크플로가 공유하던 `daily-etf-data` 그룹 때문에 대기 중 실행이 취소되던 문제를 해결했습니다. 각각 고유 그룹을 갖습니다.

**사전 확인 도입.** `scripts/check_source_ready.py`가 수집 전에 원본에 전일 데이터가 있는지 확인합니다. 없으면 즉시 종료하므로 헛도는 단계의 비용이 몇 분에서 몇 초로 줄었습니다. 거래일 판정은 `scripts/trading_days.py`로 분리해 `check_data_freshness.py`와 공유합니다.

**가드 스텝 실제 구현.** `id: guard` 스텝을 만들고, `skip`과 `skip_reason`으로 "이미 성공"과 "원본 미공개"를 구분합니다. 최종 단계 판정은 `FINAL_RETRY_UTC_HOUR` 환경변수로 분리해 크론과 함께 관리합니다.

**경량 CI 신설.** `ci-fast.yml`(모든 푸시, 빌드 제외, 2분 목표)과 `ci-full.yml`(main 대상 PR, 빌드 포함)을 분리하고 양쪽에 `cancel-in-progress: true`를 적용했습니다. **아직 실행 검증은 하지 못했습니다.**

**감시 Worker 구축.** `workers/market-daily-monitor`에 감시 기능과 공개 시각 측정 프로브를 함께 넣었습니다. 판정은 번들 휴장일 사본으로 하고, 공개 경로의 원본과 비교해 다르면 별도 Issue를 만듭니다. 기존 Actions 모니터는 삭제하지 않고 병존시킵니다.

**인코딩 복구.** 커뮤니티 API 6개 파일의 손상된 한글 문자열을 UTF-8로 복구했습니다.

## 3. 운영자가 직접 해야 할 일

### 3-1. GitHub 결제 화면 확인

Actions 무료 한도의 실제 초기화 시점을 확인해 주십시오. 계정 생성일 기준 매월 26일이라는 추정이 있으나 확인되지 않았습니다.

초기화가 임박했다면 그대로 기다리면 되고, 다음 달 1일이라면 지출 한도를 소액으로 설정해 즉시 복구하는 방안을 검토할 수 있습니다. Linux 러너 초과 단가는 분당 0.008달러 수준입니다.

### 3-2. PAT 발급과 Worker 배포

GitHub에서 Fine-grained Personal Access Token을 발급하십시오.

Repository access는 `neo-alpha-research/etf-campus` 단일 저장소로 제한하고, Permissions는 **`Issues: Read and write` 하나만** 부여하십시오. `Contents` 권한은 필요 없습니다.

만료 기간은 허용되는 최대치로 설정하고, **발급 직후 `workers/market-daily-monitor/README.md`의 만료 예정일 란에 날짜를 기록하십시오.** 만료되면 감시 장치가 조용히 멈춥니다.

이후 아래를 실행하십시오.

```
cd workers/market-daily-monitor
npm install
npx wrangler secret put MONITOR_GITHUB_TOKEN
npx wrangler secret put KRX_OPEN_API_KEY
npm run deploy
```

### 3-3. 빈 폴더 정리

이전 작업에서 남은 `D:\Archive` 빈 폴더는 마운트 지점이라 도구로 삭제되지 않습니다. Windows 탐색기에서 직접 지우셔야 합니다.

## 4. 조건별 대기 과제

### 4-1. Worker 배포 후

배포된 Worker가 실제로 동작하는지 확인합니다. 정상 판정, 실패 시 Issue 생성, 휴장일 불일치 감지 세 가지입니다.

### 4-2. Actions 한도 복구 후

배포 워크플로를 경량화합니다. `validate`와 `deploy_pages`가 같은 빌드를 두 번 수행하므로 artifact로 넘기고, 다섯 job을 셋으로 줄이며, `npx --yes wrangler@4.124.0` 반복 다운로드를 devDependency 고정으로 바꿉니다.

CI 워크플로의 실제 실행 시간과 `cancel-in-progress` 동작을 검증합니다. 현재 미검증 상태입니다.

**그리고 작업 습관을 바꿔야 합니다.** 코드 검증 목적으로 프로덕션 배포 워크플로를 실행하지 마십시오. 이번 달 215회 수동 실행의 대부분이 그 용도였고 전체 비용의 73퍼센트였습니다. 도구를 만들어도 습관이 남으면 절감은 일어나지 않습니다.

### 4-3. 2주 측정 완료 후

프로브가 기록한 원본 공개 시각 분포를 확인해 `daily-market`의 단계 수와 시작 시각을 확정합니다. 다섯 단계는 잠정치이며 실제 공개 시각이 이르면 두세 단계로 줄이고 시작을 앞당길 수 있습니다.

**이때 `FINAL_RETRY_UTC_HOUR`도 반드시 함께 조정하십시오.** 크론만 바꾸면 최종 단계 판정이 어긋나 데이터 미도착이 보고되지 않습니다.

측정이 끝나면 프로브 크론을 제거하십시오. 상시 기능이 아닙니다.

## 5. 보류 중인 별도 과제

정부 지원 서버(Rocky Linux VM) 이전은 **우선순위를 낮춥니다.** 근본 원인이 스케줄 문제로 확인되었으므로 파이프라인이 자동으로 완료되면 수동 실행이 사라지고 Actions 소모가 크게 줄어듭니다. 서버는 대체재가 아니라 감시 이중화나 백오피스 용도로 검토하면 됩니다. `scripts/run_daily_market.sh`는 이미 준비되어 있으므로 필요해지면 언제든 착수할 수 있습니다.

커뮤니티와 30일 챌린지 구현은 별도 트랙입니다. `docs/Community_Agent_Handoff_Challenge30_20260821.md`가 단일 진실이며, Phase 0(인코딩 복구)은 이번 작업에서 함께 처리되었습니다.

## 6. 작업 방식에 대한 기록

이번 국면에서 반복된 오류 유형과 그에 대응해 도입한 규칙입니다. 앞으로도 유지하십시오.

**조사 게이트.** 구현 전에 실측 조사를 먼저 시키고 보고를 받은 뒤 착수를 지시하는 방식입니다. 이 게이트 덕분에 불필요한 마이그레이션과 잘못된 대상 수정을 여러 번 막았습니다.

**옮겨 적기 금지.** 원본을 눈으로 읽고 다시 타이핑하는 과정에서 두 번 치명적 오류가 났습니다(존재하지 않는 파일명, `f"`가 `fb`로 깨짐). 원문 복사와 기계적 검증을 요구하십시오.

**확인과 추론의 구분.** 측정하지 않은 것에 "확인되었습니다"를 쓰지 않도록 명시적으로 요구해야 합니다.

**완료 증빙.** `git diff --stat`은 커밋되지 않은 변경도 출력하므로 완료 증거가 아닙니다. `git log --oneline`과 `git status --porcelain`을 함께 요구하십시오.

**잔재 금지.** 임시 파일이 작업 트리에 남는 일이 네 차례 있었습니다. `.gitignore` 보강과 함께 매 보고에서 `git status` 확인을 요구하십시오.
