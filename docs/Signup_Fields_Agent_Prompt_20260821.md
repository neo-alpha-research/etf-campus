# ETF Campus 에이전트 지시: 회원가입 수집 항목 개편

작성일: 2026-08-21
발신: EVS Navigator
수신: ETF Campus 에이전트
용도: 아래 구분선 안의 전문을 그대로 전달하십시오.

---

당신은 ETF Campus의 회원가입 수집 항목을 개편합니다. 목표는 **가입 이탈을 최소화하면서 향후 마케팅에 실제로 쓰이는 데이터만 확보**하는 것입니다. 아래 설계를 그대로 반영하십시오.

## 0. 현재 상태 (착수 전 반드시 확인)

커뮤니티는 Supabase를 사용하며 프로필은 RPC로 다룹니다. 확인된 사실은 다음과 같습니다.

- `bootstrap_community_profile(p_public_nickname)` 은 현재 닉네임 하나만 받습니다.
- `get_community_profile()` 은 `public_nickname`, `interest_account_type`, `investment_experience`, `role` 을 반환합니다. 즉 **`interest_account_type` 과 `investment_experience` 컬럼은 이미 존재하지만 가입 과정에서 채워지지 않고 있습니다.**
- `validateChallengeApplication` 이 `interestAccountType` 을 다시 받고 있어 중복 수집 구조입니다.

착수 전에 Supabase 실제 스키마(프로필 테이블 컬럼, 두 RPC 함수 정의)를 조회해 위 내용을 검증하고, 그 결과를 근거로 작업하십시오. 추측으로 진행하지 마십시오.

## 1. 설계 원칙

**최소 수집.** 가입 화면에서 받는 필수 항목은 서비스 제공에 반드시 필요한 것으로 한정합니다. 개인정보보호법상 최소수집 원칙이며, 실무적으로도 필수 입력이 늘어날수록 가입 완료율이 떨어집니다.

**단계적 프로파일링.** 모든 정보를 가입 시점에 받지 않습니다. 가입은 최소로 끝내고, 나머지는 맥락이 생겼을 때 나눠서 받습니다. 이용자가 서비스 가치를 경험한 뒤에 묻는 편이 응답률이 높습니다.

**필수와 선택의 명확한 구분.** 선택 항목에 동의하지 않아도 가입과 서비스 이용이 가능해야 합니다. 선택 항목 미입력을 이유로 기능을 막지 마십시오.

**받지 않는다는 결정도 설계입니다.** 아래 §4의 금지 항목은 마케팅 가치가 있어 보여도 수집하지 않습니다.

## 2. 3단계 수집 구조

### 1단계: 가입 화면 (필수 4개)

| 항목 | 형식 | 목적 |
|---|---|---|
| 이메일 | 텍스트, 이중 확인 | 계정 식별, 인증, 뉴스레터 발송 |
| 비밀번호 | 텍스트 | 인증 |
| 닉네임 | 2~24자, 기존 `validateNickname` 규칙 | 커뮤니티 표시 |
| 필수 동의 | 체크박스 | 이용약관, 개인정보 수집·이용 |

가입 화면에서 받는 것은 이 넷이 전부입니다. 실명, 생년월일, 휴대폰 번호는 받지 않습니다.

**마케팅 수신 동의는 별도 체크박스로 분리해 선택 항목으로 둡니다.** 필수 동의와 한 덩어리로 묶지 마십시오. 정보통신망법상 광고성 정보 전송에는 별도 동의가 필요하며, 묶어서 받으면 동의 자체가 무효가 될 수 있습니다.

### 2단계: 가입 직후 온보딩 (선택 2문항, 건너뛰기 가능)

가입 완료 직후 1회만 노출하는 화면입니다. **건너뛰기 버튼을 반드시 상단에 두십시오.** 건너뛰어도 정상 회원이며, 나중에 프로필 화면에서 언제든 입력할 수 있어야 합니다.

| 항목 | 선택지 | 컬럼 |
|---|---|---|
| 연령대 | 20대 / 30대 / 40대 / 50대 / 60대 이상 | `age_band` (신규 추가 필요) |
| 퇴직연금 유형 | DC형 / DB형 / IRP / 둘 다 보유 / 없음 / 모름 | `interest_account_type` (기존 컬럼 활용) |

이 둘만 받는 이유는 명확합니다. 두 항목이 이 사업에서 세그먼트 가치가 가장 높고, 각각 한 번의 탭으로 끝나 이탈 비용이 거의 없습니다.

연령대는 커뮤니티 프로필 뱃지에도 사용하기로 이미 결정된 항목이므로 별도 수집 없이 재사용됩니다. 퇴직연금 유형은 이 서비스에서 가장 강력한 세그먼트입니다. DC형 보유자가 핵심 타겟이므로 콘텐츠 추천, 뉴스레터 분기, 광고 타겟 검증에 직접 쓰입니다.

`interest_account_type` 의 허용값은 기존 `CHALLENGE_ACCOUNT_TYPES`(`dc`, `irp`, `both`, `unknown`, `none`)와 정합시키되 `db` 를 추가하십시오. 값 체계를 두 곳에서 다르게 두지 마십시오.

### 3단계: 맥락 발생 시 (선택)

가입 흐름에 넣지 말고 해당 기능을 쓸 때 받습니다.

| 항목 | 수집 시점 | 컬럼 |
|---|---|---|
| 투자 경력 | 챌린지 신청 화면 | `investment_experience` (기존 컬럼) |
| 관심 주제 | 뉴스레터 설정 화면, 다중 선택 | 신규 (연금, 배당, 지수·자산배분, 절세) |

**챌린지 신청 화면의 `interestAccountType` 은 프로필 값을 자동으로 불러와 채우고, 이용자는 확인 또는 수정만 하게 하십시오.** 같은 질문을 두 번 묻는 현재 구조를 제거해야 합니다.

## 3. 유입 경로는 묻지 마십시오

"어떻게 알게 되셨나요"는 마케팅 ROI 측정에 유용해 보이지만 응답 정확도가 낮고 문항 하나만큼 이탈을 만듭니다.

대신 **UTM 파라미터를 가입 시점에 서버가 자동 기록하십시오.** Threads에 싣는 모든 링크에 UTM을 부착하는 것은 이미 발행 SOP에 강제되어 있으므로, 랜딩 진입 시 UTM을 세션에 보관했다가 가입 완료 시 프로필에 함께 저장하면 됩니다. 이용자에게 묻지 않고도 더 정확한 데이터를 얻습니다.

인앱 브라우저에서 리퍼러가 소실되는 경우를 대비해, UTM이 없으면 `direct` 로 기록하고 별도 처리하지 마십시오.

## 4. 수집하지 않을 항목 (명시적 금지)

아래는 마케팅 가치가 있어 보여도 수집하지 않습니다.

**실명, 생년월일 전체, 휴대폰 번호, 주소.** 본인확인이 필요한 기능이 없으므로 수집 근거가 없습니다. 유출 시 피해 규모만 키웁니다.

**자산 규모, 연봉, 투자 금액.** 세 가지 이유로 금지합니다. 첫째, 가입 이탈률이 급격히 올라갑니다. 둘째, 커뮤니티 설계 원칙과 정면으로 충돌합니다. 이 서비스는 비교 축을 자산이 아니라 성실성에 두기로 했으며, 자산 데이터를 보유하는 순간 그 원칙이 흔들립니다. 셋째, 민감도가 높아 유출 시 신뢰 손상이 회복 불가능합니다.

**재직 회사명, 업종.** 회원 수가 적을 때 연령대와 결합하면 개인 식별이 가능합니다. 업종은 커뮤니티 회원 300명 이후에 재검토하기로 이미 정해져 있습니다.

**주민등록번호를 포함한 고유식별정보.** 어떤 경우에도 수집하지 마십시오.

## 5. 법적 요건 (반드시 반영)

**동의 항목을 분리하십시오.** 이용약관 동의, 개인정보 수집·이용 동의(필수), 마케팅 정보 수신 동의(선택) 세 가지를 각각 별도 체크박스로 두고, 전체 동의 체크박스를 두더라도 개별 해제가 가능해야 합니다.

**개인정보 처리방침에 다음을 명시하십시오.** 수집 항목을 필수와 선택으로 구분해 나열하고, 각 항목의 이용 목적과 보유 기간을 적습니다. 특히 **광고 플랫폼에 이메일 해시를 업로드해 맞춤 광고 대상을 구성할 계획이 있다면, 그 사실과 대상 플랫폼을 처리방침에 사전에 명시해야 합니다.** 처리방침에 없는 활용은 나중에 문제가 됩니다.

**만 14세 미만 가입을 차단하십시오.** 연령대 항목이 선택이므로 별도의 확인 체크박스가 필요합니다. 만 14세 이상임을 확인하는 필수 동의 항목을 두십시오.

**동의 이력을 저장하십시오.** 동의 시각, 동의한 약관 버전, 항목별 동의 여부를 기록해야 분쟁 시 입증이 가능합니다. 기존 챌린지 신청에 `privateRecordConsentVersion` 이 있으므로 같은 방식을 가입에도 적용하십시오.

**철회 경로를 제공하십시오.** 마케팅 수신 동의는 프로필 화면에서 언제든 해제할 수 있어야 하고, 모든 발송 메일에 즉시 해지 링크가 있어야 합니다. 선택 항목 입력값도 프로필에서 삭제할 수 있어야 합니다.

## 6. 구현 범위

**Supabase 스키마.** 프로필 테이블에 `age_band`, `marketing_consent`, `marketing_consent_at`, `terms_version`, `signup_utm_source`, `signup_utm_medium`, `signup_utm_campaign` 을 추가합니다. `interest_account_type` 허용값에 `db` 를 추가합니다.

**RPC 확장.** `bootstrap_community_profile` 이 닉네임 외에 동의 관련 값과 UTM을 함께 받도록 확장합니다. 온보딩 2문항은 별도 RPC(예: `update_community_profile_onboarding`)로 분리해 건너뛰기가 자연스럽게 동작하게 하십시오.

**검증 로직.** `contracts.ts` 에 `validateSignupInput` 과 `validateOnboardingInput` 을 추가합니다. 기존 `validateNickname` 을 재사용하고, 선택 항목은 미입력을 허용해야 합니다. 허용값 목록은 상수로 정의해 챌린지 신청 검증과 공유하십시오.

**화면.** 가입 화면에서 필수 4개만 받도록 정리하고, 온보딩 화면을 신규 추가하며(건너뛰기 상단 배치), 프로필 화면에서 선택 항목을 조회·수정·삭제할 수 있게 합니다.

**중복 제거.** 챌린지 신청 화면의 계좌 유형 질문을 프로필 값 프리필로 전환합니다.

## 7. 완료 판정 기준

가입 화면에서 필수 입력이 이메일, 비밀번호, 닉네임, 필수 동의 넷뿐일 것. 마케팅 수신 동의가 별도 체크박스로 분리되어 있고 미동의 상태로도 가입이 완료될 것. 온보딩 2문항을 건너뛰어도 정상 회원으로 서비스 전체를 이용할 수 있을 것. UTM이 가입 시점에 자동 기록될 것. 동의 이력(시각, 버전, 항목별 여부)이 저장될 것. 프로필 화면에서 선택 항목과 마케팅 동의를 수정·철회할 수 있을 것. 챌린지 신청 화면에서 계좌 유형이 프리필될 것.

## 8. 작업 규칙

기존 파일을 통째로 다시 쓰지 말고 증분 편집만 하십시오. 완료 보고에 `git diff --stat` 을 반드시 포함하고, 삭제 줄 수가 추가 줄 수보다 많은 파일이 있으면 사유를 설명하십시오. 임시 파일과 백업 파일을 저장소에 남기지 마십시오. 모든 파일은 UTF-8로 저장하고 저장 후 검증하십시오. 기존 타입 계약을 변경해야 한다면 구현을 멈추고 먼저 질문하십시오. 문서에 없는 결정이 필요하면 임의로 정하지 말고 질문하십시오.

## 9. 함께 확인할 사항

작업 중 아래 불일치를 발견하면 임의로 고치지 말고 보고하십시오.

`contracts.ts` 의 `CHALLENGE_METRIC_KEYS` 는 현재 `study_checkin`, `source_review`, `criteria_check`, `learning_note` 네 개이고 `metricValue` 범위가 0에서 10입니다. 그런데 챌린지 설계 문서는 Day별로 라벨이 바뀌는 지표(원리금보장 비중, 총보수 등)를 전제하고 있습니다. 두 설계가 어긋나 있으므로 어느 쪽이 최신인지 운영자 확인이 필요합니다.

## 참고 (에이전트 전달 대상 아님)

이 문서에서 수집하기로 한 항목이 향후 마케팅에서 어떻게 쓰이는지 정리입니다.

| 항목 | 활용 |
|---|---|
| 이메일 | 뉴스레터 발송, 라이프사이클 메일, 광고 플랫폼 맞춤 대상 구성(처리방침 명시 후) |
| 연령대 | 세그먼트 분석, 광고 타겟 설정 검증, 커뮤니티 뱃지 |
| 퇴직연금 유형 | 콘텐츠 추천 분기, 뉴스레터 개인화, 전자책·챌린지 타겟팅 |
| 투자 경력 | 콘텐츠 난이도 조절 |
| 관심 주제 | 뉴스레터 섹션 개인화 |
| UTM | 채널별 가입 전환 측정, 광고 예산 배분 근거 |

광고 플랫폼 활용과 관련해 유의할 점이 하나 있습니다. Meta는 금융 서비스 광고주에 대해 신원과 규제 인가 확인 절차를 운영하며 적용 국가를 확대해 왔습니다. EVS는 투자자문업 미등록을 전략적으로 유지하고 있고 Neo의 익명성도 지켜야 하므로, 광고 집행 전에 해당 절차의 요구 사항을 먼저 확인해야 합니다. 데이터를 모으는 것과 광고를 집행할 수 있는 것은 별개 문제입니다.
