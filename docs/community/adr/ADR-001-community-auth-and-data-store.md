# ADR-001: 커뮤니티 인증 및 데이터 저장소 선택

> **상태:** 제안됨 — 운영자 결정 대기  
> **결정 필요 시점:** 커뮤니티 Phase 2 구현 시작 전  
> **범위:** 공개 읽기, 이메일 인증 회원의 게시물·댓글 작성, 권한 분리, 커뮤니티 데이터 보존  
> **비범위:** 기존 ETF 정적 데이터 빌드·`ETF_PRICES` D1·기존 ETF 탐색/비교/상세 화면의 데이터 구조

## 1. 맥락

Phase 2 목표는 비로그인 사용자의 공개 글 읽기와 이메일 인증 회원의 글·댓글 작성을 제공하는 것이다. 이를 위해서는 인증 세션, 사용자 식별, 권한 판정, 커뮤니티 데이터 저장, 서버 측 생성 시각, 소프트 삭제 및 변경 이력의 신뢰할 수 있는 저장 경계가 필요하다.

현재 전용 작업 브랜치에서 확인한 실제 구조는 다음과 같다.

| 확인 항목 | 확인 결과 | 해석 |
|---|---|---|
| 프런트엔드 배포 | Next.js `output: "export"`와 Cloudflare Pages `out` 배포 | 기존 ETF 화면은 정적 빌드 경계를 유지해야 한다. |
| Cloudflare D1 | `wrangler.toml`에 `ETF_PRICES` 바인딩만 존재 | 기존 가격 데이터 D1을 회원·커뮤니티 데이터로 확장하는 승인 근거가 없다. |
| Pages Functions | 가격·수익률 관련 API만 존재 | 인증·회원·커뮤니티 CRUD API는 구현되어 있지 않다. |
| 인증 의존성·환경 파일 | 인증 SDK, 승인된 인증 환경 변수 파일, 회원 DB 모델을 확인하지 못함 | 기존 코드에서 재사용할 인증·회원 구현이 없다. |
| 외부 연동 상태 | 현재 작업 설정에서 Supabase 및 Supabase API 연동은 비활성 상태 | 비활성 연동은 프로젝트 아키텍처 승인이나 사용 권한을 뜻하지 않는다. |
| 기존 문서 | `Auth_Security_Architecture_Advisory_20260806.md`는 자문 문서이며 Supabase·소셜 로그인 등을 제안 | SSOT 결정 대장에 따라 자문은 승인 결정으로 간주하지 않는다. |

따라서 **Phase 2에 필요한 인증·회원 DB 공급자는 아직 승인된 상태로 확인되지 않았다.** 사용자 메시지의 `미결정 사항은 다음과 같이 확정합니다: [결정 내용]`에는 실제 결정 값이 포함되지 않아, 공급자·이메일 방식·보존 기간의 선택을 새 승인으로 기록할 수 없다.

## 2. 결정 기준

| 기준 | 요구사항 |
|---|---|
| 정적 ETF 서비스 보호 | 기존 `output: "export"` 빌드와 `ETF_PRICES` D1 데이터 파이프라인을 변경하거나 결합하지 않는다. |
| 공개 읽기·인증 참여 | 읽기 API는 공개하되, 작성·댓글·수정·신고는 서버에서 검증한 인증 세션과 역할을 요구한다. |
| 이메일 인증 | 비밀번호를 직접 저장하지 않고, 이메일 매직 링크 또는 일회용 코드(OTP)로 인증한다. |
| 권한·소유권 | `guest`, `member`, `moderator`, `admin` 역할을 서버 기준으로 판정하고 작성자만 자신의 게시물을 수정할 수 있게 한다. |
| 개인정보 최소화 | 이메일 인증 식별자와 공개 닉네임을 분리하고, 공개 응답에는 이메일·내부 사용자 ID를 포함하지 않는다. |
| Cloudflare 호환성 | Cloudflare Pages Functions 또는 별도 Worker에서 안전한 서버 API와 비밀값 관리를 제공할 수 있어야 한다. |
| 운영 비용·복구 | 초기 비용, 무료 플랜 중단·제한, 백업·로그·감사 가능성, 이후 운영 비용을 명확히 한다. |

## 3. 선택지 A — Supabase Auth + Supabase Postgres를 커뮤니티 전용 저장소로 사용

이 선택지는 Supabase Auth의 이메일 매직 링크 또는 OTP 인증과 동일 프로젝트의 Postgres를 함께 사용한다. 커뮤니티 테이블은 Supabase Postgres에 두고, 기존 Cloudflare D1 `ETF_PRICES`와는 분리한다. Cloudflare Pages Functions는 커뮤니티 API의 서버 경계로 사용하거나, 승인된 경우 Supabase API를 호출하는 얇은 경계로 사용한다.

| 평가 항목 | 내용 |
|---|---|
| 이메일 인증 | Supabase Auth는 매직 링크와 이메일 OTP를 지원한다.[1] |
| 권한 모델 | JWT와 Postgres Row Level Security(RLS)를 결합해 행 단위 접근 제어를 지원한다.[1] |
| Cloudflare 호환성 | Cloudflare는 Worker에서 `supabase-js`와 Worker 비밀값으로 Supabase에 연결하는 공식 예시를 제공한다.[3] Pages Functions도 동일한 서버 측 비밀값 경계를 갖도록 별도 검증이 필요하다. |
| 초기 비용 | 공식 가격표 기준 Free는 월간 활성 사용자 50,000명, DB 500MB를 포함하지만 1주일 비활성 시 프로젝트가 일시 중지될 수 있다.[2] |
| 유료 기준 비용 | 공식 가격표 기준 Pro는 월 US$25이며, 월간 활성 사용자 100,000명과 8GB 디스크 등을 포함한다. 실제 청구는 배포 시점의 가격·사용량·이메일 전송 설정을 다시 확인한다.[2] |
| 보안 이점 | 인증과 DB 권한 정책을 일관되게 관리하고, 서비스 역할 키를 클라이언트에 노출하지 않는 구조를 만들 수 있다. |
| 보안·운영 위험 | RLS 정책 누락, 공개 키 범위 오해, 서비스 역할 키의 서버 외 노출, 리다이렉트 URL·이메일 템플릿·세션 수명 오설정이 주요 위험이다. |
| 구현 영향 | `@supabase/supabase-js` 도입, Supabase 프로젝트·이메일 발송 구성, 커뮤니티 전용 스키마·RLS·마이그레이션, Cloudflare Pages 비밀값 설정이 필요하다. |

**선택 시 필수 통제:** 브라우저에는 공개 가능한 anon/public 키만 사용하고, 서비스 역할 키는 Pages Functions 또는 승인된 서버 환경의 비밀값으로만 보관한다. 모든 `user_profiles`, 게시물, 댓글, 수정 이력, 제재·신고 테이블은 RLS 기본 거부 후 최소 권한 정책을 적용한다. 수정·소프트 삭제·역할 변경은 클라이언트 전달 역할값이 아니라 검증된 세션의 사용자 식별자와 서버 정책으로 판정한다.

## 4. 선택지 B — Cloudflare Pages Functions/Workers + 신규 커뮤니티 D1 + 별도 이메일 전송 공급자

이 선택지는 기존 `ETF_PRICES`와 별개의 신규 D1 데이터베이스를 커뮤니티 전용으로 생성하고, Cloudflare Pages Functions 또는 Worker에서 인증·세션·권한·CRUD를 구현한다. 이메일 인증을 위해서는 매직 링크 또는 OTP를 전송할 승인된 이메일 공급자가 추가로 필요하다. Cloudflare D1 자체는 사용자 인증 서비스를 제공하지 않으므로, 서명된 1회용 토큰·해시·만료·재전송 방지·세션 회전·이메일 발송 평판을 애플리케이션이 직접 책임져야 한다.

| 평가 항목 | 내용 |
|---|---|
| 이메일 인증 | 별도 이메일 전송 공급자와 자체 매직 링크 또는 OTP 구현이 필요하다. 이 공급자는 현재 승인되지 않았다. |
| 권한 모델 | D1에는 RLS와 동등한 내장 사용자 권한 경계가 없으므로 모든 쿼리의 역할·소유권 조건을 Pages Functions/Worker에서 강제해야 한다. |
| Cloudflare 호환성 | 기존 Cloudflare Pages·Functions·D1 운영 영역에 맞지만, 회원·세션 보안 책임도 전부 서비스 측에 남는다. |
| 초기 비용 | Cloudflare D1은 Free 및 Paid Workers 플랜에서 사용할 수 있다. Workers Paid 플랜은 월 최소 US$5이며, D1의 실제 비용은 읽기·쓰기 행 수와 저장량을 기준으로 산정된다.[4] |
| 이메일 비용 | 별도 이메일 공급자의 발송량·도메인 인증·반송 처리 비용은 포함되지 않으며, 공급자 승인 후 산정해야 한다. |
| 보안 이점 | 데이터와 서버 경계를 Cloudflare 내에 집중할 수 있고, ETF 데이터 D1과 별도 DB·바인딩·마이그레이션으로 격리할 수 있다. |
| 보안·운영 위험 | 인증 프로토콜, 토큰 저장·회전·폐기, 이메일 전달성, 계정 열거 방지, 속도 제한, 세션 탈취 방지, 탈퇴·보존·감사 로그를 직접 설계·테스트해야 한다. |
| 구현 영향 | 신규 D1 바인딩과 마이그레이션, 이메일 공급자 설정, Pages Functions API, 세션 키·암호화 키·발신 도메인, 보안·부하·복구 테스트가 필요하다. |

**선택 시 필수 통제:** 기존 `ETF_PRICES` D1과 같은 DB나 테이블에 회원 데이터를 저장하지 않는다. 인증 토큰은 원문이 아닌 안전한 검증값 또는 해시 형태로 관리하고, 일회성·만료·재전송 제한·사용 후 폐기를 구현한다. 모든 작성·수정·삭제 API는 세션 검증 후 `WHERE author_id = authenticated_user_id`와 동등한 소유권 조건을 강제하며, 역할은 서버 저장소의 신뢰 가능한 값으로만 확인한다.

## 5. 비교와 권고 방향

| 기준 | 선택지 A: Supabase Auth + Postgres | 선택지 B: Cloudflare + 신규 D1 + 자체 이메일 인증 |
|---|---|---|
| 구현 속도 | 높음. 인증·세션·RLS를 제공한다. | 낮음. 인증·세션·이메일 전송을 직접 구현한다. |
| 보안 책임 | RLS·Auth 설정을 정확히 구성하고 운영한다. | 인증 프로토콜과 권한·세션 보안 전체를 직접 구현·운영한다. |
| Cloudflare와의 결합 | Pages/Workers에서 HTTP 기반으로 연동 가능하다.[3] | 네이티브 호환성이 높다. |
| 기존 ETF D1 격리 | Postgres 프로젝트로 물리·논리적 분리가 쉽다. | 신규 D1 바인딩·DB를 별도로 만들면 가능하다. |
| 초기 비용 | Free 가능하나 비활성 중지 제약이 있고, 상시 운영은 Pro US$25/월부터 검토한다.[2] | D1은 기존 Cloudflare 운영과 결합할 수 있으나, Paid Workers 최소 US$5/월과 별도 이메일 공급자 비용·운영 비용을 함께 고려해야 한다.[4] |
| 운영 난이도 | 중간. 공급자 설정·RLS·비밀값 관리가 핵심이다. | 높음. 이메일 인증·세션·보안 운영을 직접 책임진다. |

**권고:** 기존 자문 문서의 방향과 Phase 2의 최소 기능·보안 요구를 고려하면, 운영자가 **선택지 A를 명시적으로 승인하는 경우에만** Supabase Auth의 이메일 매직 링크 또는 OTP와 커뮤니티 전용 Postgres/RLS 구조를 적용하는 것이 구현·보안 책임의 균형이 가장 좋다. 이 권고는 공급자 채택 결정이 아니며, 운영자 승인 전에는 코드·마이그레이션·시크릿·커넥터를 변경하지 않는다.

선택지 B는 공급자 종속성을 줄이고 Cloudflare에 집중할 수 있지만, 이메일 인증과 세션 보안의 직접 구현 범위가 커서 1인 운영·최소 기반의 초기 선택으로는 더 높은 보안·운영 위험을 수반한다. 이를 선택하려면 이메일 전송 공급자와 보안 설계 검토를 추가 승인해야 한다.

## 6. 운영자 결정 요청

다음 항목을 명시적으로 승인해야 Phase 2 구현을 재개할 수 있다.

| 결정 ID | 요청 사항 | 선택 또는 입력 값 |
|---|---|---|
| ADR-001-A | 인증·커뮤니티 DB 구조 | A. Supabase Auth + Postgres / B. Cloudflare + 신규 D1 + 별도 이메일 공급자 |
| ADR-001-B | 이메일 인증 UX | 이메일 매직 링크 / 이메일 OTP / 다른 승인 방식 |
| ADR-001-C | 이메일 발신 정책 | 승인된 발신 도메인·발신자 이름·발송 서비스의 설정 담당자 |
| ADR-001-D | 커뮤니티 데이터 위치 | 선택지 A의 신규 Supabase 프로젝트 또는 선택지 B의 **신규** 커뮤니티 D1. 기존 `ETF_PRICES` D1 사용은 불가. |
| ADR-001-E | 개인정보 보존 결정 | 탈퇴 콘텐츠 처리, 인증 식별자·신고·로그·백업 보존 기간과 파기 방법 |
| ADR-001-F | 운영 권한 | 초기 admin 지정 절차, moderator 부여·회수·중대 제재의 상호 검토 방식 |

승인 응답에는 최소한 `ADR-001-A`와 `ADR-001-B`의 선택, `ADR-001-D`의 저장 위치를 포함해야 한다. 비밀값, API 키, SMTP 자격 증명, 관리자 이메일 주소는 이 문서나 채팅에 기재하지 않는다. 선택 이후에만 필요한 변수 이름과 Cloudflare·공급자 설정 경로를 별도로 안내한다.

|---|---:|
| 상단 메뉴·정적 ETF 화면 코드 변경 | 금지 |
| 커뮤니티 라우트·API·UI 코드 작성 | 금지 |
| D1·Postgres 마이그레이션 실행 | 금지 |
| Supabase·이메일 공급자·Cloudflare 외부 설정 변경 | 금지 |
| 시크릿·환경 변수 생성 또는 기록 | 금지 |
