# ETF Campus 분배금 업데이트 자동화 실행안

**기준일:** 2026-08-15  
**목표:** 운용사 공식 공지와 KRX KIND 공시를 반복 수집·대조하여, 배당형 ETF의 분배금 정보와 분배금 반영 수익률을 안전하게 최신화한다.

## 1. 자동화의 원칙

분배금 자동화는 ‘새 숫자를 찾으면 즉시 사용자 화면에 반영’하는 작업이 아니다. 원문을 불변으로 보존하고, 후보·증거·대조·수익률 산출을 차례로 수행한 뒤, 각 품질 등급에 맞는 데이터만 게시하는 작업이다.

원문은 절대 덮어쓰지 않는다. 모든 수집 파일은 `raw/{source_owner}/{year}/{month}`에 새 파일로 저장하고 SHA-256을 기록한다. 파서가 실패하거나 수치·날짜가 충돌하면 기존 게시 데이터는 유지하고 신규 데이터만 검토 큐로 보낸다.

## 2. 한 번의 자동 실행 흐름

```text
1. 대상 선정
   → 배당형 122개 워치리스트와 최근 45일 공식 공지 URL을 확인

2. 원문 수집
   → 운용사 공지·KIND 공시를 원시 파일과 해시로 보존

3. 후보·증거 생성
   → 종목코드·주당 분배금·분배락일·지급일을 행 위치와 함께 추출

4. 대조·커버리지 갱신
   → 운용사 후보와 KIND 금액·일정·개별 분배락 공시를 대조
   → 월별 분배 또는 공식 확인된 무분배 상태를 갱신

5. 수익률 생성
   → D2 분배금 반영 수익률을 산출
   → KIND 대조가 완료된 이벤트만 검증 TR에 반영

6. 품질 검증
   → 원문 해시·CSV 스키마·금액 충돌·가격 이력·테스트를 확인

7. 게시 또는 보류
   → 정상 결과만 정적 JSON/CSV를 갱신
   → 검토·차단 건은 게시하지 않고 보고서에만 기록
```

## 3. 자동 게시 상태 규칙

| 상태 | 필요한 조건 | 사용자 화면 동작 | 자동 게시 |
|---|---|---|---|
| 수집 후보 | 공식 원문을 읽었으나 대조 전 | 표시하지 않음 | 금지 |
| D1 분배금 정보 | 운용사 공식 공지 또는 KRX 일괄공시에서 금액·일정 확보 | 최근 분배금·분배락일·지급예정일 표시 | 가능 |
| D2 분배금 반영 수익률 | D1 + 공식 분배락일 + 당일 가격 + 금액 충돌 없음 + 최소 2개 이벤트 | `분배금 반영 수익률(추정)` 차트 활성화 | 가능 |
| D3 검증 TR | D2 + KIND 개별 공시 대조 + 커버리지·기업행동 검증 | `검증 TR` 차트 활성화 | 가능 |
| 검토 필요 | 새 표 구조·날짜 누락·외부 대조 불일치 | 기존 데이터 유지, 상태 안내 | 금지 |
| 차단 | 원문 해시 오류·금액 충돌·파서 구조 오류 | 기존 데이터 유지 | 금지 |

D1과 D2는 자동 게시가 가능하지만, D3은 초기에는 자동 게시 대신 검토용 변경 목록을 만들고 누적 품질을 확인한 뒤 자동 게시 범위를 넓힌다.

## 4. 실행 주기

분배금 공지는 월말·월중순과 분배락일 전후에 집중된다. 분 단위 또는 시간 단위 반복 실행은 필요하지 않다.

| 실행 시점 | 처리 목적 | 대상 |
|---|---|---|
| 평일 오전 08:00 KST | 전일 저녁 이후 공지·KIND 접수 건 확인 | 122개 워치리스트, 최근 45일 URL |
| 평일 17:30 KST | 당일 공지·종가 반영 후 D2 산출 | 분배락일 전후 ETF, 새 후보 |
| 월말·월중순 보강 실행 | 운용사 일괄공시와 배당형 워치리스트 집중 대조 | KODEX·TIGER·RISE·ACE 등 |
| 주 1회 점검 | 원문 해시·미처리 검토 큐·커버리지 결손 보고 | 전체 배당형 워치리스트 |

국내 휴장일에는 실행해도 수집·게시가 없는 정상 종료로 처리한다. 공지 URL이 없는 날은 오류가 아니라 `no_new_source`로 기록한다.

## 5. 운영 스크립트 구조

현재 스크립트는 이미 기능별로 분리되어 있다. 예약 실행에서는 이들을 직접 순서대로 나열하지 않고, 하나의 표준 실행기 `scripts/run_distribution_update.py`를 추가한다.

```text
run_distribution_update.py
  ├─ collect_distribution_sources.py
  ├─ build_distribution_candidates.py
  ├─ reconcile_kind_distribution_notices.py
  ├─ reconcile_kind_distribution_events.py
  ├─ calculate_estimated_distribution_returns.py
  ├─ calculate_total_return_history.py
  ├─ build_return_display_status.py
  └─ validate / report / publish gate
```

표준 실행기는 각 단계의 시작·종료시각, 입력 원문 수, 생성 후보 수, D1·D2·D3 게시 수, 경고·차단 사유를 `distribution_collection_runs.csv`와 JSON 보고서에 남긴다. 어떤 단계라도 오류가 나면 이후 게시 단계를 실행하지 않는다.

출력은 바로 `public/data`를 덮어쓰지 않는다. 먼저 `data/staging/distributions/{run_id}`에 생성하고, 모든 검증이 통과했을 때만 원자적으로 배포 대상 JSON·CSV를 교체한다. 이 규칙은 부분 실행이나 네트워크 오류가 사용자 차트에 반영되는 것을 방지한다.

## 6. 예외 처리

| 상황 | 자동 처리 | 운영자 확인 내용 |
|---|---|---|
| 운용사 공지 표 구조 변경 | 해당 운용사 파서만 차단, 나머지 운용사 계속 처리 | 원문과 파서 버전 비교 |
| 같은 종목·날짜의 금액 충돌 | D1·D2·D3 게시 보류 | 원문·외부 대조·정정 공시 확인 |
| KIND 개별 공시 없음 | D1/D2까지만 진행, D3 보류 | 접수번호·원문 확보 여부 |
| 가격 이력 결손 | D2·D3 보류, 분배금 D1은 표시 | 분배락일 종가 백필 |
| HTTP 429·5xx | 지수 백오프로 최대 3회 재시도 후 보류 | 다음 실행에서 재시도 |
| 원문 해시 검증 실패 | 즉시 차단, 기존 게시 값 유지 | 수집 파일·전송 오류 조사 |

## 7. 실행 환경 선택지

| 방식 | 동작 | 장점 | 비용 | 설정 난도 |
|---|---|---|---|---|
| 저장소 예약 실행 | 현재 Python 파이프라인을 정해진 시각에 실행하고, 검증 결과를 변경 요청으로 생성 | 현재 정적 CSV/JSON·표준 라이브러리 구조를 거의 그대로 사용 | 낮음 | 낮음 |
| Cloudflare 예약 작업 | 수집·대조를 서비스 내부의 예약 작업으로 수행하고, 승인된 상태를 D1·정적 데이터에 반영 | 운영 상태 화면·알림·예외 관리 확장에 유리 | 낮음~중간 | 중간~높음 |
| 혼합 운영 | Python이 원문·증거를 수집하고, 승인 결과만 서비스 데이터 계층에 게시 | 원문 감사성과 서비스 반영 속도를 함께 확보 | 중간 | 중간 |

현재 제약에서는 세 방식 모두 가능하다. 저장소 예약 실행은 가장 가벼운 출발점이고, Cloudflare 예약 작업은 운영 화면과 실시간성 요구가 커질 때 적합하며, 혼합 운영은 감사 원장과 사용자 서비스 계층을 명확히 분리해야 할 때 적합하다.

## 8. 단계적 도입 체크리스트

### 단계 1: 자동 수집과 보고서

공식 원문 수집, 해시 보존, 후보·증거 생성, 검증 보고서 생성까지만 예약 실행한다. 자동 게시는 하지 않고, 정상·검토·차단 건수가 포함된 변경 목록을 확인한다.

### 단계 2: D1 자동 게시

원문 해시, 필수 컬럼, 금액·날짜 형식, 충돌 부재를 통과한 D1 분배금 정보만 상세 카드에 자동 반영한다. 이 단계에서는 수익률 차트가 바뀌지 않는다.

### 단계 3: D2 자동 게시

운용사 공식 분배락일과 가격 이력이 있는 ETF에서만 D2 시계열을 생성한다. 화면에는 `운용사 공식 공지 기반`과 커버리지 기간을 함께 표시한다.

### 단계 4: D3 확대

KIND 대조와 무분배·기업행동 커버리지가 축적된 ETF부터 검증 TR을 공개한다. 초기에 D3은 자동 게시 전 검토 목록을 통과하도록 하고, 반복 정확도가 확인된 후 자동 승격 범위를 넓힌다.

## 9. 운영 성공 지표

자동화가 정상적으로 운영되는지는 다음 지표로 판단한다. 원문 해시 성공률, 파서 성공률, 후보 충돌률, 검토 큐 해소 시간, D1·D2·D3별 공개 ETF 수, D2·D3 수익률의 데이터 결손률을 주 단위로 확인한다.

원문 수집량이 많아지는 것보다, `검토 필요`가 사용자 화면을 바꾸지 않고 빠르게 해소되는 것이 더 중요하다.
