# ETF Campus 일일 API·분배금 통합 배치 운영안

**기준일:** 2026-08-15  
**목표:** 일일 ETF 가격·지표 API 갱신과 분배금 수집·검증·게시 판단을 한 번의 일관된 배치로 실행한다.

## 1. 결론

가능하다. 현재 `scripts/update_daily_data.py`는 공식 가격 API로 ETF 마스터·기간 수익률·연금 원장을 원자적으로 갱신하고 백업을 남긴다. 이 작업 뒤에 분배금 수집·대조·수익률 생성 단계를 붙이면, 하나의 기준일(`as_of_date`)에 가격·분배금·D2·D3 표시 상태를 함께 만들 수 있다.

다만 ‘새 지급 내역만 확인해 즉시 업데이트’라는 규칙은 `신규`뿐 아니라 `정정`, `충돌`, `취소`, `미확정`을 구분해야 안전하다. 같은 종목·분배락일의 금액이나 지급일이 바뀌는 정정 공시는 기존 수치를 덮어쓰지 않고 검토 상태로 보내야 한다.

## 2. 통합 배치 순서

```text
배치 시작·실행 잠금
  → 공식 가격 API 갱신
  → 가격 이력·기본 PR 수익률 갱신
  → 분배금 공식 원문 증분 수집
  → 후보·증거·커버리지 재생성
  → 신규·정정·충돌 이벤트 판별
  → KIND 대조·D1/D2/D3 상태 산출
  → 정적 JSON·CSV를 임시 스테이징에 생성
  → 데이터·테스트·원문 무결성 검증
  → 전체 통과 시 한 번에 게시
  → 실행 보고서·검토 큐 기록
```

가격 API 단계가 실패하면 D2·D3 수익률은 산출하지 않는다. 분배금 원문 수집에 실패해도 기존 게시 데이터를 유지하며, 새 공지가 없거나 접근이 지연된 상태를 보고서에 남긴다. 즉, 부분 실패가 사용자에게 빈 차트나 잘못된 수익률로 보이지 않게 한다.

## 3. 증분 판별 규칙

분배 이벤트는 `ticker + issuer_ex_date + event_sequence`를 자연 키로 쓴다. 이벤트의 금액·지급일·원문 해시·원천 URL은 버전 필드로 유지한다.

| 판별 | 조건 | 자동 처리 |
|---|---|---|
| 신규 | 자연 키가 없고 공식 원문·필수 필드가 정상 | 후보·증거를 추가하고 D1/D2/D3 게이트를 다시 계산 |
| 동일 | 자연 키와 금액·일정·원문 해시가 동일 | 재계산하지 않고 실행 이력만 기록 |
| 정정 | 자연 키는 동일하나 금액·지급일·원문 해시가 변경 | 기존 공개 값을 삭제하지 않고 `review_required`로 보류 |
| 충돌 | 서로 다른 공식 원천의 동일 키 필드가 상충 | D1/D2/D3 게시 차단, 원문 링크 포함 검토 큐 생성 |
| 취소·철회 | 공식 원문에 취소·정정 공시가 명시 | 이전 이벤트를 보존하고 `cancelled` 또는 `superseded` 이력 추가 |
| 미확정 | 금액·분배락일·가격 중 필수 필드 결손 | D1 일부 정보만 표시하거나 수집 상태 유지 |

자동화는 ‘새 지급일만’이 아니라 **새 지급 이벤트와 기존 이벤트의 정정 여부**까지 확인해야 한다. 지급일은 보통 분배락 후에 확정되거나 변경될 수 있어, 지급일만을 이벤트 키로 쓰면 정정 이벤트를 중복으로 오인할 수 있다.

## 4. 영향 범위 최소화

일일 가격 갱신은 전체 ETF에 수행하되, 분배금 단계는 122개 배당형 워치리스트와 최근 45일의 공식 공지 대상만 처리한다. 신규·정정 분배 이벤트가 있는 ETF만 D2·D3 시계열을 재계산한다.

| 변경 종류 | 재생성 범위 |
|---|---|
| 가격만 변경 | PR·기본 기간 수익률, 이미 활성화된 D2/D3의 마지막 일자 |
| 신규 분배 이벤트 | 해당 ETF의 분배락일 이후 D2/D3 시계열과 표시 상태 |
| 지급일만 정정 | D1 일정 정보와 상세 카드, D2/D3 시계열은 불변 |
| 금액·분배락일 정정 | 해당 ETF의 정정 이벤트 시점 이후 D2/D3 전체 재계산, 자동 게시 보류 |
| KIND 검증 승격 | D3 상태·시계열만 재생성 |

이 방식이면 1,160개 ETF 전체의 분배금 원문을 매일 다시 수집하지 않으며, 기존 데이터와 결과가 변하지 않은 종목은 재계산하지 않는다.

## 5. 단일 표준 실행기

`update_daily_data.py`를 직접 수정해 모든 도메인 규칙을 넣기보다는, 상위 실행기 `scripts/run_daily_update.py`를 새로 두는 것이 좋다. 기존 가격·분배금 스크립트는 재사용하고, 상위 실행기가 순서·잠금·스테이징·게시 판단만 맡는다.

```text
run_daily_update.py
  1. update_daily_data.py
  2. 가격 이력 갱신 및 기존 API 내보내기
  3. collect_distribution_sources.py
  4. build_distribution_candidates.py
  5. reconcile_kind_distribution_notices.py
  6. reconcile_kind_distribution_events.py
  7. calculate_estimated_distribution_returns.py
  8. calculate_total_return_history.py
  9. build_return_display_status.py
  10. validate → publish
```

상위 실행기는 `run_id`, 기준일, 각 단계의 상태, 신규·정정·충돌 이벤트 수, D1·D2·D3 게시 수, 경고·차단 사유를 `distribution_collection_runs.csv`와 JSON 보고서에 기록한다. 동시에 실행되는 두 배치가 파일을 덮어쓰지 않도록 실행 잠금을 둔다.

## 6. 게시 방식

출력 파일은 곧바로 `data`와 `public/data`를 덮어쓰지 않는다. 먼저 `data/staging/{run_id}`에 생성하고, 아래 조건을 모두 통과했을 때만 현재 버전을 교체한다.

| 검증 게이트 | 필수 여부 |
|---|---|
| 가격 API 종목 수·가격 커버리지 임계치 | 필수 |
| 원문 SHA-256 무결성 | 필수 |
| CSV/JSON 스키마·중복 키 검사 | 필수 |
| 신규 이벤트의 필수 필드 검사 | 필수 |
| 금액·일정 충돌 0건 또는 명시적 보류 | 필수 |
| D2/D3 시계열의 가격 결손 없음 | 해당 ETF별 필수 |
| 회귀 테스트·정적 빌드 | 게시 전 필수 |

검토 필요·차단 건은 보고서와 검토 큐에만 추가하고, 마지막 정상 게시 버전을 계속 제공한다.

## 7. 하루 한 번과 두 번의 선택

일일 가격 API가 종가 기준으로 업데이트된다면 장 마감 후 한 번의 통합 배치가 기본이다. 분배금 공지의 신속한 반영이 중요하면 오전에 원문 탐색만 한 번 더 수행할 수 있지만, 수익률 계산과 게시까지는 장 마감 후 배치에서 수행하는 것이 가격 기준 일관성에 유리하다.

| 선택 | 흐름 | 적합한 목적 |
|---|---|---|
| 장 마감 후 1회 | 가격·분배금·D2/D3·게시를 한 번에 실행 | 단순성, 일관된 기준일, 낮은 운영 부담 |
| 오전 탐색 + 장 마감 후 게시 | 오전에는 신규 공지만 수집, 오후에 가격과 함께 검증·게시 | 지급 일정의 빠른 발견과 수익률 기준일 일치 |

## 8. 운영 예외

공식 페이지의 표 구조가 바뀌거나 HTTP 오류가 나는 날은 그 운용사·원천만 보류한다. 전체 가격 업데이트와 다른 운용사 데이터는 계속 처리할 수 있지만, 영향 ETF의 D2/D3는 기존 상태를 유지한다. 원문 접근 오류는 최대 3회 재시도하고, 이후에는 다음 배치에서 다시 시도한다.

휴장일은 `no_market_data`로 정상 종료한다. 새 분배금 공지가 없는 날은 `no_new_distribution`으로 정상 종료한다. 둘 다 장애로 집계하지 않는다.

## 9. 도입 순서

1. 상위 실행기와 스테이징·실행 잠금을 만든다.
2. 기존 일일 가격 API 업데이트 뒤에 분배금 수집·검증 단계를 연결한다.
3. 2~4주 동안은 보고서와 검토 큐만 생성하고 자동 게시하지 않는다.
4. 정상·동일 이벤트의 비율과 파서 오류율을 확인한다.
5. D1부터 자동 게시하고, D2·D3은 품질 게이트별로 순차 활성화한다.

이 방식은 매일 새로운 지급 내역만 빠르게 반영하면서도, 정정 공시와 데이터 충돌로 인한 잘못된 차트 업데이트를 방지한다.
